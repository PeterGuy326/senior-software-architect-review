# 09 · 软件架构演化与维护（教材第 10 章 / 大纲 §9）

> 近年综合知识与案例的增长点。过线重点不是背“演化很重要”，而是能识别演化类型、选择渐进迁移方法，并用约束和验证保证演化后架构仍然正确。

## 1. 演化对象与驱动力

架构演化是系统在生命周期内对**构件、连接件和约束**进行受控改变，使其继续满足业务与质量目标。

常见驱动力：

- 业务规则、组织边界和法规变化；
- 性能、容量、可靠性或安全目标提升；
- 技术栈停服、基础设施迁移和国产化替代；
- 架构腐化、循环依赖和技术债；
- 团队规模、交付节奏和运维模式变化。

演化的目标不是“使用新技术”，而是在可接受风险和成本内持续满足需求。

## 2. 架构腐化与可持续演化

### 架构漂移与侵蚀

- **架构漂移（drift）**：实现增加了原架构未规定、但暂未违反约束的设计决策。
- **架构侵蚀（erosion）**：实现直接破坏分层、依赖方向、接口或数据所有权等架构约束。

识别手段：依赖图、架构适应度函数、静态扫描、运行时追踪、变更影响分析和架构决策记录 ADR。

### 可持续演化原则

- 先明确不变量：业务契约、数据约束、安全边界和关键 SLO；
- 变化点封装，稳定接口与实现解耦；
- 小步、可回退、可观测；
- 架构文档、代码和部署状态同步演化；
- 每次演化都重新验证关键质量属性。

## 3. 演化分类

### 按发生时机

| 类型 | 特征 | 例子 |
|---|---|---|
| 设计时演化 | 尚未运行，调整模型与设计 | 修改分层、替换存储方案 |
| 运行前演化 | 停机部署新版本 | 蓝绿切换前升级数据库结构 |
| 有限制运行时演化 | 部分服务或流量暂停 | 分批滚动升级 |
| 运行时演化 | 系统持续服务时动态调整 | 服务发现、动态路由、插件热加载 |

### 静态演化与动态演化

- **静态演化**：修改后重新构建或重启系统。
- **动态演化**：系统运行中增删、替换或重连构件，并保持状态与约束一致。

常见原子操作：增加、删除、替换构件；增加、删除连接；更新接口、参数或约束。复杂演化应分解为可验证的原子操作序列。

### 正交演化

把功能变化与运行平台、部署拓扑等变化分离，在不同维度独立描述和组合，减少一个维度修改对其他维度的连锁影响。答题关键词是“关注点分离、独立变化、组合验证”。

## 4. 动态演化的关键问题

1. **安全点**：何时可以替换构件，避免正在处理的请求被截断；
2. **状态迁移**：内存状态、会话和未完成事务如何转移；
3. **依赖顺序**：调用方与提供方版本如何兼容；
4. **约束保持**：替换后是否仍满足连接、容量和安全规则；
5. **失败回退**：迁移失败能否恢复原拓扑和数据；
6. **可观测性**：新旧版本的错误率、延迟和结果是否可对比。

常用工程技术：版本化接口、兼容读写、双写校验、影子流量、金丝雀、蓝绿发布、特性开关和自动回滚。

## 5. 遗留系统渐进迁移模式

### 绞杀者模式（Strangler Fig）

在旧系统前建立统一入口，把新能力逐步路由到新服务；旧模块随迁移完成逐步缩小，避免 Big Bang 重写。

```text
统一入口 → 新服务（已迁移功能）
        └→ 旧系统（未迁移功能）
```

### 抽象分支（Branch by Abstraction）

先在调用方和旧实现之间增加抽象层，再并行实现新能力，最后切换实现并删除旧代码。适合不能长期维护代码分支的核心模块。

### 防腐层（ACL）

在新旧模型之间做协议与语义转换，避免旧系统领域模型污染新系统。

### 并行运行与影子流量

- 并行运行：新旧系统同时处理，比较业务结果；
- 影子流量：复制真实流量到新系统但不影响正式结果；
- 双写必须配合对账、幂等和明确的主数据来源。

## 6. 数据与接口演化

### 接口兼容

- 优先向后兼容：新增可选字段，不随意删除或改变语义；
- 使用版本号、消费者契约测试和废弃窗口；
- 协议升级时明确调用链顺序，通常先升级提供方向后升级调用方。

### 数据库演化

推荐“扩展—迁移—收缩”：

1. 扩展：增加新字段或新表，保持旧代码可运行；
2. 迁移：双读/双写、回填历史数据并对账；
3. 切换：新模型成为主路径；
4. 收缩：观察稳定后删除旧结构。

禁止在一次发布中直接完成破坏性字段修改并假设所有服务同步升级。

## 7. 演化评估

评估应同时覆盖：

- **功能正确性**：关键业务结果一致；
- **结构约束**：层次、依赖、接口和数据所有权未被破坏；
- **质量属性**：性能、可用性、安全性、可修改性是否达到目标；
- **演化成本**：开发、迁移、双轨运行和回退成本；
- **风险**：数据损坏、兼容失败、容量不足及组织能力缺口。

### 演化过程已知

已知原子操作和执行顺序时，可逐步检查前置条件、约束保持及每一步的可回退性。

### 演化过程未知

只知道演化前后状态时，需要比较架构模型、依赖图、接口契约和质量指标，识别无法解释的变化与潜在侵蚀。

## 8. 架构维护

### 四类软件维护

- **改正性**：修复缺陷；
- **适应性**：适配环境、平台或法规变化；
- **完善性**：增强功能或性能；
- **预防性**：重构、消除隐患和降低未来成本。

### 架构级维护活动

- 架构知识管理：ADR、视图、约束和权衡理由；
- 修改管理：影响分析、变更边界、评审和回归验证；
- 版本管理：架构基线、接口版本、部署拓扑和依赖清单；
- 可维护性度量：圈复杂度、耦合、内聚、变更影响范围、构建与恢复时间。

## 9. 案例答题模板

```text
结论：采用绞杀者模式进行渐进演化，不进行一次性重写。
路径：先建立网关和防腐层，再拆低耦合边缘能力，最后迁移核心域。
数据：扩展—迁移—收缩，双写期间以旧库为主并持续对账。
发布：影子流量 → 1% 金丝雀 → 分批扩流 → 全量，任一指标超阈值自动回滚。
验证：比较新旧结果、P99、错误率、资源量和数据差异，达到门槛后才进入下一阶段。
```

高分答案必须同时包含：迁移顺序、数据策略、流量策略、回退方案和量化门槛。

## 10. 论文落地骨架

1. 遗留架构与演化驱动力；
2. 目标架构和关键约束；
3. 演化路线与模式选择；
4. 数据、接口、发布和回退设计；
5. 风险控制与团队协作；
6. 量化效果及仍存在的权衡。

可写指标：发布周期、变更失败率、MTTR、缺陷率、P99、单次回退时间、数据差异率、受影响服务数。

## 11. 高频易错点

- 演化不等于重写，也不等于微服务化。
- 只画目标架构，不写迁移路径，无法回答“如何演化”。
- 双写不是免费的一致性方案，必须明确主写、补偿与对账。
- 动态演化不能忽略状态迁移和安全点。
- 新技术收益必须与迁移成本、团队能力和回退难度一起权衡。
