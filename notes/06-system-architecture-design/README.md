## 6.1 软件架构概念

### 6.1.1 定义

软件架构 = **构件（Component）** + **连接件（Connector）** + **约束（Constraint）**。IEEE 1471–2000 定义为"一个系统的基本组织，体现在其组件、组件之间及组件与环境之间的关系，以及指导其设计和演化的原则中"。软件架构 ≠ 软件设计，架构关注**全局结构、非功能属性、跨部门决策**；设计关注局部实现。

### 6.1.2 发展历程（4 个阶段）

| 阶段 | 时期 | 特征 |
|---|---|---|
| **"无"架构设计阶段** | 1960s 以前 | 汇编语言、以子程序为基础，无模块化概念 |
| **萌芽阶段** | 1970s | 结构化程序设计（Dijkstra），出现"控制流图"、模块化思想 |
| **初期阶段** | 1980s | 面向对象兴起，出现构件、UML 建模，Perry & Wolf 首次提出"软件架构" |
| **高级阶段** | 1990s 至今 | 架构风格 / ADL / 4+1 视图 / DSSA / 产品线 / 基于架构的开发 ABSD |

### 6.1.3 软件架构生命周期（六阶段）

**需求分析 → 架构设计 → 架构文档化 → 架构复审 → 架构实现（构件组装）→ 架构演化（部署与后开发维护）**。其中"需求 → 设计"以架构需求说明书为输入产出架构模型；"文档化 → 复审"用于消除风险；"实现 → 演化"贯穿整个生命周期。

### 6.1.4 4+1 视图模型（Kruchten，RUP 采用）

| 视图 | 关注者 | 关注点 | 常用图 |
|---|---|---|---|
| **逻辑视图** Logical | 最终用户 / 分析师 | 系统功能、领域对象 | 类图、对象图、状态图 |
| **开发视图** Development | 程序员 / 项目经理 | 模块组织、包/子系统划分、复用与分层 | 包图、组件图 |
| **进程视图** Process | 系统集成人员 | 并发、同步、性能、可用性 | 活动图、顺序图 |
| **物理视图** Physical | 系统工程师 | 硬件拓扑、部署、通信 | 部署图 |
| **场景视图** Scenarios（+1） | 全体 | 用例驱动，串联其余四视图 | 用例图 |

### 6.1.5 架构描述语言 ADL

- **三要素**：构件、连接件、体系结构配置（Configuration）
- **典型 ADL**：UniCon、Rapide、Wright、C2、ACME、Darwin、xADL
- **与 UML 对比**：UML 通用性强、标准化好，但对连接件和约束的语义描述弱；ADL 专用于描述架构，语义更精确。
- **IEEE 1471–2000**：系统 / 架构 / 架构描述 / 涉众 / 关注点 / 视点 / 视图 / 库视点 —— **考点原文常直接命题**。

## 6.2 基于架构的软件开发方法 ABSD（Architecture-Based Software Development）

### 6.2.1 核心思想（三个基础）

1. **功能分解**：使用模块内**高内聚、模块间低耦合**原则。
2. **通过选择架构风格实现质量属性和商业需求**。
3. **软件模板**：定义构件之间的交互与通信机制。

**三大驱动力**：**功能需求 + 质量属性 + 商业需求**。ABSD 是**用例驱动 + 质量场景驱动**的开发方法。

### 6.2.2 关键概念

- **设计元素**：架构中的基本组成单元（子系统、构件、连接件）。
- **视角（Perspective）与视图（View）**：视图是一组视角的产物，视角描述"看什么、怎么看"。
- **用例（Use Case）**：捕获**功能需求**。
- **质量场景（Quality Scenario）**：捕获**非功能需求**，六要素——刺激源、刺激、环境、制品、响应、响应度量（同 7.1 质量属性场景）。

### 6.2.3 ABSD 六阶段（★必背★）

| 阶段 | 目标 | 关键活动 |
|---|---|---|
| ① **体系结构需求** | 获取用户需求、标识构件 | 需求获取 → 标识构件（生成初始类图、分组、构件打包）→ 需求评审 |
| ② **体系结构设计** | 提出架构方案 | 选择架构风格 → 映射构件 → 分析构件相互作用 → 产生架构 → 设计评审 |
| ③ **体系结构文档化** | 输出规范文档 | 主要产出：**架构规格说明书** + **软件架构质量设计说明书**（两大文档） |
| ④ **体系结构复审** | 尽早发现问题 | 由外部人员参与，主要发现潜在风险、验证需求覆盖率；至少一次里程碑评审 |
| ⑤ **体系结构实现** | 落地为代码 | 分析设计 → 构件实现 → 构件组装 → 系统测试 |
| ⑥ **体系结构演化** | 应对需求变更 | 演化步骤：**需求变化归类 → 制定演化计划 → 修改构件 → 更新构件 → 构件组装与测试 → 技术评审** |

> 记忆口诀：**"求 - 计 - 档 - 审 - 现 - 化"**（需求 / 设计 / 文档 / 复审 / 实现 / 演化）。

## 6.3 软件架构风格（★★★ 必考主表）

### 6.3.1 五大类风格总览

| 大类 | 子风格 |
|---|---|
| **数据流风格** | 批处理序列、管道-过滤器 |
| **调用/返回风格** | 主程序-子程序、面向对象、层次型、C/S（含二层 / 三层 / B/S） |
| **独立构件风格** | 进程通信、事件驱动（隐式调用 / 发布-订阅） |
| **虚拟机风格** | 解释器、基于规则的系统 |
| **以数据为中心风格（仓库风格）** | 数据库系统 / 超文本系统 / 黑板系统 |

### 6.3.2 架构风格对照大表（★背诵★）

| 风格 | 组件 | 连接件 | 典型场景 | 优点 | 缺点 |
|---|---|---|---|---|---|
| **批处理** | 独立应用程序 | 数据传输媒介（文件） | 传统数据处理、编译系统、银行日结 | 结构简单、易理解 | 无交互、实时性差、并发性差 |
| **管道-过滤器** | 过滤器（Filter） | 管道（Pipe，数据流） | UNIX Shell、编译器前端、信号处理 | 高内聚低耦合、支持并发、易复用 | 交互性差、无法处理错误、有状态难维护 |
| **主程序-子程序** | 主程序 + 子程序 | 调用-返回、共享数据 | 结构化程序、传统 C 程序 | 层次清晰、易于分解 | 数据修改易引发全局副作用 |
| **面向对象** | 对象（封装数据 + 方法） | 方法调用（消息） | 通用业务系统 | 封装、继承、多态；易演化 | 对象必须知道被调用者标识；副作用问题 |
| **层次型** | 层（Layer） | 相邻层协议 / 接口 | OSI / TCP-IP、操作系统、J2EE 分层 | 支持抽象和信息隐藏；每层可替换 | 效率损失、层次划分难；不是所有系统都能层次化 |
| **C/S（两层）** | 客户端 + 服务器 | 网络协议（RPC/SQL） | 传统 MIS、内部信息系统 | 交互性好、部分安全性易控 | 客户端胖、升级维护成本高、伸缩性差 |
| **C/S（三层）** | 表示层 + 功能层 + 数据层 | 网络协议 | 企业级 Web 应用 | 各层独立、易维护、伸缩性好 | 各层通信开销大、部署复杂 |
| **B/S** | 浏览器 + Web 服务器 + DB 服务器 | HTTP | 互联网应用、SaaS | 客户端零维护、跨平台 | 交互性弱于 C/S、安全性挑战大 |
| **进程通信（独立构件）** | 独立进程 | 消息传递（同步 / 异步） | 分布式系统、微服务 | 高并发、易扩展 | 消息可靠性、顺序性、性能开销 |
| **事件驱动 / 隐式调用 / 发布-订阅** | 事件源 + 事件处理器 | 事件广播（总线 / 中介） | GUI、Reactor、Kafka、微服务事件总线 | 强解耦、易扩展、易复用 | 控制流失控、事件顺序不确定、调试困难 |
| **解释器（虚拟机）** | 解释引擎 + 存储区 + 待解释代码 + 控制状态 | 解释调用 | JVM、SQL 引擎、脚本语言、专家系统 | 灵活、可动态改变行为、跨平台 | 性能差、难调试 |
| **规则系统（虚拟机）** | 规则库 + 工作内存 + 推理机 | 数据/规则匹配 | 专家系统、业务规则引擎（Drools） | 规则易增删、知识与推理分离 | 复杂规则维护难、性能问题 |
| **仓库风格（以数据为中心）** | 中央数据存储 + 独立构件 | 直接访问 | DB 应用、IDE、CAD、数据仓库 | 数据共享方便、构件独立 | 中央数据可靠性、可扩展性瓶颈 |
| **黑板风格** | 知识源 + 黑板（共享数据）+ 控制器 | 通过黑板间接交互 | 语音识别、图像识别、AI 推理、信号处理 | 支持不确定问题、可增量求解 | 控制策略复杂、调试困难、性能一般 |

### 6.3.3 C/S 三种形态对比

| 特性 | 两层 C/S | 三层 C/S | B/S |
|---|---|---|---|
| 客户端 | 胖客户端 | 瘦客户端 + 应用服务器 | 浏览器 |
| 部署 | 每客户端安装 | 服务器集中部署 | 零安装 |
| 维护 | 高 | 中 | 低 |
| 交互性 | 强 | 强 | 中/弱 |
| 典型协议 | 私有 / SQL | HTTP+RPC | HTTP/HTTPS |

> **风格选择与质量属性的对应关系**：管道-过滤器 → 可修改性；层次 → 可移植性、可维护性；发布-订阅 → 可扩展性、可修改性；C/S 三层 / B/S → 可扩展性、可维护性；黑板 → 可变性；解释器 → 可移植性、可变性。**与第 7 章质量属性联合命题极高**。

## 6.4 软件架构复用技术

### 6.4.1 复用分类

| 分类维度 | 类别 | 说明 |
|---|---|---|
| **按管理程度** | **机会复用**（Opportunistic Reuse） | 开发时才发现有可用资产；随机、无计划 |
| | **系统复用**（Systematic Reuse） | 有计划、有组织、以领域为基础的复用（DSSA / 产品线） |
| **按复用内容** | 代码 / 设计 / 分析 / 测试用例 / 架构 / 文档 / 需求 | 按抽象层次由低到高，抽象层次越高，复用收益越大 |

### 6.4.2 可复用资产的对象与形式

- **代码级**：类库、构件、框架、模式
- **设计级**：架构模式、设计模式、参考架构
- **分析级**：领域模型、业务模型、需求模板
- **过程/组织级**：过程模板、测试模板

### 6.4.3 复用的基本过程（三阶段）

| 过程 | 内容 |
|---|---|
| **构造 / 开发可复用资产** | 领域工程：领域分析 → 领域设计 → 领域实现 |
| **管理可复用资产** | 资产入库、分类、检索、版本、评价 |
| **使用可复用资产** | 应用工程：检索 → 理解 → 适应 → 组装 → 测试 |

复用能力 = 覆盖率 × 复用率 × 质量。系统复用与 6.5 DSSA、产品线（Software Product Line）密切相关。

## 6.5 特定领域软件架构 DSSA（Domain-Specific Software Architecture）

> 论文常考方向：**"论 DSSA 及其在……项目中的应用"**。

### 6.5.1 定义与领域

DSSA 是**在特定应用领域中，为一组应用提供组织结构参考的、标准化的软件架构**。核心特征：**领域相关、参考结构、标准化、可复用**。

- **垂直域**（Vertical Domain）：领域内定义具体系统族的公共架构（如"银行核心系统"）。
- **水平域**（Horizontal Domain）：跨多个领域的通用架构（如"通用 GUI 框架"）。

### 6.5.2 三大活动（★背诵★）

| 活动 | 输入 | 输出 | 关键任务 |
|---|---|---|---|
| **领域分析** | 领域中的系统族、专家知识 | 领域模型（Domain Model） | 定义领域边界、识别公共特征与可变点、术语词典 |
| **领域设计** | 领域模型 | DSSA、参考架构 | 定义架构风格、公共构件、可变点机制 |
| **领域实现** | DSSA、参考架构 | 可复用资产库、代码生成器、领域基础设施 | 实现构件、开发工具、测试用例 |

### 6.5.3 四种角色

| 角色 | 职责 |
|---|---|
| **领域专家**（Domain Expert） | 提供领域知识与经验、评审模型；不一定懂软件 |
| **领域分析师**（Domain Analyst） | 主导领域分析、建立领域模型、协调专家 |
| **领域设计人员**（Domain Designer） | 依据领域模型设计 DSSA / 参考架构 |
| **领域实现人员**（Domain Implementer） | 实现可复用构件、领域基础设施、代码生成器 |

### 6.5.4 建立 DSSA 的五阶段（★背诵★）

**① 定义领域范围 → ② 定义领域特定元素 → ③ 定义领域特定的设计和实现需求约束 → ④ 定义领域模型和体系结构 → ⑤ 产生、搜集可复用产品单元**。

每阶段迭代进行，均有明确的输入、输出与验证。

### 6.5.5 DSSA 三层次系统模型（★背诵★）

| 层次 | 名称 | 内容 |
|---|---|---|
| 顶层 | **领域开发环境**（Domain Development Environment） | 领域架构师使用，产生 DSSA、参考架构、可复用构件 |
| 中层 | **领域特定的应用开发环境**（DSA Environment） | 应用工程师使用，基于 DSSA 与构件库快速组装应用 |
| 底层 | **应用执行环境**（Application Execution Environment） | 运行时环境，OS、中间件、硬件支撑 |

自顶向下的顺序为：领域开发环境 → 领域特定应用开发环境 → 应用执行环境。

## 必背要点速记（10 条）

1. **软件架构 = 构件 + 连接件 + 约束**（IEEE 1471-2000）。
2. **4+1 视图**：逻辑（用户）、开发（程序员）、进程（集成）、物理（部署）+ 场景（用例）串联全局。
3. **ABSD 六阶段**：需求 → 设计 → 文档化 → 复审 → 实现 → 演化；驱动力 = **功能 + 质量 + 商业**。
4. **架构风格五大类**：数据流、调用返回、独立构件、虚拟机、以数据为中心（仓库）。
5. **管道-过滤器**关键词：数据流单向、构件是过滤器、连接件是管道；**利于并发、复用**。
6. **层次型**利于可移植性和可维护性；每层只依赖下一层；**性能损失**是主要缺点。
7. **事件驱动 / 隐式调用**：强解耦、易扩展；但**控制流不明确、顺序不可预测**。
8. **黑板风格**三要素：**知识源、黑板、控制器**；专用于**不确定 / AI / 信号识别**问题。
9. **DSSA 三活动 = 领域分析 / 领域设计 / 领域实现**；**四角色**中领域分析师最关键。
10. **DSSA 三层次**：领域开发环境 → 领域特定应用开发环境 → 应用执行环境；**五阶段**：范围 → 元素 → 约束 → 模型/架构 → 可复用单元。

## 与其他章节的关联

- **§6.2 ABSD 的质量场景** ↔ **§7.1 质量属性场景**（六要素完全一致；ABSD 用其驱动设计，SAAM/ATAM 用其驱动评估）。
- **§6.3 架构风格** ↔ **§7.1 质量属性**：不同风格天然利于不同质量属性（管道 → 可修改性，层次 → 可移植性，黑板 → 可变性，发布订阅 → 可扩展性）。案例分析常直接命题"给定质量目标选风格"。
- **§6.3 架构风格** ↔ **§9 架构演化**：微内核、层次、事件驱动等风格更利于演化；C/S 两层演化性差。
- **§6.4 复用 + §6.5 DSSA** ↔ **软件产品线（Software Product Line）**：产品线 = DSSA + 核心资产 + 产品开发 + 组织管理，是系统复用的最高形式。
- **§6.5 DSSA** ↔ **科目二案例 §6 嵌入式（ADD/DARTS）** 与 **科目三论文"DSSA 应用"**：论文题几乎每年都出现在 5 大方向中。
- **§6.3 C/S / B/S** ↔ **科目二 §3 层次式架构**（表示 / 中间 / 数据访问 / 数据）与 **§5 SOA / §4 云原生**。
