# 08 · 软件可靠性（教材第 9 章 / 大纲 §8）

> 综合知识常考指标、模型、容错与测试；案例和论文主要考“如何把可靠性目标落实为可验证的架构措施”。过线策略是先会算、会区分，再会用“故障—战术—指标”组织答案。

## 1. 基本概念与指标

软件可靠性是在规定时间、规定环境和规定输入条件下，软件无失效完成规定功能的能力。

| 指标 | 含义 | 考试用法 |
|---|---|---|
| `MTTF` | 平均失效前时间 | 不可修复对象或一次运行阶段的平均正常时间 |
| `MTTR` | 平均修复时间 | 故障发现、定位、修复和恢复的平均耗时 |
| `MTBF` | 平均故障间隔 | 工程资料常把它作为两次故障之间的平均正常运行时间 |
| `R(t)` | 可靠度 | 在时间 `t` 内无失效运行的概率 |
| `λ(t)` | 失效强度 | 单位时间内发生失效的强度 |
| `A` | 可用性 | 系统处于可服务状态的时间比例 |

常用可用性近似：

```text
A = 正常运行时间 / (正常运行时间 + 修复时间)
  ≈ MTTF / (MTTF + MTTR)
```

部分题库把“正常运行时间”记为 `MTBF`，此时写成 `A = MTBF / (MTBF + MTTR)`。作答时优先沿用题干定义，不在符号口径上硬争。

### 串并联系统

- 串联系统：任一构件失败即失败，`R = R1 × R2 × ... × Rn`。
- 独立并联系统：全部副本都失败才失败，`R = 1 - ∏(1 - Ri)`。
- 串联构件越多，整体可靠度通常越低；冗余并联可以提高可靠度，但会增加一致性、切换和成本复杂度。

## 2. 软件可靠性与硬件可靠性的区别

| 维度 | 硬件 | 软件 |
|---|---|---|
| 主要失效原因 | 物理磨损、老化、环境 | 需求、设计、编码和配置缺陷被特定输入触发 |
| 浴盆曲线 | 典型 | 不能机械套用 |
| 修复效果 | 更换后恢复，仍会继续老化 | 修复缺陷可能降低失效率，也可能引入新缺陷 |
| 冗余副本 | 相同硬件仍有价值 | 相同软件副本会保留共因缺陷，需考虑设计多样性 |

关键结论：软件不会因使用而“磨损”，但环境、输入和版本变化会暴露潜伏缺陷。

## 3. 可靠性工程闭环

```text
目标定义 → 指标分配 → 可靠性设计 → 分析验证 → 测试评估 → 发布监测 → 缺陷反馈
```

1. **目标定义**：明确任务时间、运行剖面、失效判据及目标值。
2. **指标分配**：把系统级目标分解到服务、构件和外部依赖。
3. **可靠性设计**：减少缺陷、容忍故障、快速恢复。
4. **分析验证**：使用 FTA、FMEA、模型或架构评审识别薄弱点。
5. **测试评估**：基于运行剖面注入故障并收集失效数据。
6. **运行监测**：持续观察错误率、MTTR、切换成功率和数据损失量。

## 4. 可靠性设计方法

### 4.1 避免故障

- 简化设计，降低不必要的状态和分支。
- 复用成熟构件，减少重复实现。
- 契约校验、防御式编程、静态检查和严格评审。
- 配置校验、灰度发布、版本兼容和自动回滚。

### 4.2 检测故障

- 心跳、Ping/Echo、看门狗和超时检测。
- 断言、校验和、序列号、审计日志。
- 指标、日志、链路追踪和业务对账。
- FTA（故障树）从顶层故障向下追因；FMEA 从部件失效模式向上分析影响。

### 4.3 容忍与恢复故障

| 技术 | 核心思想 | 典型风险 |
|---|---|---|
| 主备 / 多副本 | 冗余资源接管故障节点 | 脑裂、复制延迟、切换失败 |
| 重试 / 指令复执 | 瞬时故障后再次执行 | 重复副作用、重试风暴 |
| 回滚 / 检查点 | 恢复到已知正确状态 | 状态不完整、恢复时间长 |
| 降级 / 隔离 | 保核心、舍非核心，限制故障传播 | 功能损失、降级不透明 |
| N 版本程序设计 | 多个独立实现投票 | 共因需求缺陷、成本高 |
| 恢复块 | 主算法失败后执行备选算法 | 验收测试不充分 |
| 数据校验 / 对账 | 发现并修复业务不一致 | 修复滞后、人工成本 |

### N 版本与恢复块

- **N 版本程序设计**：并行执行多个独立版本，以多数表决结果作为输出；强调设计多样性。
- **恢复块**：先执行主版本，通过验收测试才提交；失败则回滚并尝试备选版本。

记忆钩子：N 版本是“并行投票”，恢复块是“串行试错”。

## 5. 可靠性模型

模型用于根据已观察到的失效数据估计当前可靠性并预测剩余缺陷。选择模型前必须确认：

- 失效是否独立；
- 修复是否立即且不会引入新缺陷；
- 测试输入是否符合真实运行剖面；
- 失效强度是否随修复逐步下降。

考试通常不要求推导具体模型公式，更常问模型假设、输入数据和选择步骤。不能把“测试通过率”直接等同于可靠度。

## 6. 可靠性测试与评估

### 测试类型

- **可靠性增长测试**：持续测试、修复并观察失效强度是否下降。
- **可靠性验证测试**：判断是否达到既定指标。
- **可靠性摸底测试**：资源有限时估计当前水平和主要薄弱点。
- **故障注入 / 混沌实验**：主动制造节点、网络、存储或依赖故障，验证检测、隔离与恢复机制。

### 评估步骤

1. 建立真实运行剖面；
2. 定义失效及严重度；
3. 收集失效时间、恢复时间和环境数据；
4. 选择符合假设的模型；
5. 估计与预测；
6. 给出置信范围和适用边界。

## 7. 案例答题模板

按“目标—威胁—战术—验证”四段写：

```text
目标：核心交易年可用性达到 99.99%，RPO=0，RTO<30s。
威胁：单点故障、网络分区、消息重复、数据库复制延迟。
战术：同城双活、多副本、超时熔断、幂等重试、自动切换、事务日志和对账。
验证：故障注入后统计切换时长、数据损失量、错误率、MTTR，并定期演练。
```

只写“采用集群、提高可靠性”得分有限；必须写清具体故障、机制和量化指标。

## 8. 论文落地骨架

1. 项目背景及可靠性目标；
2. 运行剖面与故障模型；
3. 可靠性分配与架构决策；
4. 检错、容错、恢复及数据一致性措施；
5. 测试、演练和量化结果；
6. 权衡：成本、性能、复杂度与共因故障。

可量化指标：可用性、MTBF/MTTF、MTTR、RTO、RPO、故障发现时间、切换成功率、消息丢失率、恢复演练通过率。

## 9. 高频易错点

- 可靠性不等于可用性：可用性还受修复速度影响。
- 相同软件多部署几份不能消除同一代码缺陷。
- 重试必须配合幂等、退避和上限。
- 备份不等于容灾；未验证恢复流程的备份不能证明可恢复。
- 只写技术名词而没有失效场景和度量，案例与论文都难得高分。
