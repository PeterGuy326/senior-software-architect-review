# 论文主题 05 · 微服务与云原生架构

## 历年出题角度

- 论微服务架构设计及其应用
- 论无服务器架构（Serverless）
- 论云原生架构在 XX 中的应用
- 论基于容器的应用架构

## 一、核心理论

### 云原生四要素

1. **容器化**（Docker）
2. **微服务**
3. **DevOps**
4. **持续交付**

### 十二要素应用（12-Factor）

代码库、依赖、配置、后端服务、构建/发布/运行、进程、端口绑定、并发、易处理、开发/生产一致、日志、管理进程

### 微服务拆分原则（DDD）

- **单一职责**
- **限界上下文**（Bounded Context）
- **业务能力**驱动
- **团队自治**（Two-Pizza Team）
- **数据库私有**（Database Per Service）

### 核心组件

| 组件 | 代表 | 作用 |
|---|---|---|
| 注册中心 | Nacos / Eureka | 服务发现 |
| API 网关 | Spring Cloud Gateway / Kong | 统一入口 |
| 配置中心 | Apollo / Nacos | 配置管理 |
| 熔断限流 | Sentinel / Hystrix | 治理 |
| 链路追踪 | SkyWalking / Jaeger | 可观测 |
| 服务网格 | Istio / Envoy | 流量治理 |
| 编排 | **Kubernetes** | 容器调度 |

## 二、万能提纲（单体改造微服务）

```
1. 背景（400 字）
   - 原单体系统瓶颈：耦合高、发布慢、性能差
   - 改造目标：QPS 从 5k → 50k，部署频率日级 → 小时级
2. 理论（350 字）
   - 云原生、12-Factor、微服务拆分原则
3. 实践论述（1600 字）⭐⭐⭐⭐⭐
   (1) 服务拆分：DDD 限界上下文（订单/支付/库存/用户/商品）
   (2) 数据库拆分：Database Per Service + 分库分表
   (3) 通信：同步 REST/gRPC + 异步 MQ（RocketMQ）
   (4) 基础设施：K8s + Istio + Prometheus
   (5) 分布式事务：TCC（核心交易）+ 本地消息表（最终一致）
   (6) 服务治理：熔断降级限流（Sentinel）+ 链路追踪（SkyWalking）
4. 成效（250 字）
   - QPS 10 倍、发布频率 24 倍、可用性 99.99%
```

## 三、关键数据

- QPS：峰值 **10 万**
- 部署频率：**每天多次**（从月级提升）
- 服务数：**50–100 个**
- 容器数：**500–1000**（K8s 集群 30 节点）
- MTTR：**从小时级降到分钟级**

## 四、万能句式

- "通过 **DDD 限界上下文** 将单体拆分为 10 个业务微服务 + 5 个基础服务"
- "核心交易采用 **TCC** 保证强一致，辅助场景用 **本地消息表** 实现最终一致"
- "全部容器化，通过 **Kubernetes** 编排，**Istio** 做服务网格治理"
- "**Serverless（FaaS）** 用于非核心异步场景（如图片处理），按需付费，成本降低 **40%**"

## 五、避坑点

| ❌ | ✅ |
|---|---|
| "全部微服务化" | **共同数据** / **紧耦合**场景留在单体 |
| 不谈治理 | 熔断限流链路追踪必写 |
| 忽视分布式事务 | 选**合适方案**：TCC / Saga / MQ |
| 数据库不拆 | Database Per Service 是红线 |
| 无监控 | 可观测三支柱：Metrics / Logging / Tracing |

### 模拟论文题 1 · 论微服务架构与云原生技术在企业系统中的应用

**【完整题目】**（约 410 字）

近年来，随着 Kubernetes、Service Mesh、容器化等技术的成熟，"云原生"已从概念走向规模化落地。CNCF 提出的云原生四要素——容器化、微服务、DevOps、持续交付——为企业构建弹性、可扩展、可观测的现代应用提供了系统化指导。Heroku 的 12-Factor 应用方法论、DDD 限界上下文驱动的服务拆分、Database Per Service 的数据自治原则，构成了微服务设计的工程基线。同时，TCC、Saga、本地消息表等分布式事务方案，Sentinel/Hystrix 的熔断限流，SkyWalking/Jaeger 的链路追踪，Istio/Envoy 的服务网格，共同支撑微服务系统的高可用治理。

#### 摘要框架（300 字模板）

"我于 {2023} 年主导了 {电商订单 / 在线教育 / SaaS} 系统的微服务化改造，担任 {架构师}。原单体系统 {Java 80 万行 / 月发布 1 次 / QPS 5000}，改造后 {15 个微服务 / 日发布 30 次 / QPS 6 万}。本文以该项目为背景，论述微服务+云原生的实践：基于 DDD 拆分服务、Database Per Service、TCC + 本地消息表、K8s + Istio + Prometheus + SkyWalking 治理体系、金丝雀发布。最终 QPS 提升 12 倍、可用性 99.99%、MTTR 从 2 小时降至 15 分钟。"

#### 一、项目背景（350 字提纲）

- **业务背景**：单体老系统瓶颈：耦合高、发布慢、无法弹性扩缩
- **团队规模**：30 人 + SRE 5 人
- **改造目标**：QPS 5k→50k、发布日级→小时级、MTTR 小时→分钟
- **关键质量属性**：性能、可用性、可修改性、可观测性

#### 二、核心理论（400 字提纲）

- 云原生四要素：容器化（Docker）、微服务、DevOps、持续交付
- 12-Factor：代码库/依赖/配置/后端服务/构建发布运行/进程/端口绑定/并发/易处理/开发生产一致/日志/管理进程
- 微服务拆分原则：单一职责 / 限界上下文 / 业务能力 / Two-Pizza Team / Database Per Service
- 核心组件：注册中心 Nacos、网关 Spring Cloud Gateway、配置中心 Apollo、熔断 Sentinel、追踪 SkyWalking、网格 Istio、编排 K8s
- 分布式事务：TCC、Saga、本地消息表、可靠消息

#### 三、实践论述（1500 字提纲，分 4 节）

##### 3.1 服务拆分（DDD）
- 限界上下文识别：订单/支付/库存/用户/商品/促销
- 拆分策略：先共性后差异，先冷数据后热数据
- 留单体：促销引擎（事务边界强）保留单体
- 量化：单体 80 万行 → 15 服务平均 5000 行

##### 3.2 数据库拆分 + 通信
- Database Per Service 红线
- 商品库分 16 库 64 表（tenant_id 哈希）
- 同步 gRPC + REST，异步 RocketMQ
- 量化：跨库查询 → ES 聚合，延迟 50ms 内

##### 3.3 基础设施 + 治理
- K8s 跨 3 可用区，30 节点集群
- Istio 流量治理（灰度/熔断/超时）
- Sentinel 限流（按调用方+接口）
- SkyWalking + ELK + Prometheus 三支柱
- TCC 三阶段（核心交易）+ 本地消息表（最终一致）

##### 3.4 风险与应对（必有）
- 风险 1：服务过细导致链路过长 → 合并为粗粒度领域服务
- 风险 2：分布式事务失败 → 对账兜底 + 补偿日志
- 风险 3：治理成本高 → 引入 Istio 服务网格 + GitOps

#### 四、总结与展望（250 字提纲）

- 项目结果：QPS 6 万、P99 178ms、可用性 99.995%、发布日 30 次、MTTR 15 分钟
- 经验教训：①不要"微服务一把梭"，留合理单体 ②可观测性建设要前置 ③Database Per Service 是红线
- 未来演进：FaaS 非核心场景、Service Mesh 全面下沉、Argo CD GitOps
