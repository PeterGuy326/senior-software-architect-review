# 论文主题 07 · 面向服务架构（SOA）

## 历年出题角度

- 论面向服务的架构设计及其应用
- 论 SOA 与微服务的演进
- 论企业服务总线（ESB）的应用

## 一、核心理论

### SOA 核心原则

1. **服务复用**
2. **松耦合**
3. **契约标准化**
4. **服务自治**
5. **无状态**
6. **可组合**
7. **可发现**

### SOA 与微服务对比

| 维度 | SOA | 微服务 |
|---|---|---|
| 粒度 | 粗（企业级） | 细（业务功能） |
| 通信 | **ESB**（SOAP/WS-*) | 轻量（REST/gRPC） |
| 数据 | 共享数据库多见 | Database Per Service |
| 治理 | 集中 | 去中心化 |
| 部署 | 单体部署多 | 独立部署 |

### SOA 参考模型

- **服务消费者** ⇄ **服务注册中心**（UDDI）⇄ **服务提供者**
- 通过 **WSDL** 描述，**SOAP** 传输，**ESB** 编排

### Web Service 三件套

- **SOAP**：协议（基于 XML）
- **WSDL**：服务描述
- **UDDI**：服务注册/发现

- "通过 **ESB** 屏蔽异构系统差异，以 **WSDL** 契约规范服务接口"

### 模拟论文题 1 · 论 SOA 架构与企业服务总线在大型企业系统中的应用

**【完整题目】**（约 410 字）

大型企业经过多年信息化建设，往往积累了 ERP、CRM、HR、财务、OA 等数十套异构业务系统，形成"烟囱林立"的架构格局，跨系统集成成本高、数据孤岛严重。SOA（Service-Oriented Architecture，面向服务架构）通过将企业能力抽象为标准化服务，并以企业服务总线（ESB，Enterprise Service Bus）为枢纽进行编排与治理，是解决企业级集成难题的经典方案。SOA 强调七大原则——服务复用、松耦合、契约标准化、服务自治、无状态、可组合、可发现，配合 SOAP/WSDL/UDDI 三件套和 BPEL 流程编排，已在银行、电信、政务等行业得到大规模验证。近年随着微服务兴起，SOA 也在向轻量化、去中心化方向演进。

#### 一、项目背景（350 字提纲）

- **业务背景**：大型企业 25 套异构系统、点对点集成成本高
- **团队规模**：22 人（架构 3 + 集成开发 12 + ESB 运维 4 + 业务分析 3）
- **关键质量属性**：可集成性、可复用性、可维护性、安全性
- **业务约束**：合规审计、跨部门协作、4 年建设周期

#### 二、核心理论（400 字提纲）

- SOA 七大原则：复用 / 松耦合 / 契约标准化 / 自治 / 无状态 / 可组合 / 可发现
- SOA 参考模型：消费者 → UDDI（注册中心） → 提供者，通过 WSDL 描述、SOAP 传输、ESB 编排
- Web Service 三件套：SOAP（XML 协议）/ WSDL（描述）/ UDDI（注册）
- BPEL：业务流程执行语言，跨服务编排
- WS-Security：消息级安全、签名、加密
- SOA vs 微服务：粒度（粗 vs 细）、通信（ESB vs 轻量）、治理（集中 vs 分散）

#### 三、实践论述（1500 字提纲，分 4 节）

##### 3.1 服务识别与设计
- 自顶向下业务流程拆解：贷款审批、客户开户、产品销售
- 三层服务划分：业务服务 / 实体服务 / 工具服务
- 契约先行：先 WSDL 后实现
- 量化：识别 80 个企业级服务、复用率 60%

##### 3.2 ESB 集成
- WSO2 ESB 集群（4 节点高可用）
- 协议转换：SOAP/REST/JMS/FTP 互通
- 消息路由 + 内容转换 + 协议适配
- 量化：日处理 500 万消息、平均延迟 80ms

##### 3.3 服务治理 + 安全
- UDDI v3 服务注册 + 服务目录
- BPEL 编排跨系统流程（如开户：核心系统+账务+反洗钱+短信）
- WS-Security 签名 + 加密 + SAML SSO
- SLA 监控 + 治理仪表盘
- 量化：监控 200+ 服务、SLA 达标率 99.5%

##### 3.4 风险与应对（必有）
- 风险 1：ESB 单点 → 集群 + 异地灾备
- 风险 2：SOAP 性能差 → 高频内部接口降级到 REST/gRPC（向微服务演进）
- 风险 3：WSDL 版本管理混乱 → 语义化版本 + 契约测试

#### 四、总结与展望（250 字提纲）

- 项目结果：集成接口降 80%、复用率 60%、新业务上线 6m→1m、零集成故障
- 经验教训：①SOA 是组织+架构双重改造 ②契约先行是根基 ③ESB 不能成为新单点
- 未来演进：SOA → 微服务（去 ESB 化）、API Gateway 替代 ESB、Service Mesh 治理

### 模拟论文题 2 · 论 SOA 向微服务架构的演进路径

**【完整题目】**（约 410 字）

许多企业在十多年前完成了 SOA 平台建设，以 ESB 为核心枢纽实现了跨系统集成。然而，随着业务敏捷性要求提升、容器化与云原生技术成熟，传统 SOA 暴露出 ESB 单点瓶颈、集中治理效率低、SOAP 协议笨重等问题，企业开始向微服务架构演进。SOA 与微服务在"服务化"理念上一脉相承，但在服务粒度（粗 vs 细）、通信协议（SOAP vs REST/gRPC）、治理模式（集中式 ESB vs 去中心化 Sidecar）、数据策略（共享数据库 vs Database Per Service）、部署方式（应用服务器 vs 容器）等方面存在本质差异。架构师需要规划渐进式演进路径，避免"大爆炸"式重写风险，并保留 SOA 的契约治理与服务复用优势。

请围绕"**论 SOA 与微服务的演进**"论述以下三个问题：

1. **概要叙述**你参与设计与开发的软件项目，以及你担任的主要工作（约 300 字应答）。
2. **简要说明** SOA 与微服务的核心差异，以及向微服务演进的常见模式（约 400 字应答）。
3. **详细论述**你在项目中如何制定 SOA 到微服务的演进路线、关键技术决策与最终成效（约 1500-1800 字应答）。

**【提纲式参考答案】**（约 1400 字提纲）

#### 摘要框架（300 字模板）

"我于 {2022} 年主导了 {银行 / 运营商 / 大型集团} 既有 SOA 平台向微服务演进的项目，担任 {演进架构师}。原 SOA 平台 {ESB 8 节点 / 80 个 WSDL 服务 / 日 500 万消息}，但 ESB 高负载下延迟 200ms+、新业务接入慢。通过绞杀者模式 + API Gateway 替代 ESB + DDD 重新拆分细粒度服务 + 容器化（K8s）+ Istio 服务网格，3 年内完成核心域演进。最终延迟降至 30ms、新业务接入 1m→3d、ESB 流量减少 90%。"

#### 一、项目背景（350 字提纲）

- **业务背景**：5 年前 SOA 平台已运行良好，但敏捷性瓶颈凸显
- **团队规模**：30 人（演进委员会 5 人 + 业务域 25 人）
- **关键质量属性**：性能、可修改性、可独立部署性、可观测性
- **业务约束**：演进期间老业务零中断、ROI 必须可量化、3 年规划

#### 二、核心理论（400 字提纲）

- SOA vs 微服务对比表（粒度/通信/治理/数据/部署）
- 演进模式：
  - **绞杀者模式**（Strangler Fig）：API Gateway 路由新老
  - **防腐层 ACL**：新服务屏蔽老系统数据模型
  - **分支抽象**：代码级渐进重构
  - **影子流量**：新服务接收复制流量先验证
- 康威定律：组织决定架构，先调团队
- DDD 限界上下文：重新拆分细粒度服务
- 演进路径：单体 → SOA → 微服务 → Service Mesh → Serverless

#### 三、实践论述（1500 字提纲，分 4 节）

##### 3.1 演进路线图（3 阶段）
- 阶段 1（6 个月）：API Gateway 上线，承接新接入
- 阶段 2（18 个月）：DDD 重新拆分，绞杀核心域（订单/账务/客户）
- 阶段 3（12 个月）：Istio 服务网格 + GitOps + 退役 ESB
- 量化：每季度评审 ROI

##### 3.2 关键技术决策
- API Gateway（Kong/Spring Cloud Gateway）替代 ESB 主路由
- DDD 重拆：80 个粗粒度服务 → 200 个细粒度微服务
- 协议升级：SOAP → REST/gRPC，性能提升 5x
- 数据库拆分：共享 → Database Per Service
- 防腐层 ACL：新服务通过 ACL 调用老 ESB

##### 3.3 治理与运维
- 服务网格 Istio：流量治理、熔断、灰度
- 可观测三支柱：Prometheus + ELK + SkyWalking
- DevOps：GitLab + Argo CD + K8s
- 契约管理：OpenAPI + Pact 契约测试

##### 3.4 风险与应对（必有）
- 风险 1：双轨期数据一致性 → CDC + 双写 + 对账兜底
- 风险 2：组织阻力 → 先调团队（康威定律）+ 月度演进汇报
- 风险 3：演进 ROI 难量化 → DORA 四指标 + 业务上线时长

#### 四、总结与展望（250 字提纲）

- 项目结果：延迟 200ms→30ms、新业务 1m→3d、部署频率提升 30 倍、ESB 流量降 90%
- 经验教训：①演进必须渐进式，不要大爆炸 ②保留 SOA 契约治理的精华 ③组织调整与架构调整必须同步
- 未来演进：Serverless 接入非核心、AI 治理 + 自动化 SRE
