# 论文主题 02 · 软件架构评估（ATAM）

## 历年出题角度

- 论软件系统架构评估及其应用（**高频**）
- 论质量属性驱动的架构评估

## 一、核心理论（必写）

### 三大评估方法对比

| 方法 | 特点 | 适用 |
|---|---|---|
| **SAAM** | 基于场景，最早 | 早期、可修改性为主 |
| **ATAM** | **关注权衡，最主流** | 设计阶段 |
| **CBAM** | ATAM + 经济学成本分析 | 投资决策 |

### ATAM 四类关键点（**论文必写**）

- **敏感点**：为实现某质量属性所关键的架构决策
- **权衡点**：同时影响多个质量属性（有正有负）
- **风险点**：可能导致风险的决策
- **非风险点**：已确认安全的决策

### ATAM 9 步流程

1. 介绍 ATAM → 2. 业务驱动 → 3. 被评估架构 → 4. 识别架构方法 → 5. 质量属性**效用树**
6. 分析架构方法 → 7. 场景集 + 优先级 → 8. 分析架构方法（迭代） → 9. 呈现结果

### 质量属性效用树

```
Utility（根）
├── 性能
│   ├── 数据延迟 (H,M)
│   └── 事务吞吐 (M,H)
├── 可用性
│   └── 硬件故障 (H,L)
└── 可修改性
    └── 新增功能 (L,M)
```

优先级：**(业务价值, 技术难度)**

## 三、实战示例（答题素材）

### 典型敏感点举例

- 主备切换 < 30s → 影响**可用性**
- 缓存命中率 > 95% → 影响**性能**

### 典型权衡点举例

- 全链路 HTTPS 加密 → **+安全 / -性能**
- 数据异步写入 → **+性能 / -一致性**

### 典型风险点举例

- 单点服务无熔断 → 级联故障
- MQ 未持久化 → 宕机丢消息

### 典型非风险点

- 采用业界成熟的 Kafka
- 数据库主从复制

### 模拟论文题 1 · 论质量属性驱动的软件架构评估方法及其应用

**【完整题目】**（约 420 字）

软件架构是系统满足非功能需求的根基，而非功能需求难以在编码阶段验证，因此在架构设计阶段进行评估，是降低后期返工成本、保障系统质量的关键工程实践。Carnegie Mellon 大学 SEI 提出的 ATAM（Architecture Tradeoff Analysis Method，架构权衡分析法）是目前业界最主流的架构评估方法，强调以质量属性为驱动、以场景为载体，识别架构中的敏感点、权衡点、风险点和非风险点，并通过效用树对场景进行优先级排序，最终输出可执行的改进建议。在金融、电商、电信等高质量要求的系统中，ATAM 已成为架构复审的标准动作。

请围绕"**论质量属性驱动的软件架构评估方法及其应用**"论述以下三个问题：

1. **概要叙述**你参与设计与评估的软件项目，以及你担任的主要工作（约 300 字应答）。
2. **简要说明**主流软件架构评估方法（SAAM/ATAM/CBAM）的特点与差异，并阐述 ATAM 的 9 个核心步骤（约 400 字应答）。
3. **详细论述**你在项目中如何应用 ATAM 方法构建效用树、识别四类关键点并落地改进，最终评估效果如何（约 1500-1800 字应答）。

**【提纲式参考答案】**（约 1400 字提纲）

#### 摘要框架（300 字模板）

"我于 {2023} 年参与了 {电商订单中台 / 银行核心 / 政务大数据} 项目的架构设计与评估工作，担任 {架构师}。系统服务 {800 万日订单 / 5 万 QPS / 99.99% 可用性}。在架构方案定稿前，我组织团队采用 ATAM 方法进行系统性评估，构建质量属性效用树，识别出 {4 个敏感点、2 个权衡点、3 个风险点、5 个非风险点}，并针对风险点落实 {Sentinel 熔断、TCC 补偿、压测演练} 等改进战术。第二次复审风险点全部转为非风险点。本文将以该项目为背景，论述 ATAM 评估方法的核心理论与实践应用。"

#### 一、项目背景（350 字提纲）

- **业务背景**：3 条业务线订单系统融合，需评估关键架构决策的质量属性达成度
- **团队规模**：架构组 2 人 + 评估委员会 8 人（含外部专家）
- **关键质量属性**（候选 5 选 3-4）：性能、可用性、可修改性、安全性、一致性
- **评估动因**：架构方案涉及微服务+事件驱动+TCC 等多重决策，需在编码前复审

#### 二、核心理论（400 字提纲）

- 三种评估方法对比：
  - SAAM（场景驱动，最早，偏可修改性）
  - ATAM（权衡分析，主流，覆盖多质量属性）
  - CBAM（ATAM + 经济成本，投资决策）
- ATAM 9 步：介绍 ATAM → 业务驱动 → 被评估架构 → 识别架构方法 → 效用树 → 分析架构方法 → 场景集 + 优先级 → 迭代分析 → 呈现结果
- 四类点信号词：敏感点（"为了…")、权衡点（"既…又…"）、风险点（"可能…"）、非风险点（"已验证…"）
- 效用树优先级标注：(业务价值 H/M/L, 技术难度 H/M/L)
- 质量属性场景 6 元组：源、刺激、制品、环境、响应、响应度量

#### 三、实践论述（1500 字提纲，分 4 节）

##### 3.1 业务驱动识别 + 利益相关者
- 业务方提出 5 大质量目标
- 利益相关者：业务、研发、运维、安全、SRE
- 收敛为效用树根节点

##### 3.2 效用树构建 + 场景生成
- 二级节点：性能 / 可用性 / 可修改性 / 安全性
- 关键场景：下单 P99 < 200ms (H,H)、可用性 99.99% (H,H)、新业务接入 < 1m (M,M)、等保三级 (H,M)
- 6 元组细化：源=用户峰值 200 万 / 刺激=下单 / 制品=订单服务 / 环境=大促 / 响应=正常受理 / 度量=P99 < 200ms

##### 3.3 四类点识别 + 改进战术
- 敏感点：Cache Aside、RocketMQ 持久化、TCC 补偿、API 限流
- 权衡点：HTTPS（安全↑性能↓）、异步扣库存（性能↑一致性↓）
- 风险点：促销单点无熔断、对账未压测、DR 频次不足
- 非风险点：Nacos 集群、MySQL 主从、Redis 哨兵、K8s 滚动、SkyWalking
- 改进战术：Sentinel 熔断 + 拆只读副本、补做全链路压测、DR 演练频次提升

##### 3.4 风险与应对（必有）
- 评估委员会意见分歧 → 业务+技术双维度量化
- 改进成本评估 → 引入 CBAM 经济分析
- 二次复审验证 → 风险点 100% 转非风险点

#### 四、总结与展望（250 字提纲）

- 项目结果：上线后大促零 P0 故障，可用性 99.995%
- 经验教训：①ATAM 必须早做，编码后做就是事后诸葛亮 ②场景必须可量化（6 元组的"度量"是核心） ③改进战术要量化代价
- 未来演进：将 ATAM 评估流程沉淀为团队 SOP，引入 CBAM 做成本权衡
