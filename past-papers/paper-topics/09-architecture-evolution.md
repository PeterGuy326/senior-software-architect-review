# 论文主题 09 · 软件架构演化与维护

## 历年出题角度

- 论软件系统架构的演化（**高频**）
- 论软件架构的维护与演化
- 论遗留系统的改造

## 一、核心理论

### 架构演化的驱动力

- **业务变化**（新需求、规模膨胀）
- **技术变化**（新技术、技术债）
- **非功能需求**（性能、可用性、安全）
- **组织变化**（团队结构 → 康威定律）

### 架构演化类型

| 类型 | 含义 | 代价 |
|---|---|---|
| **可修改性演化** | 小范围调整 | 低 |
| **可扩展性演化** | 新增功能 | 中 |
| **重构性演化** | 不改行为改结构 | 中 |
| **重写性演化** | 完全重写 | 高（慎用） |

### 演化模式

1. **静态演化**：停机升级，简单但有停机时间
2. **动态演化**：不停机热更新（OSGi、蓝绿、灰度）

### 康威定律

> "**组织架构决定软件架构**"

系统设计反映组织沟通结构 → 先调组织再调系统。

### 常见演化手段

- **绞杀者模式**（Strangler Fig）：逐步替换老系统
- **分支抽象**：代码级渐进重构
- **防腐层**（ACL）：新老边界隔离

## 三、关键数据

- 演化周期：**6–24 个月**
- 代码迁移：**100w 行**
- 灰度分级：**1% / 10% / 50% / 100%**
- 零停机，**RPO=0**

## 四、万能句式

- "基于**绞杀者模式**渐进式替换，避免"大爆炸"式重写风险"
- "通过**防腐层（ACL）**隔离新老系统数据模型，保持新服务的**领域纯净**"
- "遵循**康威定律**，**先调组织**（小团队负责单服务）再调架构"

## 五、避坑点

| ❌ | ✅ |
|---|---|
| 大爆炸式重写 | **渐进式**绞杀者模式 |
| 只改技术不调组织 | 康威定律：**组织决定架构** |
| 无量化收益 | 迭代速度、故障率必须前后对比 |
| 不谈回滚 | 灰度 + 可回滚 是底线 |

### 模拟论文题 1 · 论遗留系统的架构演化与改造

**【完整题目】**（约 410 字）

许多企业都面临"遗留系统"的困境——十年前甚至更久构建的核心业务系统，代码几十万行甚至上百万行，技术栈陈旧、文档缺失、修改风险高，但仍承载关键业务，无法停机重写。架构演化（Architecture Evolution）正是应对这一挑战的系统化方法论，其核心理念是**渐进式而非革命式**：通过绞杀者模式（Strangler Fig）、防腐层（ACL）、分支抽象、影子流量等技术手段，逐步替换老系统功能，最终实现整体演化。同时遵循康威定律——"组织架构决定软件架构"，演化必须先调整团队结构再调整系统。常见演化类型包括可修改性演化、可扩展性演化、重构性演化、重写性演化（慎用），代价依次递增，需要架构师按 ROI 做合理选型。

#### 摘要框架（300 字模板）

#### 一、项目背景（350 字提纲）

- **业务背景**：10 年银行核心系统，COBOL+Java 混合栈，每次改动风险大
- **团队规模**：演化委员会 5 人 + 跨域研发 50 人
- **关键质量属性**：可修改性、可扩展性、可用性、零停机
- **业务约束**：监管合规、数据零丢失、24×7 在线、3 年规划

#### 二、核心理论（400 字提纲）

- 演化驱动力：业务变化 / 技术变化 / 非功能需求 / 组织变化
- 演化类型：可修改性（低代价）/ 可扩展性（中）/ 重构性（中）/ 重写性（高代价慎用）
- 演化模式：
  - **静态演化**：停机升级，简单
  - **动态演化**：不停机热更新（OSGi、蓝绿、灰度）
- 康威定律：组织架构决定软件架构
- 演化手段：绞杀者模式、分支抽象、防腐层 ACL、影子流量、双写

#### 三、实践论述（1500 字提纲，分 4 节）

##### 3.1 架构评估 + 演化路线图
- 痛点诊断：耦合度 0.85、循环依赖 12 处、发布失败率 18%
- 三阶段路线：
  - 短期 3 个月：稳定 + 监控完善 + 自动化测试

- 量化：每季度评审 + KPI 对齐

##### 3.2 绞杀者模式落地
- API Gateway（Spring Cloud Gateway）作为流量切换枢纽
- 路由规则：新功能走新服务、老功能继续老系统
- 灰度分级：1% → 10% → 50% → 100%
- 一键回滚：3 分钟回到老路径
- 量化：每周切流 1 个功能、累计 80 个功能切换

##### 3.3 数据迁移 + 防腐层
- 双写：新老系统并行写入，老系统为权威源
- CDC（Canal）订阅 binlog 实时同步
- 校对：每日全量比对 + 差异告警
- 防腐层 ACL：新服务用领域模型，ACL 翻译老系统数据
- 量化：60 万行代码迁移、零数据丢失

##### 3.4 风险与应对（必有）
- 风险 1：双写不一致 → 异步对账 + 修复脚本 + 人工介入
- 风险 2：康威阻力 → 先调团队（组建领域团队）再调架构
- 风险 3：演化 ROI 不可见 → DORA 指标 + 月度演化汇报

#### 四、总结与展望（250 字提纲）

- 项目结果：迭代周期 2w→2d、发布失败率 18%→2%、零停机演化、迁移 60 万行
- 经验教训：①渐进式胜过大爆炸 ②先调组织再调架构 ③可回滚是底线
- 未来演进：Service Mesh + GitOps + AIOps 异常预测

### 模拟论文题 2 · 论架构演化中的康威定律与组织重构

**【完整题目】**（约 410 字）

康威定律（Conway's Law）由 Melvin Conway 于 1968 年提出："设计系统的组织，其设计的系统结构必将复制该组织的沟通结构"。这一定律深刻揭示了**组织架构与软件架构的同构关系**——单体组织产出单体系统，分布式组织产出分布式系统。在大型企业架构演化中，纯技术改造往往收效甚微，因为旧组织结构会持续把新架构"拉回"老形态。逆向康威（Inverse Conway Maneuver）主张通过主动设计组织结构来塑造期望的架构形态：要做微服务，就先按业务域组建小团队（Two-Pizza Team）；要做中台，就先成立独立中台部门；要做平台化，就先剥离平台研发。架构师在主导演化时，必须将组织设计与架构设计统一规划。

请围绕"**论软件架构的演化与组织设计**"论述以下三个问题：

1. **概要叙述**你参与设计与开发的软件项目，以及你担任的主要工作（约 300 字应答）。
2. **简要说明**康威定律、逆向康威定律以及组织与架构的关系（约 400 字应答）。
3. **详细论述**你在项目中如何同步设计组织结构与架构形态，最终业务效果（约 1500-1800 字应答）。

**【提纲式参考答案】**（约 1400 字提纲）

#### 摘要框架（300 字模板）

"我于 {2023} 年牵头 {电商集团 / 互联网公司 / 大型 SaaS} 的架构 + 组织双重演化项目，担任 {首席架构师 + 组织设计顾问}。原 {300 人单体研发 + 月发布 1 次} 改造为 {15 个域团队 × 平均 18 人 + 日发布 30 次}。本文论述逆向康威定律的应用：先按 DDD 限界上下文重组团队（订单/支付/库存/会员等），再实施微服务拆分；同时建立平台团队 + 业务团队 + SRE 三支柱，团队 API 化协作。最终迭代周期 2w→2d、跨团队依赖 -70%、研发效率 +50%。"

#### 一、项目背景（350 字提纲）

- **业务背景**：300 人研发，按职能划分（前端/后端/DBA），跨职能协作成本高
- **团队规模**：演化前 5 大职能部门 → 演化后 15 个业务域团队 + 3 个平台团队 + 1 个 SRE
- **关键质量属性**：组织效率、自治性、变更速度、跨团队协作
- **业务约束**：人员稳定 / 跨部门利益 / 老板认同

#### 二、核心理论（400 字提纲）

- 康威定律原文：组织沟通结构 = 系统设计结构
- 逆向康威定律：先设计期望的组织，再让架构自然形成
- 团队拓扑（Team Topologies 四类）：
  - Stream-aligned（业务流团队）
  - Platform（平台团队）
  - Enabling（赋能团队）
  - Complicated subsystem（复杂子系统团队）
- Two-Pizza Team：6-8 人，团队规模上限
- 团队 API：明确团队间协作契约
- 组织演化模式：职能制 → 矩阵制 → 业务线制 → 平台 + BU

#### 三、实践论述（1500 字提纲，分 4 节）

##### 3.1 现状诊断 + 目标组织设计
- 旧组织：5 大职能（前端/后端/DBA/测试/运维）+ PM 协调
- 痛点：跨职能协作 5 层沟通、决策周期 2 周
- 目标：业务域团队 + 平台 + SRE 三支柱
- 量化：跨团队依赖度 0.7 → 0.2

##### 3.2 团队拓扑落地
- Stream-aligned：15 个业务域团队（订单/支付/库存等），每队 18 人
- Platform：3 个平台团队（研发效能 / 数据中台 / 安全中台）
- Enabling：架构组 5 人，巡回赋能
- Complicated：风控算法团队 8 人
- 团队 API：每团队提供 OpenAPI 文档 + SLA + Slack 频道

##### 3.3 架构同步演化
- 先调团队（3 个月）：人员盘点 + 团队组建 + Tech Lead 任命
- 再调架构（18 个月）：按团队边界拆服务、Database Per Team
- DDD 限界上下文 = 团队边界 = 服务边界
- 量化：服务数 = 团队数 × 1.5（每团队 1-2 个服务）

##### 3.4 风险与应对（必有）
- 风险 1：人员抵触 → 沟通 + 培训 + Tech Lead 选拔机制
- 风险 2：平台团队边缘化 → 平台 KPI 与业务采纳率挂钩
- 风险 3：团队孤岛 → Enabling 团队巡回 + 架构师轮岗

#### 四、总结与展望（250 字提纲）

- 项目结果：迭代 2w→2d、跨团队依赖 -70%、研发效率 +50%、团队满意度 +30%
- 经验教训：①架构改造离不开组织改造 ②团队拓扑四类要齐 ③Tech Lead 是关键
- 未来演进：FinOps 团队、AI 平台团队、远程协作模式优化
