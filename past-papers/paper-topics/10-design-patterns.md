## 一、核心理论

### OO 设计原则（SOLID + 其他）

| 原则 | 含义 |
|---|---|
| **S**RP | 单一职责 |
| **O**CP | 开闭原则（开放扩展、关闭修改） |
| **L**SP | 里氏替换 |
| **I**SP | 接口隔离 |
| **D**IP | 依赖倒置 |
| 迪米特 | 最少知识 |
| 合成复用 | 优先组合而非继承 |

### GoF 23 种模式分类

- **创建型（5）**：单例 / 工厂方法 / 抽象工厂 / 建造者 / 原型
- **结构型（7）**：适配器 / 桥接 / 组合 / 装饰 / 外观 / 享元 / 代理
- **行为型（11）**：责任链 / 命令 / 解释器 / 迭代器 / 中介者 / 备忘录 / 观察者 / 状态 / 策略 / 模板方法 / 访问者

### 架构级模式（比 GoF 高一层）

- **MVC** / MVVM / MVP
- **分层** / 六边形 / 洋葱
- **CQRS**（读写分离）
- **事件溯源**（Event Sourcing）
- **微服务模式**（Sidecar、BFF、Saga）

**【完整题目】**（约 410 字）

设计模式（Design Patterns）是软件领域针对常见问题的可复用解决方案，是面向对象设计原则在工程实践中的结晶。GoF 23 种经典模式按目的可分为创建型（5 种）、结构型（7 种）、行为型（11 种）三大类，分别解决"对象创建、组合关系、行为协作"问题。在架构层面则有 MVC、MVVM、CQRS、事件溯源（Event Sourcing）、Sidecar、BFF、Saga 等更高层次的架构级模式。优秀的架构师不仅要熟知模式定义，更要理解其背后的 SOLID 原则（单一职责 SRP、开闭 OCP、里氏替换 LSP、接口隔离 ISP、依赖倒置 DIP），在实际场景中根据"扩展点"和"变化频率"灵活组合应用，避免过度设计与僵化套用。

#### 二、核心理论（400 字提纲）

- SOLID 原则：SRP / OCP / LSP / ISP / DIP + 迪米特 + 合成复用
- GoF 23 种分类：
  - 创建型 5：单例 / 工厂方法 / 抽象工厂 / 建造者 / 原型

#### 三、实践论述（1500 字提纲，分 5 节）

##### 3.1 创建型 + 结构型应用
- 工厂方法 + 抽象工厂：多数据源（MySQL/Oracle/PG）切换，DataSourceFactory.create()
- 装饰器：订单优惠叠加（满减 → 折扣 → 秒杀），OrderPriceDecorator 链
- 量化：新增数据源 0.5 天接入、价格规则单测覆盖 90%

##### 3.2 行为型应用
- 策略模式：支付方式（微信/支付宝/银联/数字人民币），PaymentStrategy 接口
- 责任链：订单校验链（库存→价格→风控→反欺诈），ValidatorChain
- 观察者：订单状态变更 → 履约/对账/通知 多订阅者，Spring ApplicationEvent
- 状态机：订单生命周期（新建→已付→已发→已收→已评），StateMachine
- 量化：新增支付 3d→0.5d、新增校验器 1h、扩展成本 -70%

##### 3.3 架构级模式
- CQRS：读写分离，读走 ES（索引）、写走 MySQL（事务）
- 事件溯源：订单状态以 Event 流持久化，可回放调试
- Saga：长事务（下单→扣库存→支付→履约）补偿编排
- BFF：移动端/PC端各自 BFF 聚合
- 量化：读 P99 50ms、Saga 补偿成功率 99.9%

##### 3.4 SOLID 落地
- OCP：策略模式 + SPI 机制，新增不改老代码
- DIP：依赖接口而非实现，Spring DI
- ISP：网关 / 内部 / 后台三套接口分离
- 量化：单测覆盖率 85%、循环依赖 0

##### 3.5 风险与应对（必有）
- 风险 1：模式过度设计 → 建立"是否引入新模式"评审清单
- 风险 2：模式滥用导致复杂度爆炸 → 5-8 种模式封顶
- 风险 3：新人理解成本高 → 模式手册 + Code Review 守护

#### 四、总结与展望（250 字提纲）

- 项目结果：5 种 GoF + 2 种架构模式落地、扩展成本 -70%、覆盖率 85%
- 经验教训：①模式不是越多越好 ②场景匹配比模式名重要 ③SOLID 是底层逻辑
- 未来演进：领域事件 + 事件溯源全面化、ArchUnit 模式守护

### 模拟论文题 2 · 论面向对象设计原则与重构的应用

**【完整题目】**（约 410 字）

软件系统在长期演化中往往会逐渐"腐化"，出现高耦合、低内聚、依赖混乱、可读性下降等问题，最终阻碍业务迭代速度。面向对象设计原则——**SRP 单一职责、OCP 开闭、LSP 里氏替换、ISP 接口隔离、DIP 依赖倒置**（合称 SOLID）——以及迪米特原则、合成复用原则等，为软件设计提供了系统化的判断标准。当系统违反这些原则时，重构（Refactoring）是恢复设计健康的核心手段：通过提取方法、提取类、内联函数、移动方法、消除重复、引入参数对象等小步动作，在不改变行为的前提下逐步改善结构。Martin Fowler 的《重构》一书系统总结了 70+ 种重构手法，配合 IDE（IntelliJ）和单元测试（JUnit），重构已经成为现代研发的日常实践。

请围绕"**论面向对象的设计原则与重构**"论述以下三个问题：

1. **概要叙述**你参与设计与开发的软件项目，以及你担任的主要工作（约 300 字应答）。
2. **简要说明** SOLID 设计原则、常见代码坏味道以及主流重构手法（约 400 字应答）。
3. **详细论述**你在项目中如何识别坏味道、应用 SOLID + 重构改善设计，最终成效（约 1500-1800 字应答）。

**【提纲式参考答案】**（约 1400 字提纲）

#### 摘要框架（300 字模板）

"我于 {2023} 年牵头 {核心交易系统 / 老 ERP / 中后台} 的代码质量提升项目，担任 {重构负责人}。系统 {Java 60 万行 / 圈复杂度平均 18 / 单测覆盖 30%}，新需求平均要改 8 个文件、缺陷率高。本文论述 SOLID + 重构系统化落地：基于 SonarQube + ArchUnit 识别 12 类坏味道、按风险优先级分批重构、每批 100% 单测保护。3 个月后圈复杂度降至 6、单测覆盖 80%、新需求平均改 2 个文件、缺陷率 -60%。"

#### 一、项目背景（350 字提纲）

- **业务背景**：5 年老核心系统，代码腐化严重
- **团队规模**：12 人（核心 5 + 测试 4 + Code Owner 3）
- **关键质量属性**：可修改性、可读性、可测试性、可维护性
- **业务约束**：边重构边交付、零行为变更、可回滚

#### 二、核心理论（400 字提纲）

- SOLID：
  - **SRP** 单一职责（一个类一个变化原因）
  - **OCP** 开闭（对扩展开放、对修改关闭）
  - **LSP** 里氏替换（子类可替换父类）
  - **ISP** 接口隔离（多个专用接口胜过单个胖接口）
  - **DIP** 依赖倒置（依赖抽象不依赖实现）
- 迪米特原则：最少知识
- 合成复用：组合优于继承
- 代码坏味道（Fowler 22 种）：重复代码、过长方法、过大类、过长参数、霰弹式修改、依恋情结、数据泥团、原始类型偏执、Switch 语句、平行继承、冗赘类、夸夸其谈通用性、临时字段...
- 重构手法：提取方法 / 内联 / 移动 / 改名 / 引入参数对象 / 替换条件为多态

#### 三、实践论述（1500 字提纲，分 4 节）

##### 3.1 坏味道识别 + 优先级
- 工具：SonarQube 静态扫描 + ArchUnit 架构守护 + IDE Inspector
- 量化：圈复杂度 > 15 共 80 处、过长方法 > 100 行 50 处、霰弹式修改 12 类
- 风险优先级：影响范围 × 变更频率
- 量化：识别 200+ 处问题，分 5 批重构

##### 3.2 SOLID 应用案例
- SRP：OrderService 拆为 OrderQueryService + OrderCommandService + OrderEventService
- OCP：if-else 支付分支 → 策略模式 + SPI 注册
- LSP：BasePromotion 子类违反父类契约 → 引入显式接口
- ISP：胖接口 OrderApi 拆为查询/命令/事件三接口
- DIP：直接依赖 MySQL → 依赖 OrderRepository 接口

##### 3.3 重构动作 + 测试保护
- 提取方法：100 行 → 平均 20 行
- 提取类：1 个 800 行类 → 5 个 150 行类
- 引入参数对象：8 参 → 1 个 OrderRequest 对象
- 测试保护：每次重构前补单测覆盖 → 重构 → 验证
- 量化：圈复杂度 18→6、覆盖率 30%→80%

##### 3.4 风险与应对（必有）
- 风险 1：重构破坏业务 → 单测 + 集成测试 + 灰度
- 风险 2：边重构边交付的进度冲突 → 每天 70% 业务 + 30% 重构
- 风险 3：团队认知不齐 → SOLID 培训 + Code Review 守护

#### 四、总结与展望（250 字提纲）

- 项目结果：圈复杂度 18→6、覆盖率 30%→80%、改动文件 8→2、缺陷率 -60%
- 经验教训：①重构必须有单测保护 ②小步快走优于大重构 ③SOLID 是判断标准不是教条
- 未来演进：ArchUnit 持续守护、AI 代码评审、TDD 全面推行
