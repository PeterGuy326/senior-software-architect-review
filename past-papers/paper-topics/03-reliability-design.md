# 论文主题 03 · 系统可靠性设计

## 历年出题角度

- 论系统可靠性分析与设计（**高频经典**）
- 论软件可靠性设计与实现
- 论软件容错技术及其应用

## 一、核心理论

### 可靠性指标（必写）

| 指标 | 含义 | 计算 |
|---|---|---|
| **MTBF** | 平均无故障时间（Mean Time Between Failures） | — |
| **MTTR** | 平均修复时间（Mean Time To Repair） | — |
| **可用性 A** | Availability | A = MTBF / (MTBF + MTTR) |
| **SLA** | 服务级别协议 | 99.9% / 99.99% / 99.999% |

### 可用性对应时间（金融必备）

| 可用性 | 年停机 |
|---|---|
| 99% | 3.65 天 |
| 99.9% | 8.76 小时 |
| **99.99%** | **52.6 分钟** |
| **99.999%** | **5.26 分钟**（电信级） |

### 容错技术

| 技术 | 原理 |
|---|---|
| **N 版本程序设计** | 独立开发 N 份，多数表决 |
| **恢复块** | 主块失败切备份块 |
| **防卫式程序** | 异常检查、assert |

### 冗余分类

- **结构冗余**：静态（主备）/ 动态（双机热备）/ 混合
- **信息冗余**：校验码、CRC
- **时间冗余**：重试、补偿
- **冗余附加**：额外硬件 / 软件

### 模拟论文题 1 · 论高可用系统的可靠性设计与容错技术应用

**【完整题目】**（约 410 字）

随着金融、电信、政务等关键领域系统对稳定性的要求不断提升，"四个 9"（99.99%）甚至"五个 9"（99.999%）已成为核心业务系统的硬性 SLA。可靠性设计作为系统架构非功能设计的核心组成部分，涉及 MTBF、MTTR、可用性 A、RPO、RTO 等关键指标，要求架构师从**故障预防、故障检测、故障恢复**三个维度系统性地构建容错体系。常用技术包括结构冗余（主备/双活/多活）、信息冗余（CRC/校验码/多副本）、时间冗余（重试/补偿/幂等），以及 N 版本程序设计、恢复块、防卫式编程等容错方法。同城双活 + 异地灾备的"两地三中心"已成为金融级标配。

请围绕"**论系统可靠性分析与设计**"论述以下三个问题：

1. **概要叙述**你参与设计与开发的软件项目，以及你担任的主要工作（约 300 字应答）。
2. **简要说明**软件可靠性的核心指标（MTBF/MTTR/A/RPO/RTO）以及主要冗余分类与容错技术（约 400 字应答）。
3. **详细论述**你在项目中如何从故障预防、检测、恢复三个维度落地可靠性设计，遇到的挑战和最终成效（约 1500-1800 字应答）。

**【提纲式参考答案】**（约 1400 字提纲）

#### 摘要框架（300 字模板）

"我于 {2023} 年参与了 {银行核心支付 / 证券交易 / 电信计费} 系统的 {可用性提升 / 双活改造} 项目，担任 {可靠性架构师}。系统服务 {日均 X 亿笔交易 / RT < Y ms / 可用性 SLA 99.99%}。本文以该项目为背景，论述系统可靠性的设计实践：通过同城双活 + 异地灾备 + 半同步复制 + 自动故障切换 + Sentinel 熔断 + 混沌工程演练等组合战术，将系统可用性从 99.9% 提升至 99.995%，连续 14 个月零 P0 故障。"

#### 一、项目背景（350 字提纲）

- **业务背景**：金融支付系统，老架构主备模式，半年内出过 2 次 P0
- **团队规模**：15 人（架构 + SRE + 研发）
- **关键质量属性**：可用性、一致性、性能、安全
- **业务约束**：SLA 99.99%（年停机 < 52.6 分钟）、RPO < 5s、RTO < 30s

#### 二、核心理论（400 字提纲）

- 可靠性指标：MTBF（平均无故障）/ MTTR（平均修复）/ A = MTBF/(MTBF+MTTR)
- 可用性等级表：99% (3.65 天) / 99.9% (8.76 小时) / 99.99% (52.6 分) / 99.999% (5.26 分)
- RPO/RTO：数据恢复点/恢复时间目标
- 冗余三分类：结构（主备/双活）/ 信息（CRC/多副本）/ 时间（重试/补偿）
- 容错技术：N 版本程序、恢复块、防卫式编程
- 故障三维度：预防、检测、恢复

#### 三、实践论述（1500 字提纲，分 4 节）

##### 3.1 故障预防（架构层）
- 同城双活：A/B 机房距离 30 公里、专线互联、对等部署
- 异地灾备：上海冷备 → 改为温备
- 数据库：MySQL 半同步复制 + MHA + Orchestrator
- 中间件冗余：Redis Cluster 哨兵、RocketMQ 3 主 3 从
- 量化效果：单点降为零，主备切换 RTO < 30s

##### 3.2 故障检测（监控告警）
- 三支柱：Prometheus + Grafana + Alertmanager + ELK + SkyWalking
- 告警分级：P0/P1/P2/P3，P0 直接电话+短信
- 健康检查：K8s Liveness/Readiness、5s 一次心跳
- 业务监控：交易成功率、业务异常码、用户感知 RT
- 量化效果：MTTR 从 45 分钟降到 8 分钟

##### 3.3 故障恢复（自动化）
- 自动故障切换：Keepalived + VIP 漂移、ETCD 仲裁
- 流量保护：Sentinel 熔断（QPS 阈值/慢调用比例）+ 限流 + 降级
- 数据可靠性：本地消息表 + 事务消息 + 对账兜底
- 混沌工程：ChaosBlade 每周注入故障演练
- 灰度发布 + 一键回滚

##### 3.4 风险与应对（必有）
- 风险 1：脑裂 → 仲裁集群 + 第三机房见证节点
- 风险 2：双活数据冲突 → 单元化 + 流量按用户分片
- 风险 3：依赖第三方 SDK 不稳定 → 降级开关 + Mock 兜底

#### 四、总结与展望（250 字提纲）

- 项目结果：可用性 99.995%、连续 14 个月零 P0、RPO=2s、RTO=18s
- 经验教训：①可靠性是设计出来的不是修出来的 ②演练频次决定真实可用性 ③人工切换是反模式
- 未来演进：单元化多活、Service Mesh 故障注入、AIOps 异常预测
