# 案例分析 · 过线保命卡（45/75 战术）

> 90 分钟 3 道题 / 每题 25 分 / 45 分合格 = 平均每题 15 分。
> **战术核心**：第 1 题必做拿 15+ 分，选 2 道自己擅长的各拿 15+ 分。
> **心法**：不追求任何一题满分，只求每题都稳稳压过 15。填空必写、画图必画、对比必列、结论必给。

## 一、90 分钟怎么分配

| 时间段 | 动作 | 关键点 |
|---|---|---|
| **0-5 min** | **通读 5 道题** | 铅笔在题号旁标"必做 ✓ / 备选 ○ / 放弃 ✗"；数一下题干里几个"问 1/问 2/问 3"，估工作量 |

## 二、选题决策树（5 分钟读完 5 道题的判定顺序）

第 1 题（必做）：**几乎每年都是 ATAM 质量属性场景填空 + 敏感点/权衡点/风险点/非风险点** — 送分题，只要背熟六元组和信号词，稳拿 15+ 分。

后 4 题按下面**优先级从上到下扫**，选 2 道：

1. ✅ **有"填空 / 填表 / 补图"字样** → 优先选，答案卡格式化，评分老师看到关键词就给分
2. ✅ **数据库设计题**（ER 图、范式判断、SQL、读写分离）→ 套路死板容易背，选它
3. ✅ **微服务改造 / 单体拆分 / SOA 集成**（DDD / 拆分原则 / 分布式事务）→ 万能模板套
4. ✅ **消息队列 / 缓存**（Kafka/RocketMQ 选型、Cache Aside、穿透击穿雪崩）→ 高频，模板密度高
5. ⚠️ **架构风格对比**（SOA vs 微服务、OO vs 解释器、Lambda vs Kappa）→ 有对比表就选，纯论述题跳
6. ✗ **嵌入式实时系统**（RMS/EDF 可调度分析、看门狗、HAL 分层）→ 除非你是嵌入式工程师，避开
7. ✗ **通信 5G/MQTT/CoAP 深度题、区块链、量子加密** → 陌生技术，果断放弃
8. ⚠️ **UML 补图**（类图 6 大关系、时序图、状态图）→ 只考"识别关系"就选，要求手画完整图跳
9. ⚠️ **Web 综合**（负载均衡+缓存+分库分表堆叠）→ 掺题多的时候选，纯计算跳

> 大数据 Lambda vs Kappa 二选一时 → **选 Lambda**（模板更成熟）。
> 分布式事务四方案对比 → **本地消息表** 是万能答案（除非题干明说"强一致"才选 TCC）。

## 三、🔥🔥🔥 第 1 题必做 · ATAM 质量属性场景（必背 25 条）

### 3.1 质量属性场景 6 元组（10 分基础题必拿）

**必背填空模板**：

```
(1) 刺激源 Source     — 谁发起（用户 / 攻击者 / 内部组件 / 外部系统 / 定时任务）
(2) 刺激 Stimulus     — 发生什么（请求 / 攻击 / 故障 / 超时 / 配置变更）
(3) 制品 Artifact     — 影响谁（订单服务 / 数据库 / 网络 / 缓存 / 整个系统）
(4) 环境 Environment  — 什么状态（正常运行 / 高峰 / 降级 / 故障 / 恢复中）
(5) 响应 Response     — 系统做什么（受理 / 切换 / 拒绝 / 降级 / 补偿 / 报警）
(6) 响应度量 Measure  — 量化数字（RT<500ms / 可用性>99.99% / QPS>1万 / 丢失=0）
```

> **拿分死规则**：环境**必写"高峰/降级/故障"而不是空泛的"正常运行"**；响应度量**必带数字**（ms / % / TPS / 条 / GB）。

**万能场景例句**（性能/可用性最常考，其余四种照此格式改词即可）：

- **性能**：【用户】在【大促高峰】对【订单服务】在【QPS 5 万运行时】发起【下单请求】，系统【正常受理返回】，度量【P99 < 200ms、成功率 ≥ 99.99%】
- **可用性**：【监控】在【主节点宕机】对【数据库集群】在【故障切换模式】检测【心跳丢失】，系统【自动切换从节点】，度量【切换 < 30s、数据零丢失】
- 其余四种关键词替换：**安全**（攻击者/SQL 注入/WAF 拦截/成功率 100%）、**可修改**（运营/新增规则/配置化生效/上线 < 1 天）、**可靠**（生产者/网络抖动/重试持久化 ACK/丢失率 0）、**易用**（新用户/首次登录/引导撤销提示/10 min 独立完成）

### 3.2 四类点识别信号词（必考 8-10 分）

| 类型 | 信号词 | 一句话判定 | 例子 |
|---|---|---|---|
| **敏感点** | "为达 X，采用 Y" / "该决策直接影响..." | **关键决策**，直接决定某一质量属性目标能否达成 | Disruptor 单线程撮合直接决定延迟 < 1ms |
| **权衡点** | "既... 又..." / "提升 X 但降低 Y" | **同时正向和负向影响 2 个及以上属性** | HTTPS 提升安全但降低性能约 10% |
| **风险点** | "可能导致... / 存在隐患 / 未验证 / 容量未知" | **潜在问题**，可能让质量目标达不到 | 单点 MQ 未持久化、异地异步复制可能丢单 |
| **非风险点** | "已验证 / 业界成熟 / 已有方案" | **成熟方案**，风险已被消除 | Kafka 集群、MySQL 主从、K8s 部署 |

**答题万能模板**（每条 3 句话）：

```

一旦【失效/参数不当】将【导致 P99 超标/超卖/宕机】。

YY 是【权衡点】，同时提升【安全性 +】和降低【性能 -，约 10% CPU 开销】，

建议引入【Sentinel 熔断 / 多副本持久化 / 全链路压测】战术，
将其转化为【非风险点】。

WW 是【非风险点】，采用【业界成熟方案 Kafka/MySQL/K8s】，
已在【阿里/字节/OceanBase】等大型场景验证。
```

| 质量属性 | 常用战术（至少答 3 个） |

### 3.4 Ping/Echo vs 心跳（近年真题原型）

| 维度 | Ping/Echo | 心跳 Heartbeat |
|---|---|---|
| **主动方** | **监控端**主动发 Ping | **被监控端**主动发心跳 |
| **消息方向** | 双向（请求 + 响应） | 单向 |
| **网络开销** | 大（约心跳 2 倍） | **小** |
| **监控端压力** | 大（要主动发 N 个请求） | **小**（被动接收） |
| **附带状态** | 弱 | **可携带 CPU/QPS/内存指标** |
| **适用** | 少量节点、要即时确认 | **大规模节点、云原生环境** |

> 大规模微服务、K8s、云原生 → 选**心跳**；小型监控、要即时探测 → 选 **Ping/Echo**。

## 四、🔥🔥 高频题型必背套路

### 4.1 数据库设计 / ER 图（约 65% 概率出现）

**必答四段套路**：

1. **补 ER**：找题干名词 → 实体；动词短语 → 联系；属性归到实体。**M:N 联系必须独立建表**（主键 = 双方主键组合）
2. **转关系模式**：1:1 合入任一方；1:N 在 N 端加外键指向 1 端；**M:N 独立表**
3. **判范式**：先列函数依赖 F → 求候选键（属性闭包）→ 判部分依赖（→ 违 2NF）/ 传递依赖（→ 违 3NF）/ 决定因素非超键（→ 违 BCNF）
4. **分解**：分解到 3NF 或 BCNF，必须**保持依赖 + 无损连接**（这两个词必写出来）

**万能高分句**（照抄）：

- "学生与课程之间是 **多对多（M:N）** 联系，需引入**选课**联系表，主键为 **(学号, 课号)** 复合主键"
- "当前模式存在**传递依赖**：`学号 → 系号 → 系主任`，非主属性传递依赖于码，违反 **3NF**"
- "应分解为 `学生(学号, 姓名, 系号)` 和 `系(系号, 系主任)`，**保持依赖 + 无损连接**"
- "为保证**参照完整性**，在子表的外键上定义 **ON DELETE CASCADE / SET NULL / RESTRICT**"
- "**弱实体**（如'病区'）依赖父实体存在，主键必须是**复合主键 (父键, 局部编号)**"

**高频考点速查**：

| 考点 | 关键词答法 |
|---|---|
| **1NF** | 属性原子、不可再分。违规=一列存多值/逗号分隔 |
| **2NF** | 1NF + 消除**部分依赖**。违规=联合主键中只依赖一部分 |
| **3NF** | 2NF + 消除**传递依赖**。违规=非主属性依赖非主属性 |
| **BCNF** | 3NF + 所有决定因素都是超键 |
| **事务 ACID** | 原子/一致/隔离/持久 |
| **隔离级别** | 读未提交/读已提交/可重复读/串行化 |
| **并发问题** | 丢失修改（写覆盖）/ 脏读（读到未提交）/ 不可重复读（两次读不同）/ 幻读（范围多出行）|
| **读写锁** | S 锁共享、X 锁排他；缺点=写饥饿、死锁、锁管理复杂 |
| **CAP** | 分布式必选 P；AP（MongoDB/Cassandra）vs CP（ZK/Etcd）|
| **BASE** | 基本可用 + 软状态 + 最终一致 |

**读写分离必答**（问"改完立刻读到旧值"必考）：

| 方案 | 做法 | 优缺点 |
|---|---|---|
| **强制读主 Hint Master** | 写后 1-2s 内读走主库 | 强一致，加主库压力 |
| **写后双写缓存** | 改完直接 SET Redis 新值 | 不加主库压力，有极小不一致窗口 |
| **半同步复制 / 等 GTID** | 写后等至少 1 从库 ACK | 一致性强，写延迟上升 |

### 4.2 微服务改造（约 40% 概率）

**必答五段套路**：

1. **单体痛点**：发布慢、故障影响面大、协同冲突多、新业务难承载、DB 瓶颈（**照抄题干数字**）
2. **拆分依据**：**DDD 限界上下文**（Bounded Context）+ 业务能力 + 单一职责 + 团队自治（Two-Pizza）
3. **服务粒度**：核心域（销售/订单/库存/支付）+ 支撑域（HR/供应商/商品主数据）+ 通用域（认证/权限/消息）
4. **通信方式**：**同步 REST/gRPC**（强一致 + 实时反馈）+ **异步 MQ 事件**（解耦 + 最终一致）
5. **服务治理**：Nacos（注册）+ Sentinel（熔断限流）+ SkyWalking（链路追踪）+ Apollo（配置）+ Spring Cloud Gateway（网关）

**渐进式拆分 4 阶段**（拆路径题必考）：

```
阶段 1 · 绞杀者代理     → 前置网关，单体内部模块化，不拆进程
阶段 2 · 边缘上下文先拆 → 拆用户/权限/商品主数据（依赖少）
阶段 3 · 核心业务拆分   → 拆销售/库存/订单（引入 MQ + TCC）
阶段 4 · 收尾           → 拆财务/HR，老 ERP 转只读，最终下线
```

> **红线**：禁止 Big Bang 一次性切换；每阶段必须有**回滚预案**（网关 Pass-Through / 切流回老库 / binlog 反向同步）；双写过渡 + 灰度切流（1% → 10% → 50% → 100%）。

**分布式事务四方案必背对比表**：

| 方案 | 一致性 | 性能 | 复杂度 | 适用 |
|---|---|---|---|---|
| **2PC / XA** | 强 | 差 | 中 | 传统金融、异构 DB |
| **TCC**（Try-Confirm-Cancel） | 强 | 中（+60-100ms）| 高（每业务 3 套接口） | **核心交易、资损红线** |
| **Saga**（编排 + 补偿） | 最终 | 好 | 中 | 长流程、跨多服务 |
| **本地消息表** | 最终 | **好**（+10ms）| 低 | **一般业务、通知事件（万能答案）** |
| **MQ 事务消息**（RocketMQ half message）| 最终 | 好 | 低 | 与 MQ 生态一致 |

> **不知道选哪个 → 答"本地消息表 + 消费幂等"**。除非题干出现"资损/绝对不能不一致/金融监管"字样才选 TCC。

**幂等三件套**（分布式事务必附）：全局事务 ID 作幂等键 + 空回滚保护 + 悬挂检查 + 超时自动 Cancel + T+1 对账兜底。

### 4.3 消息队列 / 缓存（约 35-40% 概率）

**消息队列选型 4 大件对比表**（必背）：

| 维度 | Kafka | RabbitMQ | RocketMQ | Pulsar |
|---|---|---|---|---|
| 吞吐 | **百万级 TPS** | 万级 | 十万级 | 百万级 |
| 延迟 | ms 级 | **μs 级最低** | ms 级 | ms 级 |
| 顺序 | 分区内 | 队列内 | Queue 内 + 顺序 API | 分区内 |
| 事务消息 | 弱 | 无 | **有（half + 回查）** | 有 |
| 副本 | ISR 半同步 | 镜像队列 | **SYNC_MASTER 同步双写** | BookKeeper |
| 协议 | 自有 | **AMQP 最丰富** | 自有 + OpenMessaging | 自有 + MQTT + Kafka |
| 适用 | **日志/大数据** | **业务消息/复杂路由** | **金融/电商/事务** | **云原生/多租户** |

> **选型口诀**：日志超高吞吐 → Kafka；金融强一致 + 事务消息 → **RocketMQ**；复杂路由 + 多语言 → RabbitMQ；云原生多租户 IoT → Pulsar。

**消息可靠性三端保障**（不丢消息必考）：

| 端 | 保障 |
|---|---|
| **生产端** | 同步发送 + Confirm ACK + 重试（1s/2s/4s 指数退避）+ 本地兜底 failed_msg 表 |
| **Broker** | 多副本 + **SYNC_MASTER 同步双写** + **SYNC_FLUSH 同步刷盘** + 跨可用区 |
| **消费端** | **手动 ACK** + 业务处理与 offset 提交同一本地事务 + 幂等去重表 UNIQUE INDEX(biz_key) + 死信队列 DLQ |

> **金句**：**at-least-once + 业务幂等 = exactly-once 效果**。

**缓存三大问题必背**：

| 问题 | 现象 | 解法 1 | 解法 2 |
|---|---|---|---|
| **穿透**（不存在的 key）| 黑产刷 | **布隆过滤器**（误判率 0.1%）| **缓存空值**（TTL 60s + rand）|
| **击穿**（单热点过期）| 瞬间打爆 DB | **互斥锁**（SETNX + PX 防死锁）| **逻辑过期 + 异步刷新** |
| **雪崩**（大量同时过期）| 集群性打垮 | **TTL 打散**（base + rand(0,600s)）| **多级缓存**（Caffeine + Redis）+ **熔断降级** |

**Cache Aside 必背**：

- **读**：查 L1 → 未命中查 L2 → 未命中加分布式锁 → 查 DB → 回填 L2 → 回填 L1 → 返回
- **写**：**先更新 DB，再删除缓存**（不是"更新"，删才幂等）
- **为何不先删缓存再更 DB**：并发下读请求会把旧值回写缓存，**长期脏数据**
- **兜底强一致**：Canal 订阅 binlog → MQ → 异步失效缓存

**热点 Key 治理**：本地 L1 缓存兜住 + Hot Key 拆多副本（`sku:{id}:0~N`）+ JD-HotKey/Sentinel 热点探测 + Redis Cluster readonly 从节点分担。

### 4.4 架构风格对比（约 25% 概率）

**11 种风格一句话背**：管道-过滤器（数据流/ETL）、分层（OS/Spring）、C/S（企业内网）、B/S（Web）、事件驱动（MQ/GUI）、黑板（AI 推理）、解释器（JVM/规则引擎）、MVC/MVVM（Web UI）、SOA（ESB 粗粒度）、微服务（Spring Cloud 细粒度）、REST（资源+HTTP）。

**OO vs 解释器**（真题原型）：

- 规则频繁改、要运营配置化 → **解释器（DSL + 外部配置）**，牺牲性能换灵活性
- 性能优先、规则稳定 → **OO**（编译执行 + JIT 优化）

**SOA vs 微服务**：

| 维度 | SOA | 微服务 |
|---|---|---|
| 粒度 | 粗（业务服务）| 细（限界上下文）|
| 通信 | **ESB 总线**（集中）| API Gateway + MQ（去中心）|
| 数据 | 共享数据库常见 | **Database Per Service** |
| 协议 | SOAP/WebService | REST/gRPC |
| 部署 | 单体服务 | 独立容器/K8s |
| 适用 | 企业集成（跨异构系统）| 互联网规模、快速迭代 |

**Lambda vs Kappa**：

| 维度 | Lambda | Kappa |
|---|---|---|
| 层次 | 批 + 速度**双层** | **仅流式**（Flink 统一）|
| 优势 | 准确、可回溯 | **简化、单套代码** |
| 劣势 | **两套代码维护贵** | 大数据量历史回填慢 |
| 选型 | 需批 + 实时兼顾 → **Lambda（默认答案）** | 完全实时优先 → Kappa |

## 五、答题模板（万能框架）

### 5.1 通用回答结构（每小问 3-5 分钟）

```
【总起】1 句点明观点/结论（例：本场景推荐 X 方案）
【展开】3 条要点，每条格式为：
  • 要点 A —— 【概念/术语】+ 【具体做法】+【量化参数或本架构落地】
  • 要点 B —— 同上
  • 要点 C —— 同上
【收尾】1 句结论/建议/权衡说明
```

### 5.2 填空题拿分技巧

- **看题干找线索词**：
  - "高并发/QPS" → 答**性能/可用性**
  - "敏感数据/合规/等保" → 答**安全性**
  - "灵活配置/上线快" → 答**可修改性**
  - "多终端/兼容" → 答**兼容性**
  - "上手简单" → 答**易用性**
- **不确定时用万能填空数字**（度量必带数字！）：
  - 性能：P99 < 500ms、平均 < 200ms、TPS ≥ 1 万
  - 可用性：≥ 99.99%（年停机 < 52.6 min）、切换 < 30s
  - 并发：QPS 5 万、峰值 10 万、日 800 万笔
  - 一致性：数据零丢失、成功率 ≥ 99.99%
- **6 元组填空万能兜底**：题干里挖出 5 个 W → 补第 6 个；环境**必写"高峰/降级/故障"**。

### 5.3 对比题 + 画图题速攻

- **对比三段式**：维度 1 A 优（引用题干数字）→ 维度 2 B 优 → 结论"本场景推荐 X，因为题干强调【关键约束】"
- **架构图不会画就画 4 层**：客户端 → CDN → 接入层（Nginx/LVS）→ 应用层（微服务）→ 数据层（缓存+库）
- **ER 图不会补就画 3-4 矩形+菱形连线**，标 1:N / M:N；**时序图 3 生命线 4 箭头**（用户→应用→DB→MQ）
- **必写标签**："分层架构"、"事件驱动"、"读写分离"等术语，评委看到关键词就给分
