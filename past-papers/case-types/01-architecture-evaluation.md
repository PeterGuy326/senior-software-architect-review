# 案例题型 01 · 架构评估（ATAM）

> **必考题型**，每年 1 题，25 分。

## 考点分布

- 质量属性**场景 6 元组**填空
- 识别**敏感点 / 权衡点 / 风险点 / 非风险点**
- 效用树**优先级**分析（业务价值 × 技术难度）
- 架构方法 / 战术选择

## 质量属性 6 元组（必背）

```
(1) 刺激源（Source）     — 谁/什么引发
(2) 刺激  （Stimulus）   — 发生了什么
(3) 制品  （Artifact）   — 影响的部分
(4) 环境  （Environment）— 运行环境
(5) 响应  （Response）   — 系统怎么做
(6) 响应度量（Measure）  — 量化指标
```

**例**：【用户】在【大促时】【订单服务】【运行正常时】【下单请求】【响应时间 < 500ms，成功率 > 99.99%】

## 四类点识别信号词

| 类型 | 信号词 | 例子 |
|---|---|---|
| **敏感点** | "为了... 我们选... / 该决策直接影响..." | 主备切换 < 30s 对可用性 |
| **权衡点** | "既...又... / 提升 X 但降低 Y" | HTTPS 提升安全但降性能 |
| **风险点** | "可能导致 / 存在隐患 / 尚未验证" | 单点 MQ 未持久化 |
| **非风险点** | "已验证 / 业界成熟 / 已有方案" | Kafka 集群、MySQL 主从 |

## 答题模板

### 问题 1：填空题（给场景填 6 元组）

**套路**：
```
(1) 源 = 题干中的用户 / 系统 / 外部事件
(2) 刺激 = 请求 / 攻击 / 故障
(3) 制品 = 被影响的模块 / 数据库 / 网络
(4) 环境 = 正常 / 高峰 / 故障模式
(5) 响应 = 系统的反应（切换 / 返回 / 拒绝）
(6) 度量 = 有数字！RT / QPS / 可用性 / 丢失量
```

### 问题 2：判断敏感点 / 权衡点 / 风险点

**套路**（务必每条都说**为什么**）：
```
XX 是【敏感点】，因为它直接决定了【可用性/性能/...】，是达成质量目标的关键。
YY 是【权衡点】，同时影响【安全性（+）】和【性能（-）】。
ZZ 是【风险点】，存在【单点 / 未验证 / 容量未知】隐患。
WW 是【非风险点】，采用【业界成熟方案 Kafka / MySQL】，已有充分验证。
```

### 问题 3：效用树排序

**套路**：
- 行优先级：**(业务价值, 技术难度)**，用 **(H, M, L)**
- 场景越具体得分越高，避免"性能好"这种空泛描述

## 万能高分句

- "该架构决策是**敏感点**，因为它**直接决定**了【可用性/性能】质量目标的达成"
- "【HTTPS 全链路加密】是**权衡点**：**提升了安全性**但**增加了约 10% 的 CPU 开销**"
- "**识别出该风险点**后，建议引入【Sentinel 熔断 / RocketMQ 持久化 / 多活部署】战术，将其**转化为非风险点**"
- "依据 **ATAM 第 5 步（效用树）**，【性能-吞吐 (H, H)】为最高优先级，应在架构决策中优先保障"

## 常见陷阱

| ❌ | ✅ |
|---|---|
| 敏感点、风险点混淆 | 敏感点 = **关键决策**；风险点 = **潜在问题** |
| 只说结论不说理由 | 每条判断必须跟一句**因为...** |
| 度量没数字 | 响应度量必须**可量化**（ms、%、TPS） |
| 分析不给改进方案 | 风险点必须给出**缓解战术** |

## 高频战术速查

| 质量属性 | 战术 |
|---|---|
| **可用性** | 心跳、Ping/Echo、冗余（主备/双活）、回滚、重试 |
| **性能** | 缓存、并发、资源池、减少计算、异步 |
| **安全** | 认证、授权、审计、加密、完整性校验 |
| **可修改性** | 模块化、封装、接口抽象、DI、配置化 |
| **可测试性** | 记录/回放、接口分离、内部监控 |
| **易用性** | 撤销、用户启动、系统启动、任务模型 |

> ⚠️ **自主命题**：题干场景为基于公开考点改编的虚构案例，避免版权风险；技术参数贴合真实工程实践。建议先**严格 25 分钟限时**作答，再对照参考答案。

### 模拟题 1 · 电商订单中台架构评估（25 分）

**【题干】**（约 850 字）

某大型综合零售集团旗下拥有 B2C 商城、跨境电商、线下门店三条独立业务线，长期以来三套订单系统数据模型各异、促销规则重复开发、库存共享困难。2024 年初集团决定建设统一订单中台，由架构师 W 主导设计。

项目关键指标：日订单峰值 **800 万笔**，大促期间 QPS 峰值 **5 万**，下单接口 **P99 < 200ms**，全年可用性 **99.99%**（停机不超过 52.6 分钟），新业务线接入周期 **< 1 个月**。

W 经过评审会议，最终选择"**微服务 + 事件驱动**"混合架构风格。基于 DDD 限界上下文将订单中台划分为 10 个业务服务（订单、支付、履约、促销、库存、会员、商品、结算、售后、对账）和 5 个基础服务（API 网关、注册中心、配置中心、链路追踪、统一日志）。关键技术决策包括：

1. **服务间同步通信**采用 gRPC（内部）与 REST（对外）双协议，**异步通信**统一使用 RocketMQ 集群（3 主 3 从持久化）；
2. **数据存储**遵循 Database Per Service 红线，订单库 MySQL 8.0 主从半同步 + 一主两从；商品库分 16 库 64 表，按 `tenant_id` 哈希分片；
3. **多级缓存**采用本地 Caffeine（L1）+ Redis Cluster（L2）+ MySQL（L3），Cache Aside 模式；
4. **下单链路**采用 TCC 三阶段补偿（Try-Confirm-Cancel）保证订单+库存+支付的最终一致性，库存扣减通过 Lua 脚本原子化；
5. **部署架构**为 Kubernetes 跨 3 个可用区，核心服务每个副本 6 个，通过 Service Mesh（Istio）做流量治理；
6. **熔断限流**：API 网关接入 Sentinel，按调用方+接口维度限流；
7. **监控**：SkyWalking 全链路追踪 + Prometheus 指标 + ELK 日志，告警通过钉钉机器人推送 SRE 值班群；
8. **安全**：全链路 HTTPS（TLS 1.3）+ JWT 鉴权 + 敏感字段 AES-256 加密落库。

为保证架构方案合理，W 计划采用 ATAM 方法对该架构进行评估。

**【小问】**（合计 25 分）

**问 1**（8 分）：用质量属性场景的 6 元组描述"大促期间订单系统的高性能场景"，要求每元素都给出**具体取值**。

**问 2**（10 分）：从上述架构决策中识别 **2 个敏感点**、**2 个权衡点**、**2 个风险点**、**2 个非风险点**，并简要说明判定理由。

**问 3**（7 分）：构建该订单中台的**质量属性效用树**，给出 4 个二级质量属性节点及各自最高优先级的具体场景（用 `(业务价值, 技术难度) = (H/M/L, H/M/L)` 标注），并解释为何"性能 - 下单 P99 < 200ms"应排在最高优先级。

---

**【参考答案】**

**问 1**：性能场景 6 元组（约 240 字）

| 元素 | 取值 |
|---|---|
| (1) 刺激源 | 大促活动期间的并发用户（峰值在线 200 万） |
| (2) 刺激 | 用户提交下单请求（含商品、收货地址、优惠券） |
| (3) 制品 | 订单服务集群及其依赖（库存服务、支付服务、Redis 缓存、MySQL 订单库） |
| (4) 环境 | 大促高峰运行模式（QPS 5 万，资源弹性扩容已完成） |
| (5) 响应 | 系统正常受理下单，扣减库存、生成订单号、写入数据库、返回结果 |
| (6) 响应度量 | **下单接口 P99 响应时间 < 200ms**，**成功率 ≥ 99.99%**，**单日峰值 800 万笔无超时降级** |

> 高分要点：每元素**必须有量化数字**，环境必须区分"正常 / 高峰 / 故障"模式，制品要细化到具体模块/中间件。

**问 2**：四类点识别（约 350 字）

- **敏感点 1**：**多级缓存（Caffeine + Redis）的 Cache Aside 策略**——它直接决定了下单接口能否达成 P99 < 200ms 的性能目标。一旦缓存命中率从 95% 跌至 80%，DB 压力激增、P99 必然超标，故是性能这一关键质量属性的敏感决策。
- **敏感点 2**：**RocketMQ 集群 3 主 3 从持久化**——它直接决定了"订单/支付/履约"事件在节点宕机时不丢消息，是可用性 99.99% 的关键保障。
- **权衡点 1**：**全链路 HTTPS + AES-256 加密**——同时影响**安全性（+，等保合规、防中间人攻击）**与**性能（-，TLS 握手与加解密 CPU 开销约 10%）**，是典型权衡。
- **权衡点 2**：**TCC 三阶段补偿**——同时影响**一致性（+，订单+库存+支付最终一致）**与**性能（-，三次远程调用增加 50-80ms 延迟）**与**可修改性（-，每个业务方法需写 Try/Confirm/Cancel 三套逻辑）**。
- **风险点 1**：**促销服务作为单体保留且未做熔断**——逻辑密集、流量大但缺乏 Sentinel 接入，存在被异常流量击穿后波及订单服务的隐患，威胁可用性目标。
- **风险点 2**：**对账服务未做全链路压测**——大促期间峰值数据量未知，存在批处理超时或资源耗尽风险。
- **非风险点 1**：**Nacos + Apollo 注册/配置中心集群**——业界成熟方案、社区案例充分，已在阿里、字节等大型电商场景验证。
- **非风险点 2**：**Kubernetes 跨 3 可用区部署 + Istio 流量治理**——CNCF 毕业项目、生产级方案，无技术不确定性。

**问 3**：效用树构建（约 280 字）

```
订单中台效用树
├── 性能
│   ├── 下单接口 P99 < 200ms        (H, H)  ⭐ 最高
│   └── 大促 QPS ≥ 5 万              (H, M)
├── 可用性
│   ├── 全年 99.99% (停机 < 52.6min) (H, H)  ⭐ 最高
│   └── 主备切换 < 30s               (H, M)
├── 可修改性
│   ├── 新业务线接入 < 1 个月         (M, M)
│   └── 新增促销规则 < 1 周           (M, L)
└── 安全性
    ├── 等保三级合规                  (H, M)
    └── 敏感数据加密存储              (M, L)
```

**为何"下单 P99 < 200ms (H, H)"排首位**：① **业务价值 H**——直接关系大促 GMV 和用户体验，每增加 100ms 下单延迟，转化率下降约 1%；② **技术难度 H**——涉及多级缓存、TCC 补偿、RocketMQ 异步、库存原子扣减等多重技术决策的耦合，是架构核心瓶颈点；③ ATAM 方法论要求**优先关注高业务价值且技术风险大的场景**，此处 (H, H) 双高，是架构决策中最必须严控的目标。

**【评分要点】**

| 得分项 | 分值 | 关键词/要求 |
|---|---|---|
| **6 元组 6 个元素**齐全 | 6 分 | 每元素 1 分；缺一扣一分 |
| **响应度量含具体量化数字** | 2 分 | 必须出现 P99/QPS/可用性数字 |
| **四类点每类 2 个** | 8 分 | 每点 1 分；判定准确即给分 |
| **每点附"因为..."理由** | 2 分 | 没说理由扣 0.5 分/点 |
| **效用树二级节点 ≥ 4 个** | 2 分 | 必含性能/可用性，缺核心质量属性扣分 |
| **每场景含 (业务价值, 技术难度) 标注** | 2 分 | 漏标扣 1 分 |
| **优先级解释含业务+技术双维度** | 3 分 | 只说技术不说业务，最多给 1 分 |

**常见扣分点**：
- ❌ 6 元组的"环境"只写"正常运行"——必须区分高峰/故障/正常三种模式之一
- ❌ 把"使用 Redis 缓存"判为非风险点——Redis 不是非风险，**Cache Aside 策略**才是敏感点的判断对象
- ❌ 把"加密"直接判为非风险点——加密影响性能，是**权衡点**
- ❌ 效用树场景描述空泛（如"性能要好"）——必须**可量化**

**高分技巧**：
- 答风险点时**附带缓解战术**（"建议引入 Sentinel 熔断 + 拆只读副本，将其转化为非风险点"），可额外加 1-2 分
- 用 ATAM 第 5 步、第 6 步等**步骤名词**点明方法论，体现专业度
- 量化对比（"全链路 HTTPS 增加约 10% CPU 开销 / TCC 增加 50-80ms 延迟"）比泛泛而谈得分高

### 模拟题 2 · 工业物联网网关效用树（25 分）

**【题干】**（约 780 字）

某工业物联网平台为大型制造企业提供设备远程监控与预测性维护服务，架构师 L 负责该平台边缘网关的架构设计与评估。

平台规模：覆盖企业 12 个生产基地、**接入终端设备 1 万台**（PLC、传感器、机器人），每秒上行数据点数 **20 万条**，关键告警端到端延迟要求 **< 100ms**，设备掉线率 **< 0.1%**，平台年可用性 **99.95%**，故障切换时间 **< 60 秒**。

L 提交的边缘网关架构方案如下：

1. **边缘层**采用 KubeEdge 在每个基地部署 1 主 2 从边缘节点，工业协议解析（Modbus/OPC UA/MQTT）由 EdgeX Foundry 完成；
2. **数据缓冲**：边缘节点本地 SQLite 缓存 24 小时数据，断网期间自动续传，恢复后基于时间戳去重；
3. **传输链路**：基地→云通过 5G 专网 + IPSec VPN 双活，主用电信、备用移动；
4. **消息层**：云端 Kafka 集群（5 节点，分区数 = 100，副本因子 = 3），按设备 ID 哈希分区保证顺序；
5. **存储层**：时序数据 TimescaleDB（按月分区）+ 冷数据归档至 OSS；告警事件 PostgreSQL；
6. **流处理**：Flink 集群消费 Kafka 实时计算告警规则，告警结果写回 Kafka；
7. **告警下行**：从云端 Kafka 经 MQTT Broker 推送到边缘网关，再到现场看板/手机端；
8. **设备认证**：基于国密 SM2 证书的双向 mTLS，CRL 每 6 小时同步；
9. **远程升级（OTA）**：差分包升级，灰度发布按基地 → 设备组 → 单设备分级推进；
10. **运维**：边缘节点状态由云端统一仪表盘监控，离线 5 分钟自动告警。

L 计划采用 ATAM 方法评估该架构，确保关键告警场景的响应延迟和断网恢复能力满足业务要求。

**【小问】**（合计 25 分）

**问 1**（8 分）：用质量属性 6 元组描述"边缘网关与云端断网 5 分钟后恢复，缓冲数据自动续传不丢失"的**可用性场景**。

**问 2**（9 分）：识别该架构中至少 **3 个敏感点**和 **2 个权衡点**，每点说明对应的质量属性及判定理由。

**问 3**（8 分）：针对"关键告警端到端 < 100ms"目标，列出**至少 3 条战术**（注明所属类别，如"事件驱动""资源池"等），并简述每条战术在本架构中的具体落地形式。

---

**【参考答案】**

**问 1**：可用性（断网恢复）场景 6 元组（约 230 字）

| 元素 | 取值 |
|---|---|
| (1) 刺激源 | 边缘节点（KubeEdge 主节点） |
| (2) 刺激 | 与云端 Kafka/控制面失联（5G 专网中断），断网持续 5 分钟 |
| (3) 制品 | 边缘网关数据缓冲模块（SQLite）+ 上传链路 |
| (4) 环境 | 网络降级模式（主用电信链路中断，备用移动链路也未及时切换） |
| (5) 响应 | 边缘节点本地 SQLite 缓存继续接收数据；网络恢复后基于时间戳自动去重续传，期间业务不感知 |
| (6) 响应度量 | **数据零丢失**（24 小时缓冲容量），**恢复后续传完成时间 < 30 秒**，**设备掉线率仍 ≤ 0.1%** |

**问 2**：敏感点 + 权衡点（约 360 字）

- **敏感点 1**：**Kafka 分区数 = 100 + 按设备 ID 哈希分区**——直接决定告警下行顺序性与吞吐能力，是性能与一致性的关键决策。分区数过少则单分区热点导致延迟超标；过多则元数据膨胀。
- **敏感点 2**：**边缘节点本地 SQLite 24 小时缓冲**——直接决定断网容忍上限，是可用性目标 99.95% 的关键保障。容量不足则数据丢失。
- **敏感点 3**：**5G 专网双活（电信主、移动备）**——直接决定基地↔云端链路可用性，影响整体故障切换 < 60s 目标。
- **权衡点 1**：**国密 SM2 双向 mTLS 认证**——同时提升**安全性（+，防伪造设备）**与降低**性能（-，握手开销和 CRL 同步带来 10-30ms 额外延迟）**，权衡明显。
- **权衡点 2**：**Flink 实时流处理告警规则**——同时影响**实时性（+，规则更新即生效）**与**资源消耗（-，相比批处理多消耗 30%-50% CPU）**与**复杂度（-，状态管理与精确一次语义实现门槛高）**。

**问 3**：性能战术（约 240 字）

| 战术 | 类别 | 在本架构的落地 |
|---|---|---|
| **事件驱动 + 异步** | 减少计算路径 | Kafka 解耦云边、Flink 实时消费，告警从"轮询数据库"改为"流式触发"，延迟从秒级降至 50ms 内 |
| **就近计算** | 减少计算 | EdgeX 在边缘节点本地完成协议解析与初步过滤，仅上行有效数据，链路传输量降低 80% |
| **资源池 + 预连接** | 资源池 | MQTT Broker 维持设备长连接池，告警下发无需重新建立 TCP，节省 20-50ms 握手时间 |
| **多级缓存** | 缓存 | 边缘 SQLite + 云端 Redis 缓存设备元数据，规则匹配时无需查 PG |
| **批量与并发** | 并发 | Flink 分区并行消费 Kafka 100 个分区，整体吞吐 ≥ 20 万 TPS |

### 模拟题 3 · 证券交易系统四类点（25 分）

**【题干】**（约 720 字）

某券商核心交易系统改造项目，目标支撑 A 股、港股、美股的统一委托与撮合服务。架构师 Q 提交了如下方案，并组织 ATAM 评估。

业务约束：日均委托 **3000 万笔**，峰值委托 **10 万笔/秒**，撮合延迟 **< 1ms**（P99.9），订单**绝对不丢单**（监管硬性要求），系统年可用性 **99.999%**（业内"五个 9"），需符合**等保四级**及证监会信息安全要求。

架构关键决策：

1. **撮合引擎**采用纯内存设计，单线程顺序撮合（避免锁开销），通过 Disruptor 队列接收委托，撮合结果异步落盘；
2. **存储**：委托和成交日志同步写入**本地 NVMe SSD + 同城远程 SSD**（双写，强一致），异步复制到异地（深圳→上海）；
3. **多活**：同城双活（深圳两个机房，距离 30 公里），异地灾备（上海冷备），切换时间 < 30 秒；
4. **网络**：行情和委托链路全部使用 RoCE（RDMA over Converged Ethernet），交易所专线接入；
5. **协议**：FIX 4.4 接入券商，内部使用自研二进制协议（消息头 8 字节）；
6. **安全**：全链路国密 SM4 加密，基于硬件 SE（安全芯片）签名；终端登录采用 U-Key + 动态口令双因子；
7. **风控**：实时风控引擎前置（撮合前过滤异常委托），规则用 Drools，热更新；
8. **监控**：自研行情秒级延迟监控，超过 500μs 立即告警；故障切换由专人值守人工触发（避免误切）；
9. **审计**：所有委托和成交日志保存 **7 年**（符合证监会要求），归档至磁带库；
10. **测试**：每周一次同城切换演练，每季度一次异地切换演练。

Q 希望通过 ATAM 评估，识别该架构中影响"撮合 < 1ms"和"绝对不丢单"两个关键质量属性的架构决策。

**【小问】**（合计 25 分）

**问 1**（12 分）：从上述决策中识别 **2 个敏感点**、**2 个权衡点**、**2 个风险点**、**2 个非风险点**，每点 1.5 分（判定 1 分 + 理由 0.5 分）。

**问 2**（8 分）：针对识别出的风险点，给出**改进战术**，并说明改进后该决策属于哪一类点。

**问 3**（5 分）：题干中"故障切换由专人值守人工触发"是否合理？从**可用性 vs 可靠性**角度给出 200 字以内分析。

---

**【参考答案】**

**问 1**：四类点（约 360 字）

- **敏感点 1**：**Disruptor 单线程顺序撮合**——直接决定撮合延迟 < 1ms 的达成，是性能关键决策。改用多线程会引入锁开销，延迟必然超标。
- **敏感点 2**：**本地 + 同城 SSD 双写强一致**——直接决定"绝对不丢单"的可靠性目标，是可靠性关键决策。
- **权衡点 1**：**RoCE / RDMA 网络**——提升**性能（+，延迟降至微秒级）**但增加**成本（-，硬件投入数倍于普通以太网）**与**运维复杂度（-，需专门 RDMA 调优）**。
- **权衡点 2**：**国密 SM4 全链路加密**——提升**安全性（+，等保四级合规）**但增加**性能开销（-，加解密带来约 50-100μs 延迟）**。
- **风险点 1**：**异地复制为异步**——存在主中心整体故障时，未同步到上海的委托可能丢失，威胁"绝对不丢单"目标，且监管对此高度敏感。
- **风险点 2**：**故障切换为人工触发**——切换时间难以稳定保证 < 30 秒（人响应时间不可控），威胁可用性 99.999% 目标。
- **非风险点 1**：**FIX 4.4 协议接入券商**——业界事实标准，全球券商通用，无技术风险。
- **非风险点 2**：**审计日志保存 7 年归档磁带库**——监管明确要求且方案成熟，业内通用做法。

**问 2**：风险点改进战术（约 220 字）

| 风险点 | 改进战术 | 改进后类型 |
|---|---|---|
| **异地复制异步** | 引入"半同步复制 + 全局序列号 + 重试日志"：核心委托写入异地至少 1 个副本后再 ACK，写入超时降级为异步 + 报警；同时部署独立"丢单巡检"服务每 5 分钟比对深圳/上海序列号 GAP | 风险点 → **权衡点**（性能 ↓ 50μs，可靠性 ↑） |
| **人工切换** | 引入"智能仲裁 + 自动切换"：采用 ZooKeeper/etcd 三机房仲裁集群，主中心连续 3 秒心跳丢失自动触发切换；保留人工"降级开关"以应对网络分区误判 | 风险点 → **非风险点**（仲裁为业界成熟方案） |

**问 3**：人工切换合理性分析（约 180 字）

**结论：不合理，建议改为自动切换为主、人工降级为辅。**

理由：① 99.999% 年停机仅 5.26 分钟，留给人工响应+决策+操作的窗口太小，几乎不可能稳定达标；② 证券系统的故障切换属于**可用性维度**（系统能否快速对外恢复服务），而非"可靠性维度"（数据是否丢失），可用性目标天然要求自动化；③ 担心"误切换"是合理顾虑，但解法是**仲裁集群 + 多数决 + 切换前快照**，而非牺牲切换速度；④ 业界成熟方案（如阿里 OceanBase、蚂蚁链）均已采用自动仲裁切换，技术路径可靠。

## 2024 下半年真题 · 试题一（AI 智能平台质量属性 + Ping/Echo vs 心跳）

> 来源：2024 年 11 月 系统架构设计师案例分析 试题一（必答 25 分）
> 公开真题回忆版，仅供学习参考。

### 【题干场景】

某公司基于**大语言模型（LLM）**开发"智能问答平台"。架构师在设计阶段需识别 6 类质量属性需求，并对系统可靠性设计选用合适的故障检测策略（Ping/Echo 与心跳模式二选一）。

### 【问题 1】（6 分）从场景中识别质量属性

| 编号 | 场景描述 | 标准答案 |
|---|---|---|
| (1) | 系统需支持千万级用户并发，平均响应 < 2s | **性能（Performance）** |
| (2) | 全年可用率达到 99.99% | **可用性（Availability）** |
| (3) | 数据传输全程加密，防止泄露 | **安全性（Security）** |
| (4) | 新业务模块上线不影响现有服务 | **可修改性（Modifiability）** |
| (5) | 兼容 iOS / Android / Web 多终端 | **兼容性（Compatibility）** |
| (6) | 用户首次使用 10 分钟内可独立完成基本操作 | **易用性（Usability）** |

### 【问题 2】（10 分）Ping/Echo 与心跳模式实现原理

**Ping/Echo**：
> 监控组件**主动周期性**发送 Ping 请求 → 被监控组件回发 Echo 响应。监控组件超时未收到 Echo 即判定故障。**主动权在监控端**。

**心跳（Heartbeat）**：
> 被监控组件**主动周期性**发送一条简短心跳消息 → 监控组件在预设周期内未收到则判定故障。**主动权在被监控端**。

### 【问题 3】（9 分）为什么本系统选心跳更合适

| 维度 | 心跳优势 |
|---|---|
| **网络开销** | 单向消息，流量约为 Ping/Echo 的 1/2 |
| **监控端压力** | 被动接收，无需主动发起 N 个请求，适合千万级节点 |
| **故障识别速度** | 心跳丢失即判定，无需等待 Echo 超时往返 |
| **附带状态** | 心跳消息可携带 CPU/QPS/内存等指标，一举两得 |

### 【采分关键词】

质量属性 6 部分场景 / 主动方向 / 单向消息 / 大规模节点 / 资源利用率 / 附带状态

### 【常见扣分点】

- ❌ 把"99.99% 可用率"答成"可靠性"——可用性 vs 可靠性必区分（可用性看在线比例，可靠性看 MTBF）
- ❌ Ping/Echo 与心跳混淆主动方向——心跳必是**被监控端发起**
- ❌ 选心跳理由只说"消息少"——必须从**资源利用率、监控端压力、附带状态**等多维论证

## 2022 下半年真题 · 试题一（电商系统质量属性效用树 + OO vs 解释器风格）

> 来源：2022 年 11 月 系统架构设计师案例分析 试题一
> 公开真题回忆版，仅供学习参考。

### 【题干场景】

某电子商务公司升级**会员与促销管理系统**，目标提升灵活性并提供个性化服务。关键需求：
- 管理员可在页面上**灵活设置折扣规则和促销活动逻辑**，设置后即生效
- 系统响应时间 **< 0.3 秒**
- 支持**横向存储扩展**、**故障自动热备份**

架构师争议采用 **面向对象（OO）** 还是 **解释器** 架构风格。

### 【问题 1】（12 分）完善质量属性效用树

| 质量属性 | 子属性 | 场景描述 |
|---|---|---|
| **可修改性** | 折扣规则可修改 | 管理员页面修改折扣规则后立即生效，无需重新部署 |
| **可修改性** | 个性化策略灵活定义 | 支持任意维度（用户/商品/地理/时间）自定义促销逻辑 |
| **性能** | 响应时间 | 高峰期商品页响应时间 < 0.3 秒 |
| **性能** | 高并发支撑 | 大促 QPS 峰值 5 万 |
| **可用性** | 故障热备份 | 自动检测节点故障并切换备机 |
| **可扩展性** | 横向存储扩展 | 数据增长可线性扩存储节点 |

### 【问题 2】（13 分）面向对象 vs 解释器 三维度对比

| 维度 | 面向对象（OO） | 解释器 | 结论 |
|---|---|---|---|
| **可修改性** | 一般（修改规则需改类、重新编译部署） | **好**（编写新规则文件 + 导入资源/外部配置即可） | **解释器更优** |
| **灵活性** | 一般（规则受类设计约束） | **好**（DSL 语法灵活定义规则表达式） | **解释器更优** |
| **性能** | **好**（编译后直接执行 + JIT 优化） | 差（解释执行有 N 倍开销） | OO 更优 |

**最终建议**：**推荐解释器风格**

**理由**：本场景**可修改性 + 灵活性 > 性能**——业务对"运营可灵活配规则"的诉求高于绝对性能（0.3 秒响应可通过缓存 + 索引优化达成，规则解释开销是次要矛盾）。

### 【采分关键词】

效用树 / 可修改性 / 灵活性 / 解释器风格 / DSL / 外部配置 / 业务诉求权衡

### 【常见扣分点】

- ❌ 选 OO 不分析"业务侧灵活性需求"——丢失场景对齐
- ❌ 性能维度答"OO 性能差"——错，OO 是编译执行，比解释器快
- ❌ 效用树只列质量属性不列具体场景——必须三层（属性 → 子属性 → 场景）
