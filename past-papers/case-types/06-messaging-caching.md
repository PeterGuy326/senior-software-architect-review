# 案例题型 06 · 消息中间件 / 缓存应用

> 高频题型，近 5 年出现多次，25 分。

## 考点分布

- 消息队列**选型对比**（Kafka / RabbitMQ / RocketMQ）
- 保证**可靠性**（不丢、不重、顺序）
- 缓存**三大问题**（穿透、击穿、雪崩）
- 缓存一致性
- 热点 Key / 大 Key 问题

## 消息队列对比（必背）

| 维度 | Kafka | RabbitMQ | RocketMQ | Pulsar |
|---|---|---|---|---|
| 吞吐 | **百万级** | 万级 | 十万级 | 百万级 |
| 时延 | ms 级 | **μs 级** | ms 级 | ms 级 |
| 可靠 | 高（副本） | 高 | **金融级** | 高 |
| 功能 | 流式为主 | **协议丰富**（AMQP） | 事务消息 / 顺序 | 存算分离 |
| 语言 | Scala | Erlang | Java | Java |
| 适用 | 日志 / 大数据 | 业务消息 | **金融交易** | 云原生 |

## 消息可靠性三要素

### 1. 不丢消息

- **生产端**：同步发送 + 确认 ACK + 重试
- **Broker**：**多副本 + 持久化**（Kafka min.insync.replicas ≥ 2）
- **消费端**：**手动 ACK**，处理成功后再提交 offset

### 2. 不重复消费

- **幂等**：业务去重（唯一键 / Redis setnx / 状态机）
- **消费端去重表**

### 3. 顺序消息

- **全局顺序**：单分区（吞吐低）
- **局部顺序**：按业务主键 hash 到同一分区（推荐）

## 缓存三大问题（必背）

### 1. 缓存穿透（**不存在的数据**）

- **布隆过滤器**（Bloom Filter）
- **缓存空值**（短 TTL）

### 2. 缓存击穿（**热点过期瞬间**）

- **互斥锁**（Redis setnx）
- **永不过期** + 异步更新
- **预热**

### 3. 缓存雪崩（**大量同时过期**）

- **过期时间加随机**（TTL + rand）
- **多级缓存**（本地 Caffeine + Redis）
- **熔断降级**

## 缓存一致性（Cache Aside 模式）

**推荐：先更新 DB，再删除缓存**

| 方案 | 问题 |
|---|---|
| 先删缓存再更 DB | 并发下读请求会把旧值写回缓存 |
| **先更 DB 再删缓存** ✅ | 极小窗口期可能读到旧值（可接受） |
| 延迟双删 | 更新前删 + sleep + 再删 |
| 订阅 binlog | Canal 监听变更异步失效缓存（**强一致方案**） |

## 答题模板

### 问题 1：消息队列选型

**标准回答**：
> 本系统为**金融支付**场景，要求：
> - **不丢消息**（金融级可靠）
> - 十万级 TPS
> - 事务消息、顺序消息
>
> 综合对比，选 **RocketMQ**：
> - 同步双写 + **SYNC_MASTER** 零丢失
> - 内建**事务消息**支持半消息回查
> - 阿里生产级验证

### 问题 2：可靠性设计

**模板三段式**：
> - 生产端：**同步发送 + confirm + 失败重试 3 次**
> - Broker：**主从同步复制 + 持久化**
> - 消费端：**手动 ACK + 本地幂等表**
> 实现 **at-least-once + 业务幂等 = 有且仅一次**的效果。

### 问题 3：缓存方案设计

**模板**：
```
1. 读：Cache Aside，缓存命中直接返回，未命中回源 DB 后写缓存
2. 写：先更新 DB，再删除缓存
3. 防穿透：布隆过滤器前置
4. 防击穿：热点 Key 永不过期 + 异步刷新
5. 防雪崩：TTL = base + random(0, 300s)
6. 最终一致：Canal 监听 binlog 兜底失效缓存
```

## 万能高分句

- "选型 **RocketMQ**，同步双写 + 手动 ACK + 本地幂等表实现 **exactly-once**"
- "通过 **布隆过滤器 + 缓存空值** 两级防穿透，将数据库压力降低 **99%**"
- "热点 Key **永不过期 + 异步刷新**，避免击穿瞬间数据库雪崩"
- "缓存一致性采用 **Cache Aside（先更 DB 后删缓存）**，辅以 **Canal 监听 binlog** 兜底"

## 常见陷阱

| ❌ | ✅ |
|---|---|
| 选型不给理由 | 必须对比 **2–3 种** 说明差异 |
| 只说不丢 | **不丢、不重、顺序**三要素都要讲 |
| 穿透击穿混淆 | **穿透 = 不存在**；**击穿 = 热点过期** |
| 先删缓存再更 DB | **推荐反过来**（并发安全） |
| 无多级缓存 | 加 **本地 + 分布式** 两级 |

### 模拟题 1 · 双 11 秒杀 Cache Aside 与三大缓存问题（25 分）

**【题干】**（约 820 字）

某综合电商平台正在筹备 2024 年双 11 大促，业务部门策划了"**整点秒杀**"活动：每天 10:00、14:00、20:00 各开放 3 场，每场上架 SKU 200 个，单 SKU 库存 100~5000 件不等，活动持续 5 分钟。架构师 H 牵头改造商品详情与下单链路，团队规模 25 人，开发周期 10 个月。

业务关键指标：秒杀峰值 **QPS 5 万**（瞬时可冲到 8 万），下单接口 **P99 < 200ms**，全年可用性 **99.99%**，单日活跃用户 **8000 万**，热点商品访问占比 **80% 集中在 20 个 SKU**。MySQL 订单库主从架构（一主两从），单库 QPS 上限约 **8000**，远低于秒杀峰值。

H 提交的缓存方案核心决策如下：

1. **缓存架构**：Caffeine 本地缓存（L1，容量 10 万 Key，过期 30s）+ Redis Cluster（L2，6 主 6 从，单分片 10 万 QPS）+ MySQL（L3）三级结构；
2. **读路径**：采用 **Cache Aside 模式**——先查 L1，未命中查 L2，未命中回源 MySQL，回写 L2 后再回写 L1；
3. **写路径**：先更新 MySQL，再删除 L2，本地 L1 通过订阅 Redis Pub/Sub 通知失效；
4. **TTL 策略**：商品详情 TTL = 600s + random(0, 300s)，秒杀活动期间热点 SKU 设为"逻辑过期 + 异步刷新"；
5. **库存扣减**：Redis 原子 Lua 脚本预扣 + RocketMQ 异步落库，超卖检查由 Lua 内置；
6. **限流降级**：Sentinel 网关层按用户 + IP + 接口三维度限流，下单 5 QPS/用户；
7. **监控**：Prometheus 采集缓存命中率（目标 ≥ 95%）、Redis 大 Key（> 10KB 告警）、Redis 慢查询（> 5ms 告警）。

H 在评审中遇到三类质疑：① 黑产用不存在的 SKU ID 刷接口怎么办（**穿透**）；② 整点开抢瞬间热点 Key 集中失效怎么办（**击穿**）；③ 大量商品 TTL 同一时刻到期怎么办（**雪崩**）。

**【参考答案】**

**问 1**：Cache Aside 流程（约 200 字）

```
读路径（Read-Through 风格 Cache Aside）：
  client → 查 L1（Caffeine）
       命中 → 直接返回
       未命中 → 查 L2（Redis）
              命中 → 写回 L1（TTL 30s）→ 返回
              未命中 → 加分布式锁（防并发回源）→ 查 MySQL
                     → 写回 L2（TTL 600+rand(0,300)s）→ 写回 L1 → 返回

写路径（先 DB 后 Cache）：
  client → UPDATE MySQL
        → DEL Redis L2 Key
        → publish "invalidate:{key}" 到 Redis Pub/Sub
        → 各应用节点订阅消息，DEL 本地 Caffeine L1 Key
```

**为何"先更 DB 再删缓存"优于反向**：① 反向（先删缓存）方案下，并发读请求在"删缓存→更新 DB"窗口内会**用旧值回写缓存**，造成长期脏数据；② 正向方案下脏数据窗口仅为"更 DB 完成→删缓存完成"间的 ms 级时间窗，且后续任何读请求会立即修正；③ 写后失效语义清晰，工程实现简单（无需协调读锁）。

**问 2**：三大缓存问题解法（约 380 字）

| 问题 | 现象 | 解法 1（本架构落地） | 解法 2（本架构落地） |
|---|---|---|---|
| **穿透** | 查不存在的 SKU ID（黑产攻击） | **布隆过滤器**：启动时把全量 SKU ID 加载入 RedisBloom（误判率 0.1%，约 10MB 内存），查询前先过滤 | **缓存空值**：MySQL 未查到的 Key 写回 `NULL` 占位，TTL 60s + rand(0,30)s，避免每次都打 DB |
| **击穿** | 单热点 Key 在过期瞬间被并发请求击穿到 DB | **互斥锁**：Redis SETNX `lock:{sku_id}` 30s，只允许 1 个线程回源，其他线程 sleep 50ms 后重试 L2 | **逻辑过期 + 异步刷新**：热点 SKU 不设物理 TTL，value 内嵌 `expire_at` 字段；查询发现已逻辑过期则提交异步任务刷新，旧值继续返回（最终一致） |
| **雪崩** | 大量 Key 同时过期或 Redis 集群整体故障 | **TTL 打散**：基础 TTL=600s + random(0,300)s，避免整点同时失效 | **多级缓存 + 熔断降级**：L1 本地缓存挡住 50% 流量；Sentinel 配置 Redis 异常率 > 30% 时熔断，降级为本地 + DB 直连 + 降级页 |

**补充落地参数**：
- 布隆过滤器更新策略：每日凌晨全量重建 + Canal 监听 SKU 表增量；
- 锁超时兜底：互斥锁必须设置 TTL（30s）防死锁，回源失败要主动 DEL 锁；
- 雪崩二级保护：Redis 集群本身做 6 主 6 从 + 跨可用区，单可用区故障可自动切换。

**问 3**：热点 Key 治理（约 180 字）

1. **本地缓存 L1（Caffeine）兜住热点**：80% 流量在 20 个 Key 上 → L1 命中率可达 95%+，单节点本地命中无 Redis 网络开销，相当于把热点流量从 Redis 卸载到应用进程内存。
2. **热点 Key 多副本（Hot Key 拆分）**：把 `sku:{id}` 拆为 `sku:{id}:0` ~ `sku:{id}:N`（N=10），客户端按随机 hash 选副本，把单分片压力拆到 N 个分片，单分片 QPS 从 10 万降至 1 万。
3. **热点探测 + 自动迁移**：JD-HotKey / Sentinel HotKey 实时统计 Top-K 热点，秒级推送给应用层强制写入本地缓存，TTL 5s。
4. **读多写少场景考虑只读副本**：Redis Cluster 配置 `readonly` 模式，slot 内读请求由从节点分担。

**问 4**：脏数据并发场景与兜底（约 130 字）

**脏数据窗口**：T1 时刻读请求 R 查 L2 未命中，回源读到 V_old；同时 T2 时刻写请求 W 更 DB 为 V_new 并 DEL L2；T3 时刻 R 把 V_old 写回 L2——此后所有读请求都拿到 V_old，直到下一次失效。

**Canal 兜底方案**：
- 部署 Canal 监听 MySQL binlog，订阅 `sku` 表的 UPDATE/DELETE 事件；
- Canal 解析 binlog 后向 RocketMQ `cache_invalidate_topic` 投递失效消息；
- 各应用节点消费消息执行 `DEL L2 Key + publish L1 失效`，实现**最终一致**且**无侵入业务代码**；
- 延迟约 100~500ms，可接受。

### 模拟题 2 · 订单事件 RocketMQ 顺序消息与幂等设计（25 分）

**【题干】**（约 780 字）

某 SaaS 化餐饮订单中台为连锁餐饮品牌（覆盖 1.2 万家门店）提供统一订单服务。架构师 D 主导建设订单事件总线，将订单状态变更（下单/支付/出餐/送达/评价/退款）以事件形式广播给：财务结算、库存扣减、积分发放、骑手调度、数据分析 6 个下游服务。

业务约束：日均订单 **600 万笔**、峰值 QPS **3 万**（午晚餐高峰）、状态变更事件量约 **3000 万/日**、端到端延迟 **< 500ms**、年可用性 **99.99%**、**绝对不可乱序**（出餐事件不可早于支付事件被消费，否则财务对不上账）、**绝对不可丢失**（监管要求）、**绝对不可重复处理**（重复扣库存=超卖）。团队规模 18 人，周期 8 个月。

D 提交方案核心决策：

1. **MQ 选型**：RocketMQ 5.x 集群（4 主 4 从，SYNC_MASTER 同步双写，磁盘 RAID10 + 持久化），相比 Kafka 选择理由是顺序消息和事务消息支持更成熟；
2. **顺序保证**：以 `order_id` 作为 Sharding Key，使用 `MessageQueueSelector` 把同一订单的所有事件路由到同一队列；
3. **生产端**：同步发送 + 失败重试 3 次（指数退避 1s/2s/4s），重试仍失败写入本地 `failed_msg` 表 + 监控告警；
4. **事务消息**：下单成功事件采用 RocketMQ 事务消息（half message + 回查），保证 DB 写入与 MQ 投递最终一致；
5. **消费端**：手动 ACK，业务处理 + 提交 offset 在同一本地事务中（消息表去重模式）；
6. **幂等机制**：基于消息表 `idempotent_log(msg_id, biz_key, status)` UNIQUE INDEX(`biz_key`)，重复消息直接跳过；
7. **死信队列**：消费失败 16 次后转入 DLQ，由人工运维介入；
8. **监控**：消费堆积 > 1 万告警，消费 RT P99 > 200ms 告警。

**【参考答案】**

**问 1**：顺序消息原理（约 220 字）

**RocketMQ 顺序消息原理**：
1. RocketMQ Topic 由多个 MessageQueue（默认 4 个）组成，每个 Queue 内消息**严格 FIFO**；
2. 生产端通过 `MessageQueueSelector` 把同一业务键的消息**固定路由到同一 Queue**（`hash(order_id) % queue_size`）；
3. 消费端使用 `MessageListenerOrderly`，单个 Queue 由**单个消费线程串行消费**（broker 端会对 Queue 加分布式锁，避免多消费者并发拉取）；
4. 三层保障——生产路由一致 + Broker 内 FIFO + 消费单线程，实现**Queue 内严格有序**。

**为何不能保证全局顺序**：不同 `order_id` hash 后路由到不同 Queue，跨 Queue 之间无顺序关系。如需全局顺序只能 `queue_size=1`，但吞吐降至单 Queue 上限（< 1 万 TPS），不可行。**业务上"同订单内事件有序"已足够**，跨订单事件本就无依赖关系。

**问 2**：消息不丢失三端保障（约 320 字）

| 阶段 | 保障措施 | 本架构落地 |
|---|---|---|
| **生产端** | ① 同步发送（waitStoreMsgOK = true） | 同步发送，等待 Broker SYNC_MASTER 双写 ACK 后返回 |
| | ② 失败重试 + 本地兜底 | 重试 3 次（1s/2s/4s 指数退避），仍失败写 `failed_msg` 表 + 钉钉告警 |
| | ③ 事务消息 | 下单事件用 half message + 回查，保证 DB 与 MQ 一致 |
| **Broker** | ① 同步双写（SYNC_MASTER） | 4 主 4 从同机房 SSD，主写完同步从节点 ACK 后返回生产端 |
| | ② 同步刷盘（SYNC_FLUSH） | 关键 Topic 配置同步刷盘，避免 OS Cache 丢失（牺牲 5-10ms 性能） |
| | ③ 多副本 + 跨可用区 | 4 主分布在 2 个可用区，单可用区故障不影响数据 |
| **消费端** | ① 手动 ACK | `MessageListenerOrderly#consumeMessage` 返回 SUCCESS 才提交 offset |
| | ② 本地事务一致 | 业务处理 + 写 `idempotent_log` + 提交 offset 在同一 MySQL 事务 |
| | ③ 失败重试 + DLQ | 消费失败本地重试 16 次，仍失败转 DLQ，避免阻塞 Queue |

整体语义为 **at-least-once + 业务幂等 = exactly-once 效果**。

**问 3**：幂等设计必要性与方案对比（约 180 字）

**为何必须**：① RocketMQ 仅承诺 at-least-once，网络抖动 / Broker 重投 / 消费 ACK 丢失都会导致重复投递；② 业务上重复扣库存=超卖、重复扣款=客诉、重复发积分=资损，每一条都是 P0 故障。

| 方案 | 实现 | 优点 | 缺点 |
|---|---|---|---|
| **业务状态机** | 订单状态从 `PAID` → `COOKING` 只允许单向流转，重复触发自动忽略 | 与业务天然契合，无额外存储 | 复杂业务难穷举所有状态转移 |
| **存储层去重表** ✅ | `idempotent_log(msg_id, biz_key, status)` UNIQUE(`biz_key`)，处理前先 INSERT，冲突即跳过 | 通用、强一致、可审计 | 需写表，10-20ms 额外开销 |
| **Redis 去重** | `SETNX dedup:{msg_id} 1 EX 86400` | 快（< 2ms） | Redis 故障会失效，弱一致 |

**本架构选型**：去重表 + 业务事务原子提交，金融级强一致优先，幂等 SLA 100%。

**问 4**：DLQ 处理（约 90 字）

**进入 DLQ 条件**：消费失败 16 次（默认配置），通常对应：① 消息体格式异常（非常 bug）、② 下游强依赖故障（DB/Redis 连续宕机）、③ 业务逻辑死循环。

**恢复流程**：① 监控告警通知 SRE；② 人工排查 DLQ 中具体消息和异常栈；③ 修复 bug 后通过运维平台**重投回原 Topic**或**手动调用补偿接口**；④ 复盘根因写入 SOP，避免下次重复进 DLQ。

| 得分项 | 分值 | 关键词/要求 |
|---|---|---|
| 顺序消息三层保障 | 4 分 | 生产路由 / Broker FIFO / 消费单线程，缺一扣 1 分 |
| MessageQueueSelector + Sharding Key 机制 | 2 分 | 必须说 hash(order_id) % queue_size |
| 全局顺序限制原因 | 2 分 | 必须说不同 Queue 之间无序 |
| 三端各 2 条以上保障 | 6 分 | 每端 2 分；缺端扣 2 分 |
| 配置含具体参数（SYNC_MASTER/同步刷盘/重试次数） | 3 分 | 没参数扣 1 分/项 |
| 幂等必要性含 at-least-once 论证 | 2 分 | 没说 RocketMQ 语义扣 1 分 |

| 选型理由扣金融场景 | 1 分 | 必须说强一致 |
| DLQ 触发条件 + 恢复流程 | 3 分 | 缺一扣 1 分 |

**常见扣分点**：
- ❌ 顺序消息答"全局顺序"——错，RocketMQ 只保 Queue 内顺序
- ❌ 不丢消息只答 Broker 副本——三端都要答
- ❌ 幂等用"消费前查 DB 是否处理过"——并发下两个消费者同时查到未处理，仍会重复，必须 UNIQUE INDEX
- ❌ 答 SYNC_FLUSH 不区分异步刷盘——同步刷盘性能损失要量化（5-10ms）

**高分技巧**：
- 提到 **at-least-once + 业务幂等 = exactly-once** 这条经典论述
- 死信队列说"DLQ 消息也要监控告警，避免静默堆积"
- 量化对比：同步刷盘 vs 异步刷盘 RT 差异 / Redis 去重 vs 表去重延迟差异

### 模拟题 3 · Kafka / RabbitMQ / RocketMQ 选型对比（25 分）

**【题干】**（约 750 字）

某综合性互联网集团旗下有 4 类业务，IT 治理委员会希望建立**统一消息中间件标准**以降低运维成本，由架构师 P 主导技术选型论证。4 类业务画像：

**业务 A · 用户行为日志采集**：日均 **800 亿条**埋点（点击、曝光、播放）、峰值 **300 万条/秒**、容忍 **0.01% 丢失率**、消费方为离线数仓 Hive 和实时数仓 Flink；不要求顺序、不要求事务，**只要求超高吞吐**。

**业务 B · 在线支付/账务**：日均 **8000 万笔**支付事件、峰值 **2 万 TPS**、**绝对不丢、绝对不重、严格顺序**（账户级），需要**事务消息**与 DB 写入一致，受**等保三级**与**金融监管**约束。

**业务 C · 业务工作流通知**：HR/OA/CRM 等内部系统的 **百万级/日** 业务事件，多种路由模式（fanout、direct、topic）、**消息体复杂**（XML/JSON 混合）、客户端语言异构（Java/Python/.NET）、**延迟消息**（超时提醒）需求强。

**业务 D · IoT 设备遥测**：500 万台设备每 30 秒上报 1 次、约 **15 万 TPS**、**MQTT 协议**接入、需要**云原生弹性扩缩**与**多租户隔离**。

候选 MQ 包括：**Kafka 3.x、RabbitMQ 3.12、RocketMQ 5.x、Pulsar 3.x**。集团约束：① 优先国产/开源；② 团队主力语言 Java；③ 容器化部署；④ 总 TCO 越低越好。

**【小问】**（合计 25 分）

**【参考答案】**

**问 1**：四种 MQ 多维对比（约 280 字）

| 维度 | **Kafka** | **RabbitMQ** | **RocketMQ** | **Pulsar** |
|---|---|---|---|---|
| **吞吐** | 百万级 TPS（最强） | 万级 TPS | 十万级 TPS | 百万级 TPS |
| **延迟** | ms 级（5-10ms） | μs~ms 级（最低） | ms 级（5-10ms） | ms 级 |
| **顺序** | 分区内有序 | 队列内有序 | Queue 内有序 + 顺序消息 API | 分区内有序 |
| **事务消息** | 弱（仅生产事务） | 不支持 | **支持**（half message + 回查） | 支持 |
| **副本一致性** | ISR 半同步 | 镜像队列（性能差） | SYNC_MASTER 同步双写 | BookKeeper 多副本（存算分离） |
| **协议** | 自有二进制 | **AMQP 0-9-1**（功能最全） | 自有 + 部分 OpenMessaging | 自有 + Kafka 兼容 + MQTT |
| **运维成本** | 中（依赖 ZK，3.x 后 KRaft） | 低（单机即用，集群难） | 中（依赖 NameServer） | 高（依赖 BK + ZK，组件多） |
| **适用** | 日志/大数据 | 业务消息/复杂路由 | 金融/电商/事务 | 云原生/多租户 |

**核心定位**：
- **Kafka** = "**日志型大吞吐管道**"，为流计算和数据湖优化
- **RabbitMQ** = "**业务消息瑞士军刀**"，AMQP 协议丰富，路由灵活但吞吐弱
- **RocketMQ** = "**金融级业务消息**"，阿里电商验证，事务/顺序/延迟原生支持
- **Pulsar** = "**云原生新一代**"，存算分离适合多租户大规模

**问 2**：四类业务选型（约 360 字）

**业务 A · 行为日志 → Kafka**
- 业务匹配：300 万 TPS 远超 RabbitMQ/RocketMQ 单集群上限，Kafka 百万级吞吐 + 顺序写盘机制契合超高吞吐场景；与 Flink/Spark 集成最成熟。
- 淘汰对比：RabbitMQ 万级吞吐直接出局；RocketMQ 十万级要部署 30+ 集群，运维成本爆炸；Pulsar 吞吐够但运维复杂度过高，且团队没有 BookKeeper 经验。

**业务 B · 支付/账务 → RocketMQ**
- 业务匹配：事务消息原生支持（half message + 回查机制），SYNC_MASTER 同步双写满足"绝对不丢"，顺序消息 API 满足账户级有序；阿里金融场景 10+ 年验证，等保三级合规案例丰富。
- 淘汰对比：Kafka 无原生事务消息（生产事务仅保证 producer 端）；RabbitMQ 镜像队列性能差且不支持事务；Pulsar 事务消息成熟度不足。

**业务 C · 业务工作流 → RabbitMQ**
- 业务匹配：AMQP 协议支持 fanout/direct/topic/headers 四种路由模式，原生支持死信队列做延迟消息（DLX + TTL），多语言客户端最成熟（Java/Python/.NET/Go 全覆盖），百万级/日吞吐绰绰有余。
- 淘汰对比：Kafka 路由模式单一（仅 partition）；RocketMQ 路由能力弱于 AMQP；Pulsar 协议复杂，学习成本高。

**业务 D · IoT 遥测 → Pulsar**
- 业务匹配：原生支持 MQTT 协议适配，存算分离架构天然支持多租户隔离（500 万设备分租户），云原生 K8s Operator 成熟，弹性扩缩符合 IoT 业务波动特性。
- 淘汰对比：Kafka 无 MQTT 原生支持需额外网关；RocketMQ 多租户能力弱；RabbitMQ 15 万 TPS 已超能力上限。

**问 3**：收敛路线图（约 180 字）

**收敛策略**：长期统一到 **Kafka（数据流） + RocketMQ（业务流）**双 MQ 体系。

**为何不能"一统"**：① **吞吐量级差**——日志 300 万 TPS 与支付 2 万 TPS 共集群会互相干扰，资源隔离差；② **可靠性级差**——日志容忍 0.01% 丢失追求性能（异步刷盘），支付绝对不丢必须同步刷盘，配置矛盾；③ **协议生态差**——MQTT/AMQP 各有原生集群更高效。

**3 阶段路线图**：
- **第 1 年**：业务 A 迁 Kafka，业务 B 迁 RocketMQ（已有），业务 C 暂留 RabbitMQ，业务 D 暂留 EMQX；
- **第 2 年**：业务 C 评估迁 RocketMQ（用 Tag + 延迟消息替代 AMQP topic 路由），逐步淘汰 RabbitMQ；
- **第 3 年**：业务 D IoT 网关层用 EMQX，下游统一接 Kafka，淘汰独立 Pulsar；最终保留 Kafka + RocketMQ 双中台。

## 2024 下半年真题 · 试题二（Cache-Aside 缓存一致性）

> 来源：2024 年 11 月 系统架构设计师案例分析 试题二
> 公开真题回忆版，仅供学习参考。

### 【题干场景】

某购物网站采用 **Cache-Aside（缓存 + 数据库）双存储**模式，应对高并发商品访问。架构师需设计读写流程并解决并发一致性问题。

### 【问题 1】（8 分）数据读取流程

```
1. 客户端请求 → 应用程序向缓存查询
2. 缓存命中 → 直接返回数据
3. 缓存未命中 → 应用程序查询数据库
4. 将 DB 查到的数据写入缓存
5. 返回数据给客户端
```

### 【问题 2】（4 分）数据更新流程

```
1. 应用程序更新数据库
2. 应用程序删除（而非更新）缓存中对应数据
```

**为什么是删而不是更新缓存？**
1. 避免**计算成本浪费**（重新计算后又被覆盖）
2. 防止**并发写场景下脏数据**（A 写后 B 写，缓存被旧值覆盖）
3. 下次读自然回填，保证**新鲜度**

### 【问题 3】（13 分）并发一致性问题与解决方案

**根因**（4 分）：
> 缓存与数据库是**两个独立存储**，更新操作**非原子**。并发读写时，A 线程读到旧值并准备写缓存时，B 线程同时完成"写库 + 删缓存"，A 把旧值写回缓存 → 缓存与数据库不一致。

**解决方案**（9 分，列举 ≥ 4 种）：

| 方案 | 原理 | 适用 |
|---|---|---|
| **延时双删** | 先删缓存 → 写库 → 休眠 500ms → 再删缓存 | 通用首选 |
| **分布式锁** | 写操作加锁，读写互斥 | 强一致场景 |
| **Binlog 订阅（Canal）** | 监听 MySQL binlog 异步删缓存 | 解耦最佳 |
| **MQ 异步** | 写库后发 MQ，消费者删缓存 | 高并发解耦 |
| **缓存短过期** | 设置短 TTL，最终一致 | 低成本兜底 |
| **触发器** | DB 触发器调用删缓存接口 | 已淘汰，性能差 |

### 【采分关键词】

Cache-Aside / 删缓存非更新 / 非原子操作 / 延时双删 / Canal binlog / 最终一致

### 【常见扣分点】

- ❌ 写流程答"先删缓存→写库"——标准 Cache-Aside 是**先写库→后删缓存**
- ❌ 写流程答"写库 + 更新缓存"——必须是**删**，不是**更新**
- ❌ 一致性方案只答"加锁"——必须给出 ≥ 4 种解法体现思路广

## 2024 上半年真题 · 试题五（Web 综合：技术匹配 + 缓存雪崩 + 读写分离）

> 来源：2024 年 5 月 系统架构设计师案例分析 试题五
> 归位说明：本题为 Web 架构综合题，因缓存雪崩为最 distinctive 考点归此；读写分离部分可与 [02-database-design.md](./02-database-design.md) 关联学习。

### 【题干场景】

某 B2C 电商平台日活 500 万，需设计高可用 Web 架构。架构师需匹配技术与软件、设计缓存雪崩对策、说明读写分离方案。

### 【问题 1】（5 分）技术与软件对应

| 技术分类 | 代表软件 |
|---|---|
| **负载均衡** | HAProxy / Nginx / LVS / F5 |
| **缓存服务器** | Squid / Varnish / Redis / Memcached |
| **分布式文件系统** | FastDFS / HDFS / Ceph / MinIO |
| **Web 应用服务器** | Tomcat / Jetty / WildFly / WebLogic |
| **NoSQL 数据库** | MongoDB / Redis / Cassandra / HBase |

### 【问题 2】（10 分）缓存雪崩 6 大对策

| 对策 | 实现 |
|---|---|
| **错开过期时间** | `expire = 3600 + random(0, 600)`，避免同时失效 |
| **多级缓存** | 本地（Caffeine）+ 分布式（Redis），单层失效不影响整体 |
| **集群高可用** | Redis Sentinel / Cluster 防缓存服务挂掉 |
| **限流降级** | Sentinel 限流 + 兜底返回默认值 |
| **数据预热** | 启动 / 大促前预加载热点数据 |
| **热点永不过期** | 核心数据不设 TTL，后台异步更新 |

### 【问题 3】（10 分）B2C 读写分离架构

```
                ┌──────── 主库（写）─────────┐
   Web/APP ──── ┤                            │
                └── binlog ──┬→ 从库 1（读） │
                             ├→ 从库 2（读） │
                             └→ 从库 3（读） │
```

**采用理由**：
1. **读远多于写**：B2C 读写比通常 9:1，甚至 99:1
2. **横向扩展读性能**：加从库即可线性扩展
3. **主库专注写入**：CPU/IO 不被读拖累
4. **故障隔离**：从库挂不影响写入

**面临问题与解决**：

| 问题 | 解决 |
|---|---|
| **主从延迟** | 半同步复制 / 关键读走主库 / 缓存兜底 |
| **数据一致性** | 半同步 + 监控延迟告警 |
| **路由复杂度** | ShardingSphere / MyCAT 中间件代理 |

### 【采分关键词】
