# 案例题型 08 · 嵌入式 / 构件组装

> 中频题型，约 2–3 年一次，25 分。

## 考点分布

- 嵌入式**实时系统**设计
- **构件**（Component）识别、接口契约
- 嵌入式软件架构风格（分层、事件驱动、任务调度）
- 实时调度算法（RM / EDF）
- 与硬件的接口设计

## 嵌入式核心理论

### 嵌入式软件分类

| 类型 | 特点 | 例子 |
|---|---|---|
| **硬实时** | 违反时限 = 系统失败 | 航天、汽车 ABS |
| **软实时** | 违反时限 = 降级 | 音视频、IoT |
| **弱实时** | 不严格 | 家电 |

### 嵌入式架构风格

1. **分层架构**：硬件抽象层 HAL → 驱动 → 中间件 → 应用
2. **事件驱动**：中断 + 事件循环
3. **任务调度**：RTOS 多任务 + 优先级
4. **管道-过滤器**：信号处理链

### 实时调度算法

| 算法 | 特点 |
|---|---|
| **RMS**（Rate Monotonic） | 频率越高优先级越高，**静态** |
| **EDF**（Earliest Deadline First） | 截止期最近优先，**动态** |
| **DMS** | 截止期越短优先级越高 |

### 可调度判定

- **RMS**：Σ(Ci/Ti) ≤ n(2^(1/n) - 1)，n→∞ 时极限 **0.693**
- **EDF**：Σ(Ci/Ti) ≤ 1（利用率满 100% 可达）

## 构件化核心理论

### 构件要素

- **接口契约**（Interface）
- **独立部署**
- **无持久状态**（或明示）
- **可组装**

### 主流标准

- **CORBA**（跨语言）
- **COM/DCOM**（微软）
- **EJB**（Java EE）
- **OSGi**（模块化 Java，支持热插拔）

### 构件复用层次

1. 代码复用（库）
2. 设计复用（模式）
3. 分析复用（领域模型）
4. 架构复用（参考架构）

## 答题模板

### 问题 1：嵌入式架构设计

**模板**：
```
1. 分层：HAL → BSP → RTOS → 中间件 → 应用
2. 调度：FreeRTOS / μC/OS，RMS 静态优先级
3. 通信：消息队列 / 信号量 / 共享内存
4. 实时保证：中断响应 < 10μs，关键任务周期 10ms
5. 可靠性：看门狗 WDT + 双机热备
```

### 问题 2：可调度分析

**套路**：
```
给定任务周期 Ti 和执行时间 Ci：
1. 计算 U = Σ(Ci/Ti)
2. 对比 RMS 上界 n(2^(1/n)-1)
3. U ≤ 上界 → 可调度；否则必须用 EDF 或优化
```

### 问题 3：构件识别与组装

**套路**：
1. 识别可复用单元（UI / 通信 / 数据处理 / 算法）
2. 定义接口契约（如 OpenAPI / proto）
3. 组装：依赖注入 / IoC 容器
4. 版本管理：语义化版本

### 问题 4：嵌入式 + 物联网

**模板**：
```
端（MCU + RTOS）→ 边（网关 Gateway）→ 云（IoT 平台）
- 端：分层 + 事件驱动
- 边：数据过滤 + 协议转换（MQTT / CoAP）
- 云：设备管理 + 规则引擎 + 大数据
```

## 万能高分句

- "采用**分层架构**：**HAL → BSP → RTOS（FreeRTOS）→ 中间件 → 应用**，实现**硬件解耦**与**可移植**"
- "关键任务使用 **RMS 静态优先级**调度，经可调度性分析 **U = 0.65 < 0.693**，满足实时约束"
- "通过**看门狗 WDT**  + **双机冷备 / 热备**保障 **99.999%** 可用"
- "构件接口以 **OpenAPI** 契约先行，通过 **OSGi** 支持运行时**热插拔**"

## 常见陷阱

| ❌ | ✅ |
|---|---|
| 不区分硬实时/软实时 | 题干要看清**失败后果** |
| 可调度分析没计算 | **列出公式 + 代入数字** |
| 构件 = 类 | 构件是**可独立部署**的单元 |
| 忽视硬件 | 嵌入式必须讲 **HAL / BSP / 中断** |
| 无可靠性手段 | **看门狗 / 双机 / ECC** 必写 |

### 模拟题 1 · 车载网关实时调度 RMS / EDF 可调度性分析（25 分）

**【题干】**（约 800 字）

某新能源汽车 OEM 厂商研发新一代**中央域控制器（HPC）**，整合原车身、底盘、动力、ADAS、信息娱乐 5 个独立 ECU 为单一域控架构，由架构师 K 主导嵌入式实时软件设计。芯片选型为 **NXP S32G3（Cortex-A53 ×4 + Cortex-M7 ×3）**，主频 1.0 GHz，运行 **AUTOSAR Adaptive + Classic** 双内核（A 核跑 Adaptive AUTOSAR，M 核跑 Classic AUTOSAR + FreeRTOS），符合 **ISO 26262 ASIL-D** 功能安全等级。

业务约束：
- 整车通信总线：CAN-FD（500kbps）+ Ethernet（100Mbps，TSN 时间敏感网络）；
- 关键控制周期：制动 ABS 周期 **10ms**、动力扭矩 **20ms**、ADAS 感知 **40ms**、车身控制 **100ms**、信息娱乐 **200ms**；
- 启动时间：**< 800ms**（满足"插钥匙即用"用户体验）；
- 故障响应：单点故障 **< 100ms** 内降级（FailOperational）；
- 日志记录：黑匣子持续记录 30 秒滚动数据。

K 已识别出 5 个核心实时任务（部署在单个 Cortex-M7 核）：

| 任务 | 名称 | 周期 Ti（ms） | 执行时间 Ci（ms） | 截止期 Di（ms） | 优先级（RMS） |
|---|---|---|---|---|---|
| τ1 | ABS 制动 | 10 | 3 | 10 | 最高 |
| τ2 | 扭矩控制 | 20 | 4 | 20 | 高 |
| τ3 | ADAS 感知融合 | 40 | 8 | 40 | 中 |
| τ4 | 车身控制（车窗/车灯） | 100 | 10 | 100 | 低 |
| τ5 | 信息娱乐通信 | 200 | 20 | 200 | 最低 |

K 计划用 **RMS（Rate Monotonic Scheduling）**进行可调度性分析；如果 RMS 不满足，再评估 **EDF（Earliest Deadline First）**。

**【小问】**（合计 25 分）

**问 1**（10 分）：使用 **RMS 利用率上界判定法**，列出 5 任务的 CPU 利用率计算过程，给出 RMS 上界 `n(2^(1/n)-1)`（n=5）的具体数值，判定该任务集是否可调度，并给出**完整推导**。

**问 2**（6 分）：若任务 τ3（ADAS 感知）的执行时间 Ci 因算法升级从 8ms 增加到 **15ms**，请重新计算 CPU 利用率并判定是否仍可调度。如果 RMS 不可调度，**EDF** 是否可调度？为什么？

**问 3**（5 分）：解释 **RMS 与 EDF** 的本质区别（静态 vs 动态、上下文切换、实现复杂度），并说明在车载嵌入式系统中**主流仍选择 RMS** 的原因。

**问 4**（4 分）：本系统的可靠性如何保证？请列出至少 **4 项嵌入式可靠性技术**（含看门狗、双核冗余等）并说明在本架构的作用。

**【参考答案】**

**问 1**：RMS 可调度性分析（约 280 字）

**步骤 1：计算总 CPU 利用率 U**

```
U = Σ(Ci / Ti)
  = C1/T1 + C2/T2 + C3/T3 + C4/T4 + C5/T5
  = 3/10 + 4/20 + 8/40 + 10/100 + 20/200
  = 0.30 + 0.20 + 0.20 + 0.10 + 0.10
  = 0.90
```

**步骤 2：计算 RMS 利用率上界 U_max(n)**

```
U_max(n) = n × (2^(1/n) - 1)
n = 5：
  2^(1/5) = 2^0.2 ≈ 1.1487
  U_max(5) = 5 × (1.1487 - 1) = 5 × 0.1487 ≈ 0.7435
```

（n→∞ 时极限为 ln 2 ≈ 0.693）

**步骤 3：判定**

```
U = 0.90 > U_max(5) = 0.7435
```

**结论**：**充分条件不满足，RMS 利用率上界判定法判定不可调度**。

**步骤 4：必要时用响应时间分析（RTA，更精确）**

但 U=0.90 已接近 EDF 上界 1.0，硬实时系统设计原则是"避免接近上界"，建议优化任务参数或换 EDF。

> 注：RMS 上界判定是**充分非必要**条件——超过上界**不一定**不可调度（可用 RTA 进一步分析），但工程上一般直接判定为高风险。

**问 2**：τ3 执行时间增至 15ms 的影响（约 200 字）

**RMS 重新分析**：

```
U = 3/10 + 4/20 + 15/40 + 10/100 + 20/200
  = 0.30 + 0.20 + 0.375 + 0.10 + 0.10
  = 1.075
```

`U = 1.075 > 1.0`，**RMS 不可调度**（甚至超过 EDF 上界 100%）。

**EDF 可调度性判定**：

EDF 充要条件：`U ≤ 1`（仅当截止期等于周期时）

```
U = 1.075 > 1.0
```

**EDF 也不可调度**——因为 CPU 已经"过载"，任何调度算法都无法满足所有截止期。

**解决方案**：
1. **算法优化**：感知融合算法剪枝，C3 降至 ≤ 12ms；
2. **任务拆分**：将 τ3 拆为 "感知预处理（C=5ms, T=40ms）+ 融合计算（C=10ms, T=80ms）"；
3. **多核分配**：把 τ3 迁至空闲 M7 核（采用分区 / Bound 静态绑定）；
4. **硬件升级**：使用更高频率的 M7 或 A 核执行。

**问 3**：RMS vs EDF 本质区别（约 220 字）

| 维度 | **RMS（Rate Monotonic）** | **EDF（Earliest Deadline First）** |
|---|---|---|
| 优先级 | **静态**——周期越短优先级越高，运行时不变 | **动态**——剩余截止期越近优先级越高 |
| 利用率上界 | `n(2^(1/n)-1)`，n→∞ 极限 0.693 | **1.0（100%）** |
| 上下文切换 | 较少（优先级稳定） | 多（动态计算） |
| 实现复杂度 | 简单——优先级表驱动 | 复杂——每次调度需重新排序 |
| 时序可预测性 | **高**（静态分析友好） | 低（动态行为难证明） |
| 失效行为 | 高优先级任务永远抢占低优先级，过载时低优先级饿死 | 过载时所有任务都可能错过截止期（雪崩） |
| ISO 26262 认证 | 主流路径 | 难认证 |

**车载嵌入式选 RMS 的原因**：
1. **可证明性**：ASIL-D 要求形式化验证，RMS 静态分析友好；
2. **过载行为可预测**：故障时高优先级（ABS）必然存活，低优先级（信息娱乐）降级，符合 FailOperational；
3. **AUTOSAR Classic 标准支持**：OS 模块原生 RMS 静态优先级；
4. **工具链成熟**：Vector DaVinci 等支持 WCET 分析 + RMS 自动化；
5. **EDF 雪崩不可控**——汽车级不可接受。

**问 4**：嵌入式可靠性技术（约 180 字）

| 技术 | 在本架构作用 |
|---|---|
| **看门狗 WDT（独立 + 窗口）** | M7 核每 50ms 喂狗，超时 3 倍硬件复位；窗口看门狗防止程序失控喂狗 |
| **双核 Lockstep（M7 ×2 同步）** | 两个 M7 跑相同代码，硬件比对结果，不一致触发安全反应——满足 ASIL-D 单点故障 99% 覆盖率 |
| **ECC 内存** | DDR + Flash 全 ECC，单 bit 翻转自动纠正，多 bit 翻转触发降级 |
| **冷/热双机冗余** | 主域控故障时备用 ECU（如 EBC 制动控制器）独立完成 ABS，FailOperational < 100ms |
| **Memory Protection Unit (MPU)** | OS 隔离任务地址空间，防止单任务故障污染其他任务内存 |
| **CRC 校验 + 安全启动** | Bootloader → 内核 → 应用每一级签名校验，防固件篡改 |
| **黑匣子日志（FIFO 滚动）** | 持续记录最后 30s CAN/Ethernet 报文 + 任务调度轨迹，事故后取证 |

**常见扣分点**：
- ❌ U_max 公式记错——`n(2^(1/n) - 1)` 不是 `n(2^n - 1)`
- ❌ 把 RMS 上界写死为 0.693——0.693 是 n→∞ 极限，n=5 时 0.7435
- ❌ EDF 上界判定写"≤ 0.693"——错，EDF 是 ≤ 1
- ❌ "RMS 不可调度直接换 EDF"——首先要判 EDF 是否也过载（U>1 时谁都救不了）
- ❌ 可靠性只答看门狗——必须双核 Lockstep / ECC / MPU 多管齐下
- ❌ 不考虑 ASIL-D 认证——车载必须谈功能安全

**高分技巧**：
- RMS 计算**写出每一步小数和总和**比直接写 0.9 得分高
- 引用 **AUTOSAR Classic / Adaptive 双内核** 体现行业现状
- 提到 **WCET（最坏执行时间）** 分析、**Liu & Layland 1973 论文**经典出处
- 解决方案给出**具体拆分参数**比"优化代码"得分高
- 可靠性提及 **MISRA-C / ISO 26262 / DO-178C** 标准

### 模拟题 2 · 工业控制器构件组装与 AADL 建模（25 分）

**【题干】**（约 760 字）

某工业自动化龙头企业研发新一代**柔性产线控制器**（PLC + Edge Compute 一体机），用于离散制造（汽车焊装、3C 装配）现场。架构师 R 主导软件架构设计，**强调"构件化 + 复用"**——产品线包含基础版 / 专业版 / 旗舰版，三档产品**70% 软件构件可复用**，差异化通过构件组装实现。

业务约束：
- 控制周期：硬实时 PLC 扫描 **1ms**，软实时数据采集 **10ms**，业务 **100ms**；
- 现场协议：Modbus-TCP / OPC UA / EtherCAT / Profinet 四类（构件化适配）；
- 设备规模：单控制器接入 **256 个工位**，整线 **2000 个 I/O 点**；
- 安全等级：**SIL2**（功能安全 IEC 61508）；
- 硬件平台：x86 工控机 + RT-Linux Preempt-RT 实时内核；
- 团队规模：14 人（含 3 名嵌入式架构师），开发周期 14 个月。

R 提交的构件化架构核心决策：

1. **分层架构**：HAL（硬件抽象）→ BSP（板级支持包）→ RTOS（RT-Linux）→ 中间件（构件总线）→ 应用构件 → UI；
2. **构件化总线**：基于 **OSGi**（Apache Felix） 实现热插拔，构件粒度按"协议适配 / 工艺逻辑 / 算法 / UI 控件"4 类；
3. **核心构件清单**（30+ 构件）：
   - 协议层：Modbus-Component、OPC-UA-Component、EtherCAT-Component、Profinet-Component；
   - 工艺层：MotionControl、PIDController、CamProfile（电子凸轮）、Trajectory（轨迹规划）；
   - 数据层：HistoryDB、AlarmManager、RecipeManager；
   - 算法层：VisionInspect、QualityPredict（AI）、EnergyOptimize；
   - 公共层：LogService、ConfigService、SecurityService；
4. **接口契约**：所有构件 OpenAPI 3.0 + IDL 定义接口，**版本号 SemVer**，向后兼容遵循"破坏性变更必升大版本号"；
5. **建模工具**：使用 **AADL（Architecture Analysis & Design Language）+ OSATE**进行架构建模，生成可调度性分析、流分析、错误模型；
6. **构件组装**：通过 XML 配置文件声明依赖关系，OSGi 启动时按 **拓扑排序** 解决依赖；
7. **实时保证**：硬实时构件（MotionControl、PIDController）跑在 RT 线程组（SCHED_FIFO 优先级 90+）+ 内存预分配 + CPU 隔离（isolcpus）；
8. **容错**：构件级故障隔离（沙箱）、故障构件自动重启、关键构件双副本主备切换。

**【参考答案】**

**问 1**：构件特征与 OSGi 落地（约 380 字）

**构件核心特征**：

| 特征 | 含义 | 本架构落地 |
|---|---|---|
| **接口契约** | 通过明确接口与外部交互，不暴露内部实现 | OpenAPI 3.0 + IDL 双重契约，编译时校验 |
| **独立部署** | 可独立编译、打包、部署、版本化 | 每个构件打包为 OSGi Bundle（JAR + Manifest） |
| **可替换** | 同接口的构件可热插拔替换 | OSGi `bundle:install/start/stop/uninstall` 命令 |
| **组装性** | 通过组装配置文件构造系统，不改代码 | XML + 拓扑排序自动解析依赖 |
| **无持久状态（或显式）** | 状态通过明确通道暴露 | 构件状态通过 ConfigService 显式持久化 |

**OSGi 热插拔机制**：
1. **类加载隔离**：每个 Bundle 有独立 ClassLoader，避免类冲突；
2. **生命周期管理**：INSTALLED → RESOLVED → STARTING → ACTIVE → STOPPING → UNINSTALLED；
3. **服务注册中心**：ServiceRegistry 追踪所有发布的服务接口；
4. **版本依赖解析**：Manifest 中 `Import-Package; version=[1.0,2.0)` 声明版本范围；
5. **热替换**：旧版本 Bundle stop → 新版本 install + start，业务零中断（前提：接口兼容）。

**适合构件化的边界**：
- ✅ 协议适配层（Modbus / OPC UA 各家协议接入差异大但接口相同）
- ✅ 算法插件（PID / 模糊 PID / 模型预测控制 MPC，可按工艺切换）
- ✅ UI 控件（按客户定制不同界面）
- ✅ 业务工艺（汽车焊装 vs 3C 装配差异巨大）

**不适合构件化的场景**：
- ❌ **高频交互的紧耦合代码**——构件间调用开销 > 业务逻辑本身（如 1ms 级 PLC 扫描内）
- ❌ **强一致状态共享**——多构件读写同一内存映像，构件化反而增加同步开销

**问 2**：AADL 建模与对比（约 280 字）

**AADL 核心元素**：

| 元素 | 含义 | 本架构应用 |
|---|---|---|
| **Component** | 软件 / 硬件 / 系统三大类（process / thread / device / processor / bus / memory） | MotionControl 建模为 thread；x86 CPU 建模为 processor；EtherCAT 建模为 bus |
| **Feature** | 组件的对外接口（port、参数、subprogram） | MotionControl 输入 port: PIDSetPoint，输出 port: MotorCommand |
| **Connection** | 组件间数据 / 事件流 | 数据流 PIDController → MotionControl，周期 1ms |
| **Property** | 组件属性（周期、WCET、优先级、内存占用、错误率） | MotionControl: Period=>1ms, Compute_Execution_Time=>0.3ms, Priority=>95 |
| **Mode** | 系统运行模式 | 启动 / 运行 / 停机 / 紧急停机 4 模式切换 |
| **Flow** | 端到端数据 / 事件流分析 | 传感器→控制器→执行器端到端延迟 < 5ms |

**应用**：通过 OSATE 工具基于 AADL 模型自动生成：① **可调度性分析**（基于属性的 RMS / EDF 推导）；② **流延迟分析**（端到端 latency）；③ **错误传播分析**（EMV2 错误模型）；④ **代码框架生成**（Ramses）。

**对比优势**：

| 维度 | UML-MARTE | SysML | **AADL** |
|---|---|---|---|
| 定位 | 实时扩展 | 系统工程 | **嵌入式实时专用** |
| 形式化 | 弱 | 弱 | **强**（语法严格、语义精确） |
| 可分析性 | 低 | 低 | **高**（OSATE 工具链） |
| 学习成本 | 中 | 中 | 高 |
| 工业应用 | 通用 | 通用 | **航空/航天/汽车 ASIL-D 必备** |

AADL 的核心优势是**可分析性**——能基于模型直接推导可调度性、流延迟、错误传播，而 UML/SysML 主要用于"沟通"。

**问 3**：实时性保证（约 130 字）

| 手段 | 说明 |
|---|---|
| **RT-Linux Preempt-RT 内核** | 全内核可抢占（CONFIG_PREEMPT_RT_FULL）+ 中断线程化 + 优先级继承（防优先级反转） |
| **SCHED_FIFO 实时调度策略** | 关键任务用 chrt 设置优先级 90+，绝对优先级抢占 |
| **CPU 隔离（isolcpus）** | Linux 启动参数 `isolcpus=2,3`，把 CPU 2/3 从普通调度域剥离，专供实时任务 |
| **内存预分配 + mlockall** | 启动时 malloc + mlockall 锁定物理内存，避免运行时缺页中断 |
| **PRP 协议（Parallel Redundancy Protocol）** | 双网口冗余，丢包毫秒级切换 |
| **NUMA 绑定** | 实时任务绑定单 NUMA 节点，减少跨节点内存访问 |

**问 4**：构件化 4 层复用（约 100 字）

**构件复用 4 层次**：
1. **代码复用**——库（lib）级别，函数/类的二进制复用；
2. **设计复用**——设计模式（如观察者、工厂、策略）的复用；
3. **分析复用**——领域模型（DDD）的复用，业务概念与边界；
4. **架构复用**——参考架构 / 平台的复用（最高层次）。

**70% 复用如何实现**：
- 基础版：协议层 4 个 + 公共层 3 个 + 工艺层 PIDController + UI 简版（共 10 个构件）；
- 专业版：在基础版上 +HistoryDB、+CamProfile、+Trajectory、+VisionInspect（共 14 个构件，10 个复用 = 71%）；
- 旗舰版：在专业版上 +QualityPredict（AI）、+EnergyOptimize（共 18 个构件，14 个复用 = 78%）。

差异化构件以"插件包"形式分发，授权解锁 → 同一二进制差异化销售。

## 2024 下半年真题 · 试题三（ROS 机器人操作系统升级）

> 来源：2024 年 11 月 系统架构设计师案例分析 试题三
> 公开真题回忆版，仅供学习参考。

### 【题干场景】

某机器人公司开发新一代服务机器人，操作系统计划从 **ROS1 升级到 ROS2**。架构师需说明 ROS 特点、ROS1/ROS2 区别、ROS2 四种通信模型。

### 【问题 1】（5 分）ROS 定义与特点

**定义**：
> ROS（Robot Operating System）是一个**开源的元操作系统**（Meta-OS），运行在 Linux 之上，为机器人应用提供**硬件抽象、底层设备控制、消息传递、包管理**等服务。

**5 大特点**：
1. **点对点设计**：去中心化通信
2. **多语言支持**：C++ / Python / Java
3. **精简集成**：可与 OpenCV、PCL 等无缝集成
4. **开源免费**：BSD 协议
5. **工具丰富**：rviz 可视化 / gazebo 仿真 / rosbag 录制

### 【问题 2】（10 分）ROS1 vs ROS2 核心区别

| 维度 | ROS1 | ROS2 |
|---|---|---|
| **通信协议** | 自定义 TCPROS/UDPROS | **DDS**（Data Distribution Service）工业标准 |
| **节点管理** | 依赖中心 **roscore** | **去中心化**，节点自治 |
| **跨平台** | 仅 Linux 友好 | **Linux / Windows / macOS** 全支持 |
| **实时性** | 弱（无原生支持） | **强实时**（适用安全关键场景） |
| **安全** | 无加密 | **DDS-Security**（加密、认证、访问控制） |
| **生命周期** | 启动即运行 | **明确的节点生命周期管理** |
| **QoS 策略** | 简单 | 丰富（可靠性、持久性、截止时间） |

### 【问题 3】（10 分）ROS2 四种通信模型

| 通信 | 模式 | 特点 | 典型场景 |
|---|---|---|---|
| **话题 Topic** | **发布-订阅**，异步、单向 | 一对多解耦 | 传感器数据流（激光雷达、摄像头） |
| **服务 Service** | **请求-响应**，同步 | 一对一阻塞 | 一次性命令（开关机、状态查询） |
| **动作 Action** | **请求 + 反馈 + 结果** | 长时任务带进度反馈 | 机械臂运动、导航规划 |
| **参数 Parameter** | **全局键值共享** | 配置管理 | 速度上限、PID 参数 |

### 【采分关键词】

元操作系统 / 点对点 / DDS / 去中心化 / roscore / 实时性 / DDS-Security / 话题 / 服务 / 动作 / 参数

### 【常见扣分点】

- ❌ ROS 定义答成"操作系统"——必须答**元操作系统**（运行在 Linux 之上）
- ❌ ROS2 通信协议答成 TCP/UDP——必须答 **DDS**
- ❌ 四通信少答动作（Action）——动作是 ROS2 长任务核心机制

## 2022 下半年真题 · 试题三（宇航嵌入式分布式综合化电子系统：心跳 vs 超时探测）

> 来源：2022 年 11 月 系统架构设计师案例分析 试题三
> 公开真题回忆版，仅供学习参考。

### 【题干场景】

某宇航装备**分布式综合化电子系统**，采用**四层架构**：**模块支持层、操作系统层、分布式中间件层、功能应用层**。架构师需设计故障检测方案，并对故障类型分类，最后分析数据驱动方法的优势。

### 【问题 1】（8 分）心跳检测 vs 超时探测对比

| 维度 | 心跳检测（Heartbeat） | 超时探测（Ping/Echo） |
|---|---|---|
| **主动方** | **被监控节点**主动发送 | **监控节点**主动发起 |
| **消息** | 节点固定周期发心跳告"我活着" | 节点发 PING → 被探测节点回 ECHO |
| **判定** | N 周期内未收到心跳 → 故障 | 超时未回 ECHO → 故障 |
| **网络开销** | 单向消息，开销低 | 双向消息，开销翻倍 |
| **故障发现速度** | 慢（需等 N 个周期） | 快（超时即判定） |
| **适用** | 大规模节点（节省监控端压力） | 小规模 + 故障必须快速发现 |

### 【问题 2】（8 分）故障类型分类（四层监控器）

| 监控器层级 | 监控对象 | 典型故障类型 |
|---|---|---|
| **核状态监控** | CPU 核心 | 核异常（崩溃、寄存器错乱）、温度过高 |
| **分区状态监控** | OS 分区（ARINC 653 分区） | 分区超时、分区资源耗尽、分区间通信失败 |
| **模块状态监控** | 硬件模块 | 模块掉电、模块响应超时、模块自检失败 |
| **系统状态监控** | 整个系统 | 网络分区、多节点同时失效、全局服务不可用 |

**采分原则**：故障从**最小粒度**（核）到**最大粒度**（系统）逐层升级，每层独立监控器，**故障局部处理为主，全局兜底**。

### 【问题 3】（9 分）数据驱动方法

**基本概念**：
> 不依赖**精确的物理/数学解析模型**，而是基于**历史故障数据 + 实时遥测数据**，用统计学习/机器学习方法**识别故障模式**和**预测故障**。

**对比解析模型方法**：

| 维度 | 解析模型 | 数据驱动 |
|---|---|---|
| **依赖** | 精确物理建模 | 历史数据 |
| **适用** | 简单已知系统 | **复杂未知系统** |
| **精细化** | 难度大（需重新建模） | **可逐渐精细化**（数据越多越准） |
| **未来扩展** | 修改困难 | **兼容未来变化**（增加新故障样本即可） |

**核心优势**：
1. **逐步精细化**：随数据积累不断提升准确率
2. **兼容未来变化**：新故障模式只需补充样本即可，无需重新建模
3. **适应复杂系统**：宇航系统组件多、交互复杂，难以精确解析建模

### 【采分关键词】

心跳 / 超时探测 / Ping/Echo / 四层监控器 / 核/分区/模块/系统 / 数据驱动 / 解析模型 / 逐步精细化

### 【常见扣分点】

- ❌ 心跳与超时探测主动方混淆——心跳必是被监控端发起
- ❌ 故障分类层级混乱——必须按"核 → 分区 → 模块 → 系统"四层
- ❌ 数据驱动优势只说"精度高"——必须答出"逐步精细化 + 兼容未来"
