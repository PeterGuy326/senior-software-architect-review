# 案例题型 02 · 数据库设计（ER + 规范化）

> **必考题型**，几乎每年 1 题，25 分。

## 考点分布

- 补全 **ER 图**（实体、属性、联系、基数）
- 转换 ER → **关系模式**
- 判定**范式**（1NF / 2NF / 3NF / BCNF）
- 识别**函数依赖 / 候选键 / 主键 / 外键**
- 参照完整性、并发控制、分布式数据库
- **关系库 + 缓存 / NoSQL 混合架构**（Cache Aside、读写分离、反规范化、存储选型）—— 近年高频综合题型

## 核心理论（必背）

### 函数依赖

- **部分依赖**：X → Y，但存在 X 的真子集 X' 也能 → Y → 违反 2NF
- **传递依赖**：X → Y → Z，违反 3NF
- **平凡依赖**：Y ⊆ X 时 X → Y（可忽略）

### 范式

| 范式 | 要求 | 常见违规 |
|---|---|---|
| **1NF** | 属性**原子**（不可再分） | 一列存多值 |
| **2NF** | 1NF + **消除部分依赖**（非主属性完全依赖候选键） | 联合主键中只依赖一部分 |
| **3NF** | 2NF + **消除传递依赖** | 非主属性依赖非主属性 |
| **BCNF** | 3NF + **所有决定因素都是候选键** | 主属性对主属性的部分依赖 |

### ER 图联系类型

- **一对一（1:1）**
- **一对多（1:N）**
- **多对多（M:N）**（需引入**联系表**）

### 基数（Cardinality）

- 最小 / 最大基数，如 (0,1)、(1,N)

## 答题模板

### 问题 1：补全 ER 图

**套路**：
1. 找题干中名词 → 实体
2. 找动词短语 → 联系
3. 属性分到实体内
4. **弱实体**用双框，**多值属性**用双椭圆

### 问题 2：ER → 关系模式

**套路**：
- **1:1**：合入任一方（选被依赖方）
- **1:N**：N 端加外键指向 1 端
- **M:N**：**独立一张联系表**（主键 = 双方主键组合）

**标注**：关系模式写为 `学生（学号, 姓名, 系号）`，主键加粗 / 加下划线。

### 问题 3：判范式 + 分解

**套路**：
```
(1) 列函数依赖集 F
(2) 求候选键（闭包算法）
(3) 判范式：
    - 有非原子属性 → 1NF
    - 有部分依赖 → 2NF 冲突
    - 有传递依赖 → 3NF 冲突
(4) 分解：
    - 保持依赖、无损连接
    - 每个子模式都是 3NF 或 BCNF
```

### 问题 4：参照完整性

**套路**（触发器或约束）：
- **插入**子表 → 要求父表有对应键
- **删除 / 更新**父表 → 级联（CASCADE）、置空（SET NULL）、拒绝（RESTRICT）

## 万能高分句

- "学生与课程之间是 **多对多** 联系，需引入**选课**联系表，主键为 **(学号, 课号)** 组合"
- "当前模式存在**传递依赖**：`学号→系号→系主任`，违反 **3NF**，应分解为 **学生(学号,姓名,系号)** 和 **系(系号,系主任)**"
- "为保证**参照完整性**，在子表的外键上定义 **ON DELETE CASCADE**，父记录删除时联动清理"

## 并发与分布式加分点

### 并发控制

- **悲观锁**（`SELECT ... FOR UPDATE`）vs **乐观锁**（版本号 / 时间戳）
- **隔离级别**：读未提交 / 读已提交 / 可重复读 / 串行化
- **问题**：脏读 / 不可重复读 / 幻读 / 丢失更新

### 分布式数据库

- **分片**：水平分片（按范围 / 哈希）/ 垂直分片
- **复制**：主从 / 多主
- **CAP / BASE**
- **两阶段提交 2PC** / **三阶段 3PC**

## 常见陷阱

| ❌ | ✅ |
|---|---|
| M:N 联系不建表 | **必须**独立表 |
| 联系表主键只用一个 | 主键 = **双方主键组合** |
| 分解只说结果不给函数依赖 | 必须**列出 F** 再推 |
| 不说保持依赖 / 无损连接 | **两个性质**必须明确 |
| 外键方向错 | **多方**指向**一方** |

### 模拟题 1 · 在线教育选课系统 ER + 3NF 分解（25 分）

**【题干】**（约 820 字）

某高校"智慧学堂"在线教育平台为全校 **5.2 万名本科生 + 1.8 万名研究生**提供选课、上课、作业、成绩管理一站式服务。项目由信息化办公室主导，组建 **18 人**团队（DBA 2 人、后端 8 人、前端 4 人、测试 3 人、PM 1 人），开发周期 **8 个月**，2025 年春季学期上线。

业务关键指标：每学期开放课程 **6000 门**（含通识、专业、实验、体育），选课开放期 24 小时内峰值 **QPS 1.2 万**（学生抢热门课），系统单日峰值访问 **200 万次**，选课接口 **P95 < 300ms**，年可用性 **99.95%**。

DBA 张工根据需求梳理出业务规则如下：

1. **学生**信息含学号（唯一）、姓名、学院、专业、年级、入学年份、联系方式（手机号、邮箱）；
2. **教师**含工号（唯一）、姓名、所在学院、职称、研究方向；
3. **课程**含课程号、课程名、学分、学时、课程类型（通识/专业/实验/体育）、开课学期；同一门课程**每学期可由多位教师**分别开多个**教学班**（如"高等数学"在 2025 春有 8 个班，分别由不同老师上课）；
4. **教学班**含教学班号（唯一）、上课时间段（一周内多个时段，如周一 1-2 节、周三 3-4 节）、上课地点（教室）、容量上限（如 60 人）、当前选课人数；
5. **学生选课**：一名学生在一个学期可选多个教学班，一个教学班有多名学生；选课时需记录**选课时间**、**选课状态**（已选/退课/已完成）；
6. **成绩**：学生选完一个教学班后，每学期末由教师录入**期末成绩**（百分制）、**平时成绩**、**实验成绩**（仅实验类课程），系统按权重自动计算**总评成绩**；
7. **选课规则约束**：先修课程不达标禁止选课、同一时段不能选两门、教学班选满拒绝；
8. 数据库选用 **MySQL 8.0**，订单库一主两从半同步复制；选课表预估**单学期数据量 60 万行**，三年积累 **360 万行**。

张工初步给出实体关系草图，但其中 ER 图存在缺漏，且部分关系模式未达到 3NF，需对方案进行规范化分析。

**【参考答案】**

**问 1**：ER 图补全 + 教学班建模理由（约 280 字）

```mermaid
erDiagram
    STUDENT ||--o{ ENROLLMENT : "选课"
    CLASS_SECTION ||--o{ ENROLLMENT : "被选"
    COURSE ||--o{ CLASS_SECTION : "开设"
    TEACHER ||--o{ CLASS_SECTION : "讲授"
    ENROLLMENT ||--|| GRADE : "对应"
    STUDENT {
        string sid PK
        string name
        string college
        string major
        int    grade_year
    }
    TEACHER {
        string tid PK
        string name
        string college
        string title
    }
    COURSE {
        string cid PK
        string cname
        decimal credit
        int    course_hours
        string course_type
    }
    CLASS_SECTION {
        string section_id PK
        string cid FK
        string tid FK
        string semester
        string time_slot
        string classroom
        int    capacity
        int    enrolled_count
    }
    ENROLLMENT {
        string sid FK
        string section_id FK
        datetime enroll_time
        string  status
    }
    GRADE {
        string sid FK
        string section_id FK
        decimal final_score
        decimal regular_score
        decimal lab_score
        decimal total_score
    }
```

基数：STUDENT-ENROLLMENT (1:N)、CLASS_SECTION-ENROLLMENT (1:N)、COURSE-CLASS_SECTION (1:N)、TEACHER-CLASS_SECTION (1:N)、ENROLLMENT-GRADE (1:1)。

**为什么"教学班"必须独立建实体**：① 教学班具备**自身属性**（容量、时间段、教室、当前人数），是 ER 中的**弱实体到独立实体演变**的典型；② 同一课程同一教师在不同学期可开多个班，**纯 M:N 联系无法承载这些非键属性**；③ 学生的选课对象是"教学班"而非"课程"或"教师"，业务主键是 section_id；④ 若强行用"课程-教师"M:N，时间段、教室冲突检测无法在数据库层表达，违反**避免多值属性入主表**原则。

**问 2**：候选键 + 范式判定 + 3NF 分解（约 320 字）

（1）**候选键推导**：从 F 出发，{学号, 教学班号} 闭包：  
{学号, 教学班号} → 姓名,学院,专业（依赖①）→ 课程号,教师工号（依赖③）→ 课程名,学分（依赖②）→ 教师姓名（依赖④）→ 期末成绩,平时成绩（依赖⑤），覆盖全属性。故**候选键 = {学号, 教学班号}**，唯一。

（2）**范式判定**：R 属于 **1NF**。理由：存在**部分函数依赖**——非主属性"姓名/学院/专业"仅依赖候选键的真子集"学号"（依赖①），违反 2NF；同时存在**传递依赖**——课程号→课程名（先经教学班号→课程号→课程名），违反 3NF。故未达 2NF。

（3）**保持依赖且无损连接的 3NF 分解**：

| 关系 | 属性 | 主键 | 来源依赖 |
|---|---|---|---|
| R1 学生 | (学号, 姓名, 学院, 专业) | 学号 | ① |
| R2 课程 | (课程号, 课程名, 学分) | 课程号 | ② |
| R3 教师 | (教师工号, 教师姓名) | 教师工号 | ④ |
| R4 教学班 | (教学班号, 课程号, 教师工号) | 教学班号 | ③ |
| R5 选课成绩 | (学号, 教学班号, 期末成绩, 平时成绩) | (学号, 教学班号) | ⑤ |

**验证**：① **保持依赖**——F 中 5 条依赖分别在 R1/R2/R3/R4/R5 中保留；② **无损连接**——R4 与 R5 通过 教学班号 公共属性可还原原表，R1/R2/R3 通过 R4/R5 外键关联，符合 chase test。

**问 3**：抢课并发控制方案（约 220 字）

（1）**数据库层方案**：在教学班表使用**带条件 UPDATE + 行锁**实现"先扣容量再插入选课记录"：

```sql
START TRANSACTION;
UPDATE class_section 
   SET enrolled_count = enrolled_count + 1
 WHERE section_id = ? AND enrolled_count < capacity;
-- 受影响行数 = 0 → 容量已满，回滚
INSERT INTO enrollment(sid, section_id, enroll_time, status) VALUES (?, ?, NOW(), '已选');
COMMIT;
```

InnoDB 在 UPDATE 时获取**行级排他锁（X 锁）**，且 `enrolled_count < capacity` 条件由数据库原子判定，**杜绝超选**。

（2）**方案对比**：

| 方案 | 优点 | 缺点 | 适用 |
|---|---|---|---|
| **乐观锁（version 字段）+ 重试** | 无锁、并发高 | 8000 人抢 60 名额 → 99% 失败重试，**雪崩风险** | 冲突低场景 |
| **悲观锁（SELECT ... FOR UPDATE）** | 强一致、不丢请求 | 行锁排队，P95 可能 > 300ms 不达标 | 中等并发 |
| **Redis 预扣减 + 异步落库** | **QPS 1.2 万可扛**、亚毫秒响应 | 一致性弱、需对账补偿 | **本场景推荐**：Redis Lua 原子扣减容量，扣减成功后投递 RocketMQ 异步写 MySQL |

### 模拟题 2 · 医院 HIS 弱实体 + 多值属性建模（25 分）

**【题干】**（约 780 字）

某三甲综合医院"康宁医院"启动新一代 **HIS（医院信息系统）** 改造，整合现有的门诊挂号、住院、处方、检查、检验、电子病历共 6 大子系统。项目由信息科牵头，外包给厂商 A 团队 **22 人**联合开发，建设周期 **14 个月**，2026 年中投产。医院日均门诊量 **8000 人次**、住院床位 **1200 张**、月处方量 **24 万张**。

DBA 团队梳理需要建模的核心业务对象：

1. **科室**（department_id 全院唯一）：含科室名、所在楼层、负责人、电话；下设**病区**——一个科室可有多个病区，**病区编号在科室内部唯一**（如"心内科 - 1 病区"、"心内科 - 2 病区"）；
2. **医生**（doctor_id 唯一）：姓名、性别、职称、所属科室、**多个执业资格证**（一名医生可拥有"主任医师证 + 介入资格证 + 麻醉资格证"等 1-5 个不等）；
3. **患者**（patient_id 全院唯一）：姓名、性别、出生日期、身份证号、**多个联系方式**（手机、座机、紧急联系人手机），**多个过敏药物**（青霉素、磺胺、链霉素等，可为空）；
4. **床位**：床位号在病区内部唯一（不跨病区），含床位类型（普通/重症/隔离）、当前状态（空闲/占用/维护）；
5. **住院**：一名患者一次住院记录含住院号（系统全局唯一）、入院日期、出院日期、主治医生、所在床位、诊断编码（ICD-10）；
6. **检查项目**：CT、MRI、心电图等，每项有标准价格；患者每次住院期间可做**多项检查**，每项检查记录执行时间、执行医生、检查结果文本；
7. **处方**：处方号、开方医生、患者、开方时间，**一张处方含 1-N 种药品**，每种药品标注剂量、用法、用量、天数；
8. 数据库平台为 **达梦 DM8**（信创要求），日活跃连接数预估 **1500**，热数据保留 5 年。

DBA 注意到几个建模难点：病区不能脱离科室存在、医生执业资格是多值、处方-药品是 M:N 携带属性。请基于 ER 模型规范化建模。

**【小问】**（合计 25 分）

**问 1**（8 分）：用 Mermaid `erDiagram` 给出**病区**、**床位**、**医生执业资格**、**患者过敏药物**四个建模点的处理方案。其中：（1）说明哪些是**弱实体**及其判定依据（3 分）；（2）将"医生的多个执业资格证"和"患者的多个过敏药物"两个**多值属性**消除为独立实体（5 分）。

**弱实体判定**（3 分）：

**问 2**：候选键 + BCNF 分解（约 350 字）

（1）**候选键**：{处方号, 药品编码} 的闭包覆盖全属性（处方号→医生工号→医生姓名；处方号→患者ID→患者姓名；药品编码→药品名称,规格,单价；处方号,药品编码→剂量,用法,用量,天数；处方号→开方时间）。**候选键 = {处方号, 药品编码}**，唯一。

（2）**范式判定**：属于 **1NF**。理由：① 非主属性"医生姓名 / 患者姓名"对候选键存在**部分依赖**（仅依赖处方号一部分）→ 违反 2NF；② 同时"医生姓名"通过"医生工号"传递依赖于候选键 → 违反 3NF；③ 依赖②④的左部不是超键 → 违反 BCNF。

（3）**BCNF 分解**：

| 关系 | 属性 | 主键 |
|---|---|---|
| R1 处方主表 | (处方号, 开方医生工号, 患者ID, 开方时间) | 处方号 |
| R2 医生 | (医生工号, 医生姓名) | 医生工号 |
| R3 患者 | (患者ID, 患者姓名) | 患者ID |
| R4 药品 | (药品编码, 药品名称, 规格, 单价) | 药品编码 |
| R5 处方明细 | (处方号, 药品编码, 剂量, 用法, 用量, 天数) | (处方号, 药品编码) |

**保持依赖性验证**：
- F 中依赖① → R1 全部保留；
- 依赖② → R2 保留；依赖③ → R3 保留；依赖④ → R4 保留；依赖⑤ → R5 保留；
- 5 条依赖**全部保持**，且每个分解关系左部都是超键，**满足 BCNF**。
- **无损连接**：R1 与 R5 通过"处方号"等值连接可还原原表，R2/R3/R4 通过外键链接 R1/R5。

**问 3**：审计与加密方案（约 220 字）

（2）**加密 + 审计**：

（1）**国家分片倾斜测算**（3 分）：

（2）**user_id 哈希对四类查询的影响**（5 分）：

| 查询模式 | 占比 | 命中分片数 | 影响 | 加权得分 |
|---|---|---|---|---|

**问 2**：改进方案（约 320 字）

（1）**分片键 + 算法**：选择 **user_id 作为唯一分片键**，分片算法采用"**user_id % 库数 → 库号；user_id / 库数 % 表数 → 表号**"两级哈希。理由：① user_id 查询占 65% 主流量，最高频路径必须直达；② user_id 分布天然均匀（雪花 ID）；③ 国家维度通过库内 country_code 字段+索引解决，不上升为分片键。

（2）**库数与表数测算**：
- 3 年订单总量：380 万 × 365 × 3 ≈ **41.6 亿**；活跃 12% ≈ 5 亿（90 天内）。
- 单表上限 500 万：5 亿 / 500 万 = **100 张表**。
- 单库 1TB：每库 5 张表 × 单表 200GB ≈ 1TB → **20 库 × 5 表 = 100 表**。
- 余量保护：实际取 **32 库 × 32 表 = 1024 表**（2^N 便于扩容、留 30% 弹性）。

（3）**非主键查询解决方案**：
- **按 order_no 查**（25%）：order_no 雪花 ID 中**内嵌 user_id 后 N 位**作为分片路由因子（"基因法"），无需建二级索引，直接命中分片；
- **按 merchant_id 查**（8%）：建立**异构索引表**（merchant_id → user_id, order_no），CDC 监听 binlog 实时同步至 ES，商家端走 ES 查询；
- **BI 报表**（2%）：MySQL → Flink CDC → ClickHouse 实时入仓，BI 走 ClickHouse 不打主库。

**问 3**：分布式事务 + 冷热合规（约 220 字）

（1）**分布式事务选型**：选 **本地消息表 + 最终一致**。

| 方案 | 一致性 | 性能 | 复杂度 | 适配本场景 |
|---|---|---|---|---|
| TCC | 强一致 | P95+50ms | 高（每业务写 3 套） | ❌ 大促 1100 万 QPS 扛不住 |
| Seata-AT | 强一致 | P95+30ms | 低 | ❌ 全局锁瓶颈 |
| Saga | 最终一致 | 中 | 中 | ⚠️ 长流程补偿复杂 |
| **本地消息表** | **最终一致** | **P95+10ms** | 低 | ✅ **推荐** |

理由：跨境电商订单允许秒级最终一致；本地消息表借助 RocketMQ 事务消息 + 定时补偿扫描器，**无全局锁、性能影响最小**，与团队现有 RocketMQ 栈契合度高。

（2）**冷热分离 + 跨境合规**：
- **冷热**：90 天内热数据留 MySQL；91-365 天迁 TiDB（可分析）；1 年以上归档 OSS + Hudi 表。
- **跨境合规**：在分片内增加 country_code 维度的**物理隔离**——印尼/泰国数据库部署在新加坡 Region，沙特数据库部署在中东 Region；通过 ShardingSphere 的 **多活路由策略**按 country_code 路由到对应 Region 的库集群，**禁止跨 Region 复制敏感字段**，符合 GDPR 和当地数据驻留法规。

**【参考答案】**

**问 1**：缓存数据选型与粒度（约 300 字）

**适合缓存的数据特征**：读多写少、对一致性容忍秒级、计算/JOIN 成本高、访问热点集中。映射到本场景：

- `spu_name / detail_html / main_img / 类目路径 / brand_name` —— 几乎只读 → **强烈适合缓存**；
- `sku.price` —— 读多写少（改价低频）→ **适合缓存**；
- `sku.stock` —— 每秒被扣减几十次 → **不适合和详情聚合在一起缓存**，否则每次扣减都要失效整个聚合对象，命中率塌方。

**取舍方案 —— 二级 key 拆分**：

- `spu:base:{spu_id}` 缓存 SPU 基础信息 + 类目路径 + 品牌名 + 该 SPU 的 SKU 骨架（sku_id、规格、价格），TTL = 1800s + random(0,600s)；**改价/改类目/上下架时删**。
- `sku:stock:{sku_id}` 单独缓存库存（或直接用 Redis 原子计数器做库存预扣），**库存扣减只动这一个小 key**。
- 详情页 = `GET spu:base:{id}` 拿骨架 + `MGET sku:stock:*` 批量拿实时库存，应用层组装返回。

这样**低频的改价只失效 base、高频的扣库存只动 stock**，互不干扰，命中率高 —— 直接回应了 DBA 的质疑 (a)。

**问 2**：Cache Aside 读/写路径（约 230 字）

```
读路径：
  client → GET spu:base:{id}
       命中 → MGET sku:stock:* 组装 → 返回
       未命中 → SET lock:spu:{id} {uuid} NX PX 10000（防并发回源）
              → 查 MySQL 从库（JOIN spu/sku/category/brand）→ 组装聚合对象
              → SET spu:base:{id} {json} EX (1800+rand) → DEL lock → 返回
       （没抢到锁的线程 sleep 20ms 后重试 GET）

写路径（先 DB 后 Cache）：
  client → UPDATE MySQL 主库（改价/改库存/上下架）
        → DEL spu:base:{id}（若改库存还要同步 SET/DEL sku:stock:{sku_id}）
        → 返回
```

**"先更 DB 再删缓存"的优势**：① 优于"先删缓存再更 DB"——后者在"删缓存→更 DB 完成"窗口内，并发读会查从库（仍是旧值）回写缓存，造成**长期脏数据**；前者脏数据窗口仅 ms 级，且后续读会立即修正。② 优于"更新缓存"——删是**幂等**的；更新聚合对象要重新 JOIN 计算、写路径变重；并发两个写各自算的聚合对象可能互相覆盖成中间态；大量被改的 SPU 短期不会被读，更新缓存是浪费——**删 + 懒加载**更经济。

**问 3**：穿透与雪崩的针对性解法（约 320 字）

**痛点 ③ —— 缓存穿透（查不存在的 spu_id）**：

1. **布隆过滤器**：启动时把全量上架 SPU ID（120 万）灌入 RedisBloom（误判率 0.1% ≈ 约 200KB 内存），查询前先 `BF.EXISTS`，不存在直接拒绝；上下架时 `BF.ADD`，每日凌晨全量重建兜底（解决删除导致的误判累积）。
2. **缓存空值**：MySQL 查不到的 spu_id 也写 `spu:base:{id} = "NULL"` 占位，TTL = 60s + random(0,30s)，避免反复打 DB；同时网关层对 spu_id 做格式/范围校验拦截明显非法值。

**痛点 ④ —— 缓存雪崩（大促集中上架后缓存集中失效）**：

1. **TTL 打散 + 上架预热**：基础 TTL = 1800s + random(0,600s)，让同时上架的商品不在同一秒过期；上架流程里**主动 SET 进 Redis 预热**。
2. **多级缓存 + 熔断降级**：应用本地加一层 Caffeine（容量 1 万、TTL 60s）挡住头部热点；Sentinel 配置 Redis 异常率 > 30% 或 RT > 50ms 时熔断，降级为本地缓存 + 限流 + 静态兜底详情页；Redis 本身 6 主 6 从 + 跨可用区，单点故障自动切换。
3. **互斥锁回源（兼防击穿）**：同一 spu_id 失效瞬间只放 1 个线程查 DB，其余等待，避免热点 SPU 失效瞬间几千请求同时回源压垮主从。

**问 4**：读己之写一致性 + 反规范化评价（约 350 字）

**痛点 ② 根因**：读写分离下写走主库、读走从库，**主从复制是异步的**（大促 binlog 量大、从库 apply 慢，延迟 50~800ms）；运营在主库改完价、立刻刷新，请求被路由到尚未同步的从库 → 读到旧价。即使删了缓存，回源读的也是从库，仍是旧值。

**解决方案对比（≥ 2 种）**：

| 方案 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| **强制读主**（Hint Master） | 写操作后一小段时间（如该商品 1~2s 内）的读请求强制路由主库（ShardingSphere `HintManager` / 注解 `@MasterRoute`） | 简单、强一致 | 主库读压力上升；需精确界定"哪些读"走主 |
| **写后双写缓存** | 改价时不只删缓存，**直接把新值 SET 进 Redis**；读优先读缓存 → 立即看到新值 | 不增加主库压力，C 端立即可见 | 缓存与 DB 仍有极小不一致窗口；要保证写缓存成功（失败要补偿） |
| **等待复制位点 / 半同步复制** | 关键写后等至少 1 个从库 ACK（semi-sync），或读请求带写时 GTID、路由到已追上该 GTID 的从库 | 一致性强 | 写延迟上升、改造成本高 |

**推荐组合**：改价时"**先更主库 + 立即 SET 新值进 Redis（覆盖）+ 异步再 DEL 一次兜底**"，C 端读缓存即得新值；运营预览页等强一致场景用**强制读主**。

**DBA 质疑 (c) —— 反规范化冗余 `category_name / brand_name` 进 `spu` 表**：

- **利**：列表/详情查询不用再 JOIN `category / brand`，单表查询，高 QPS 下显著降负载；与缓存配合更顺（聚合对象本就要带这些字段）。
- **弊**：① 数据冗余 —— 类目/品牌改名要同步更新所有相关 `spu` 行（**更新放大**）；② 违反 3NF（`category_name` 传递依赖 `category_id`），一致性维护成本上移到应用层；③ 类目层级深时冗余整条路径更脆弱。
- **适用条件**：**读远多于写、被冗余字段极少变更（品牌名/类目名几乎不改）、能接受用 Canal 监听 binlog 或定时任务做最终一致**。本场景读写比 250:1、类目品牌名基本不变 → **可以做反规范化**，但要 (a) 只冗余稳定字段；(b) `category / brand` 改名时用 Canal 监听 binlog 异步刷新 `spu` 表 + 缓存；(c) 仍以 `category_id / brand_id` 为准、保留外键约束，冗余名仅供展示。本质是"**反规范化 = 用空间和一致性维护成本换查询性能**"的经典权衡——工程上常"规范化设计 + 针对性反规范化 + 缓存"三层叠加。

**常见扣分点**：
- ❌ 把整个 SPU 聚合对象（含库存）当一个 key 缓存——高频扣库存会把命中率打塌，必须拆 key
- ❌ Cache Aside 写"先删缓存再更 DB"——并发读会回写旧值造成长期脏数据
- ❌ 缓存一致性答"更新缓存"而非"删缓存"——删才幂等、才避免中间态
- ❌ 穿透答"加大缓存容量""延长 TTL"——答非所问
- ❌ 把"改价读到旧价"全归咎于缓存 TTL——根因是**读写分离的主从延迟**，删了缓存回源从库照样旧
- ❌ 互斥锁/分布式锁不设 PX 过期时间——会死锁

**高分技巧**：
- 用"`spu:base` + `sku:stock` 二级 key"这种**具体 key 命名**体现工程落地能力
- 引"逻辑过期 + 异步刷新""布隆误判率 0.1% ≈ 200KB""TTL = base + rand(0,600s)"等量化参数
- 读己之写给**对比表 + 推荐组合**而不是只选一个
- 反规范化收尾点出"规范化 + 针对性反规范化 + 缓存三层叠加"的设计哲学，比单纯说"省 JOIN"高一个层次

**【参考答案】**

**问 1**：6 类数据选型（约 360 字）

| # | 数据 | 选型 | 理由（匹配 + 为何不用别的） |
|---|---|---|---|
| 1 | 商品/订单核心 | **MySQL**（一主多从，后续分库分表） | ACID 事务、外键、复杂 JOIN、成熟对账生态——金融级订单必须关系库；NoSQL 普遍弱事务/弱 JOIN，不胜任 |
| 2 | 详情聚合 + 购物车/会话 | **Redis** | 纯 KV、内存级 < 5ms、原生 TTL（购物车自动过期）、丰富结构（Hash 存购物车、String 存详情 JSON）；MongoDB 延迟/内存效率不如 Redis；放 MySQL 达不到 5ms 且耗连接 |
| 3 | 行为日志/埋点 | **Kafka 缓冲 → HBase/数仓** | 600 亿条/日只有 Kafka 百万级吞吐扛得住采集，下游 Flink 实时风控 + 落 HBase/Hive 离线分析；MySQL/MongoDB 写吞吐差几个数量级；用 ES 存原始日志成本爆炸 |
| 4 | 评论 + 全文检索 | **Elasticsearch**（原文同时存 MySQL/MongoDB 做主存，ES 做检索副本） | 倒排索引天生做全文检索 + BM25 相关度 + 高亮 + 聚合（评分分布用 aggregation）；MySQL `LIKE '%kw%'` 不走索引、FULLTEXT 也弱；MongoDB 文本搜索远不如 ES |
| 5 | 社交关系/好友推荐 | **Neo4j**（超大规模可换 NebulaGraph/JanusGraph） | 关注/粉丝是天然图，"二度人脉"= 2-hop 遍历，关系库要多次自连接 JOIN 性能爆炸；图库 index-free adjacency 让多跳遍历近常数级；反欺诈关联也适合 |
| 6 | 排行榜 + 计数器 + 分布式锁 | **Redis** | ZSet 做排行榜（`ZADD`/`ZREVRANGE`，score = 销量）、`INCR`+`EXPIRE` 做限流计数器、`SET NX PX` 做分布式锁；MySQL 做这些会被高频写打爆 |

**问 2**：跨存储一致性（下单为例，约 280 字）

跨存储**没有全局事务**，整体策略是"**关系库内强一致（ACID）+ 跨库最终一致**"，至少用以下 4 个机制：

1. **本地消息表 / 事务消息（Outbox 模式）**：下单时在 MySQL **一个本地事务**里写 `t_order` + 写 `t_msg_outbox`（待发事件）；后台 relay 把 outbox 投到 Kafka，投成功标记已发——保证"订单落库"与"事件发出"原子（最终一致）。
2. **Redis 库存预扣 + Lua 原子脚本 + 对账补偿**：下单先用 Lua 脚本原子 `DECR` Redis 库存（不足则失败），订单最终落库后异步把扣减对账回写 MySQL 库存表；定时对账任务修正不一致（订单失败但 Redis 已扣 → 回补）。
3. **消费端幂等**：Kafka 至少一次投递，ES（评论数）、排行榜（销量）的更新消费者用业务唯一键（order_id）去重，避免重复累加。
4. **CDC（Canal / Debezium）兜底**：MySQL 评论/商品的变更经 binlog 单向同步到 ES，保证 ES 与 MySQL 最终一致——避免业务"双写"不一致。

**问 3**：Polyglot Persistence 的新问题与应对（约 280 字）

| 新问题 | 应对 |
|---|---|
| **跨库一致性难保证**（无分布式事务） | Saga / 本地消息表 + 消费幂等 + 定时对账 + CDC；业务上接受最终一致并设计补偿流程 |
| **运维复杂度 ×N**（要懂 MySQL/Redis/ES/Neo4j/Kafka 各自部署、监控、容灾、扩容） | 收敛存储种类（够用即可，别为炫技堆栈）、优先云托管、统一监控告警平台、每种存储建 SOP |
| **数据冗余、同步链路长**（同一份评论存 MySQL + ES，商品存 MySQL + Redis） | 明确"**主存储 vs 派生存储**"，派生存储一律由 CDC 单向同步生成、不接受业务直接写，重建有据可依 |
| **跨存储查询/聚合困难**（要 join MySQL 订单 + Neo4j 关系 + ES 评论） | Flink 实时打宽到 ClickHouse/HBase 宽表，或应用层 API 聚合，避免在线跨库 JOIN |
| **故障域扩大**（任一存储挂影响一块功能） | 每个存储独立做高可用 + 降级预案：ES 挂 → 搜索降级为按时间排序；Neo4j 挂 → 推荐降级为热门榜 |
| **数据治理/权限分散** | 统一元数据管理、统一脱敏与审计策略 |

**常见扣分点**：
- ❌ 全文检索选 MySQL FULLTEXT——大规模检索 + 相关度排序必须 ES
- ❌ 社交关系选关系库——"二度人脉"多跳 JOIN 性能爆炸，要图数据库
- ❌ 行为日志选 MongoDB/MySQL——600 亿条/日吞吐扛不住，要 Kafka + HBase/数仓
- ❌ 跨库一致性答"用分布式事务（XA/2PC）解决"——跨异构存储无法 2PC，必须最终一致
- ❌ 只堆存储不谈运维/一致性代价——多存储是有成本的，要点出权衡

**高分技巧**：
- 每类选型用"**业务特征 → 匹配存储能力 → 排除其它候选**"三段式
- 提"主存储 vs 派生存储""Outbox 模式""CDC 单向同步"等术语体现架构深度
- Polyglot 部分点出"**收敛存储种类**"——别让评委觉得你只会堆技术栈
- 一致性给"强一致（库内）+ 最终一致（跨库）"的分层结论，比笼统说"保证一致性"高一档
