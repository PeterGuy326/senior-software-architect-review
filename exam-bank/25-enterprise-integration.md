# 企业应用集成（EAI / ESB / 中间件 / 集成模式） · 18 题

> **高频考点**（每年 1-3 题）· EAI 四层次（表示/数据/应用接口/业务流程）及耦合度排序 · 点对点 P2P vs 中心辐射 Hub-and-Spoke vs 总线 ESB（连接数 N(N−1)/2）· ESB 核心能力 · ESB vs API 网关 vs 微服务"哑管道" · 中间件分类（RPC/MOM/ORB-CORBA/TPM/数据访问/应用服务器）· 同步 vs 异步 · Web Service 三要素 SOAP/WSDL/UDDI · SOAP vs REST · 企业集成模式 EIP（基于内容的路由/聚合器/分割器/死信通道/保证投递）· 遗留系统演化四策略 · iPaaS

### 1. EAI（企业应用集成）按集成切入点划分，下列**不属于**其四个层次的是：

A. 用户界面集成（表示集成）

B. 数据集成

C. 应用接口集成（控制集成 / 功能集成）

✅ **D. 网络协议集成**

**答案**：D
**解析**：EAI 四个层次 = 用户界面（表示）集成、数据集成、应用接口（控制/功能）集成、业务过程（流程）集成；按切入点从表示层到数据层、应用接口层、业务流程层逐级深入。"网络协议集成"不是 EAI 的层次划分维度。

---

### 2. 下列对 EAI 各集成层次**按耦合度从松到紧**排序正确的是：

✅ **A. 用户界面集成 < 数据集成 < 应用接口集成 < 业务过程集成**

B. 数据集成 < 用户界面集成 < 应用接口集成 < 业务过程集成

C. 用户界面集成 < 应用接口集成 < 数据集成 < 业务过程集成

D. 业务过程集成 < 应用接口集成 < 数据集成 < 用户界面集成

**答案**：A
**解析**：用户界面集成只在表示层"拼界面"（Portal/iframe/SSO），各系统内部互不依赖，最松；数据集成直接搬数据、绕过应用逻辑，比应用接口集成略松；应用接口集成要调用对方业务能力，耦合上升；业务过程集成把多个系统的能力编排进同一条端到端流程，一处改动牵连最多，最紧。

### 3. 某集团有 10 个系统全部采用点对点（P2P）方式两两集成，理论上最多需要的接口连接数为：

A. 10

B. 20

✅ **C. 45**

D. 100

**答案**：C
**解析**：点对点两两互联的连接数为 N×(N−1)/2 = 10×9/2 = 45 条；连接数随系统数近似平方增长，系统一多就成"意大利面式"接口网，改一处牵全身，是典型的集成反模式。

---

### 4. 关于点对点、中心辐射（Hub-and-Spoke）、总线（ESB）三种集成拓扑，下列说法**错误**的是：

A. 点对点拓扑的连接数随系统数近似平方增长，可维护性最差

B. 中心辐射模式所有系统只连中心 Hub，连接数降为线性 N，但 Hub 易成单点瓶颈

C. ESB 是中心辐射模式的演进形态，强调标准化接入，且可集群/分布式部署

✅ **D. ESB 拓扑必然是单一节点、无法分布式部署，因此可用性低于点对点**

**答案**：D
**解析**：ESB 在保留"线性连接数 + 集中治理"优点的同时，可以集群化、分布式部署来消除早期单一 Hub 的单点问题；"中心化易成性能/可用性瓶颈"是其需要权衡的缺点，但不等于"必然单点、不可分布式"。点对点反而因接口耦合度高、变更影响面大而最难维护。

---

### 5. 关于企业服务总线 ESB 的核心能力，下列**不属于**其职责的是：

A. 协议转换（SOAP↔REST↔JMS↔FTP↔HTTP）

B. 消息路由（含基于内容的路由 Content-Based Router）

C. 数据格式转换与消息增强（XML↔JSON 字段映射、从其它系统补字段）

✅ **D. 主数据的 Golden Record 建模与跨系统主数据去重清洗**

**答案**：D
**解析**：ESB 的核心能力是协议转换、消息路由、格式转换、消息增强、服务编排、统一安全、消息监控审计；而主数据建模、Golden Record、跨系统去重清洗属于 MDM（主数据管理，数据集成层）的职责，不是 ESB 该做的事。

---

### 6. 在 SOA 架构中，ESB（企业服务总线）的主要作用是：

✅ **A. 连接服务消费者与服务提供者，屏蔽协议、位置、数据格式差异，实现松耦合通信与位置透明**

B. 集中存放企业所有服务的源代码与版本

C. 替代关系数据库，承担业务数据的持久化

D. 负责前端页面的渲染与展示逻辑

**答案**：A
**解析**：ESB 是 SOA 的通信枢纽，让服务消费者与提供者"互不知道对方在哪、用什么协议、用什么格式"，通过总线完成传输、协议转换、路由、格式转换、编排，从而实现去中心化通信与位置透明。它既不是代码仓库，也不承担数据持久化或页面渲染。

---

### 7. 相比传统 SOA + ESB，微服务架构在服务间通信上的典型理念是：

A. 用更重的智能管道集中编排所有调用

✅ **B. "智能终端，哑管道"——业务/路由逻辑放在服务里，通道只负责传输**

C. 所有微服务必须共用一个数据库以保证一致性

D. 服务间一律改用 SOAP/WSDL 同步调用

**答案**：B
**解析**：微服务相对 SOA 的一大变化就是用"哑管道（dumb pipe，如轻量 REST/gRPC 或简单消息总线）+ 智能终端（smart endpoint）"取代 ESB 这种重型智能管道，把路由、转换、编排等逻辑下沉到各服务中，实现去 ESB 化、去中心化治理。微服务强调每个服务独立数据库、轻量通信，并不要求共库或统一同步协议。

### 8. 下列中间件类型与代表产品对应**错误**的是：

A. 面向消息中间件 MOM —— RabbitMQ / Kafka / RocketMQ

B. 远程过程调用 RPC 中间件 —— Dubbo / gRPC / Thrift

✅ **C. 对象请求代理 ORB 中间件 —— Tomcat / WebLogic**

D. 事务处理中间件 TPM —— Tuxedo / CICS

**答案**：C
**解析**：Tomcat、WebLogic 属于应用服务器中间件（提供事务、连接池、安全等容器服务）；对象请求代理 ORB 中间件的代表是 CORBA（通过 IIOP 协议实现跨语言、跨平台的分布式对象调用）。

---

### 9. CORBA 属于下列哪一类中间件？

A. 面向消息中间件 MOM

B. 应用服务器中间件

✅ **C. 对象请求代理（ORB）中间件**

D. 数据访问中间件

**答案**：C
**解析**：CORBA（Common Object Request Broker Architecture）通过 ORB（对象请求代理）+ IIOP 协议实现分布式对象调用，屏蔽对象的物理位置与实现语言，是 ORB 类中间件的典型代表；同步调用模式。

---

### 10. 关于同步通信与异步通信，下列说法**错误**的是：

A. 同步通信（如 RPC/HTTP）调用方阻塞等待返回，时序强依赖，耦合度较高

B. 异步通信（如 MOM/消息）发完即走、不等结果，可解耦并削峰填谷

C. 异步通信通常只能保证最终一致性

✅ **D. 跨系统的企业应用集成（EAI）应优先采用同步 RPC，以保证强一致性**

**答案**：D
**解析**：跨系统的 EAI 集成首选**消息传递（异步）**实现解耦、削峰、可靠投递，避免同步 RPC 强依赖导致的级联故障（雪崩）；只有强一致、需要立即结果的少数环节（如支付扣减）才用同步 RPC 或 TCC，不应一把梭用同步。

### 11. Web Service 的三个核心标准（"三件套"）是：

A. HTTP / HTML / JSON

✅ **B. SOAP / WSDL / UDDI**

C. REST / JSON / OpenAPI

D. SOAP / XML / FTP

**答案**：B
**解析**：Web Service 三要素 = SOAP（基于 XML 的消息协议）+ WSDL（Web 服务描述语言，描述接口）+ UDDI（统一描述、发现和集成，服务注册与发现）。三者协作完成"描述服务—注册发现服务—调用服务"的闭环。

---

### 12. 关于 SOAP 与 REST 的对比，下列说法**错误**的是：

A. SOAP 基于 XML，REST 常用 JSON，更轻量

B. SOAP 有 WSDL 强契约和 WS-Security 等企业级规范，REST 多靠约定与文档

C. SOAP 可跨多种传输协议（HTTP/SMTP/JMS 等），REST 主要基于 HTTP

✅ **D. REST 是一种通信协议，SOAP 则是一种架构风格**

**答案**：D
**解析**：恰好相反——SOAP 是一种基于 XML 的消息协议（可跨多种传输协议、有 WS-* 系列规范、强契约）；REST 是一种架构风格（资源 + 统一 HTTP 动词 + 无状态 + 可缓存），轻量、易扩展，是当前主流。

### 13. ESB 中"根据消息内容（如订单金额、地区、业务类型）把消息分发到不同的处理服务"，对应的企业集成模式（EIP）是：

A. 聚合器 Aggregator

B. 分割器 Splitter

✅ **C. 基于内容的路由 Content-Based Router**

D. 死信通道 Dead Letter Channel

**答案**：C
**解析**：基于内容的路由器（Content-Based Router）检查消息体的内容（字段值、类型、地区等）来决定把消息转发到哪个目的地，是消息路由器模式的一种典型实现；聚合器是攒齐合并、分割器是拆分、死信通道是存放无法投递/处理的消息。

---

### 14. 下列对企业集成模式（EIP）的描述**错误**的是：

A. 聚合器 Aggregator 把一组相关消息攒齐后合并为一条

B. 分割器 Splitter 把一条大消息（如批量订单）拆成多条小消息分别处理

C. 死信通道 Dead Letter Channel 用于存放无法投递或处理失败的消息，供人工/补偿处理

✅ **D. 消息转换器 Message Translator 的作用是把同步调用自动改造为异步调用**

**答案**：D
**解析**：消息转换器（Message Translator）做的是数据格式与结构的转换（如 XML→JSON、字段重映射），让格式不同的系统能互通；"把同步改成异步"不是它的职责。聚合器、分割器、死信通道的描述均正确。

---

### 15. 关于企业集成模式中的"保证投递（Guaranteed Delivery）"，下列说法**正确**的是：

✅ **A. 消息持久化落盘，即使节点宕机重启也不丢，最终一定送达（通常为 at-least-once，需消费端幂等）**

B. 消息只保存在内存中以追求最高吞吐

C. 保证投递即保证消息绝不重复（exactly-once）

D. 保证投递必须配合同步 RPC 才能生效

**答案**：A
**解析**：保证投递通过消息持久化（落盘）+ 失败重试 + 死信通道实现"宕机不丢、最终送达"，语义通常是 at-least-once（可能重复，需消费端做幂等处理），而非 exactly-once；它是消息中间件的能力，与同步 RPC 无关。

### 16. Hohpe《企业集成模式》把"应用集成方式"归纳为四类，其中被业界**普遍推荐**用于跨系统集成的是：

A. 文件传输（File Transfer）

B. 共享数据库（Shared Database）

C. 远程过程调用（Remote Procedure Invocation）

✅ **D. 消息传递（Messaging）**

**答案**：D
**解析**：四类集成方式中——文件传输简单但粒度粗、实时性差；共享数据库紧耦合、易冲突；远程调用同步、强耦合、易级联故障；消息传递异步、松耦合、可靠投递、可削峰，是业界推荐的跨系统集成方式（也是 ESB/MOM 的基础）。

### 17. 教材按"业务价值 × 技术价值"四象限给出遗留系统（Legacy System）的演化策略，下列对应**错误**的是：

A. 业务价值高、技术价值高 → 继承（封装/集成），系统保留，做接口对接

B. 业务价值高、技术价值低 → 改造（局部重构 + 数据迁移），逐步现代化

✅ **C. 业务价值低、技术价值高 → 淘汰（直接弃用、用新系统替代）**

D. 业务价值低、技术价值低 → 淘汰（替换重建）

**答案**：C
**解析**：业务价值低但技术价值高的系统，正确策略是**集成**——用 Wrapper/适配器封装出标准接口并入新平台，复用其技术资产；只有业务价值低、技术价值也低的系统才**淘汰（替换重建）**。四象限关键词：淘汰 / 继承（封装包装 + 适配器）/ 改造（局部重构 + 数据迁移）/ 集成（接口对接）。

### 18. 关于 iPaaS（Integration Platform as a Service，集成平台即服务），下列说法**正确**的是：

✅ **A. 云上的集成中台，把连接器、流程编排、API 管理、数据映射等 ESB/ETL/API 网关能力以 SaaS 方式提供，面向多云/混合集成**

B. 一种数据库分库分表中间件

C. 一种容器编排引擎，等价于 Kubernetes

D. 一种前端 UI 框架，用于构建企业门户页面

**答案**：A
**解析**：iPaaS 是云上的集成平台即服务，提供预置连接器、可视化流程编排、API 管理、数据映射等能力，把传统 ESB + ETL + API 网关的功能 SaaS 化，代表如 MuleSoft Anypoint、Boomi、阿里集成中台等，主要面向多云与混合环境的集成场景。
