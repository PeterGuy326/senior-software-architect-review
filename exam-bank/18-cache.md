# 缓存（击穿 / 雪崩 / 穿透 / 一致性 / Redis） · 12 题

> **高频考点**（每年 1-2 题，案例题高频）· 缓存的本质是**用空间换时间、用一致性换性能** · **三大经典问题**：**穿透**（查不存在的 key 透到 DB）/ **击穿**（热 key 过期瞬间高并发打 DB）/ **雪崩**（大量 key 同时过期或缓存宕机）· **缓存更新模式**：Cache Aside（旁路、最常用）/ Read-Through / Write-Through / Write-Behind · **一致性**：先更新 DB 再删缓存（最常用）vs 先删缓存再更新 DB · **淘汰策略**：LRU / LFU / FIFO / Random · Redis 持久化 RDB vs AOF · 多级缓存（本地 Caffeine + 远程 Redis）

---

### 1. **缓存穿透（Cache Penetration）** 的典型场景与防护手段，下列描述**错误**的是：

A. 大量请求查询数据库中**不存在的 key**，缓存层不命中、全部打到 DB

B. 可以通过**布隆过滤器（Bloom Filter）** 在缓存前过滤掉一定不存在的 key

C. 可以将"不存在"也缓存（缓存空值），并设置较短过期时间

✅ **D. 增大缓存容量就能彻底解决穿透问题**

**答案**：D
**解析**：穿透的根因是"查的 key 根本不存在"——再大的缓存也装不下"不存在的数据"。两大解决方案：①**布隆过滤器**（O(1) 判断"一定不存在"，有少量误判但绝不漏判）；②**缓存空值**（key→null，设短 TTL 防止占空间）。穿透常见来源：黑产恶意攻击、爬虫扫描 ID。

---

### 2. **缓存击穿（Cache Breakdown）** 的根本原因是：

A. 大量 key 同时过期

✅ **B. 某个**热点 key 突然失效**，瞬间高并发请求全部打到数据库**

C. 缓存服务整体宕机

D. 数据库连接池耗尽

**答案**：B
**解析**：**击穿专指"单点热 key 失效"**——比如某爆款商品详情页的 key 刚过期，1 秒内 10 万请求并发查 DB，DB 直接被压垮。解决方案：①**热 key 永不过期**（后台异步刷新）；②**互斥锁（Mutex / SingleFlight）**——只让一个线程查 DB 回填缓存，其他线程等待结果；③**逻辑过期**（缓存中存"逻辑过期时间"，过期时异步刷新、返回老值）。

---

### 3. **缓存雪崩（Cache Avalanche）** 的常见诱因，下列**不属于**的是：

A. 大量 key 设置了相同或相近的过期时间，同时失效

B. Redis 集群整体宕机

✅ **C. 单个 key 被高频访问**

D. 缓存重启后所有数据丢失（冷启动）

**答案**：C
**解析**：**单 key 高频访问是热 key 问题或击穿问题，不是雪崩**。雪崩特征是"大面积失效"。预防方案：①**过期时间打散**（基础 TTL + 随机偏移，如 30 分钟 ± 5 分钟）；②**Redis 高可用**（主从/哨兵/Cluster + 持久化）；③**限流降级**（Sentinel/Hystrix 在缓存崩时降级返回兜底数据保护 DB）；④**多级缓存**（本地 Caffeine 兜底 Redis）；⑤**预热**（重启后批量回填热数据）。

---

### 4. **Cache Aside（旁路缓存）** 模式的标准读写流程是：

✅ **A. 读：先查缓存、未命中则查 DB 并回填缓存；写：先更新 DB，再删除缓存**

B. 读：先查 DB；写：先写缓存

C. 读：只查缓存；写：只写 DB

D. 读写都同时操作缓存和 DB

**答案**：A
**解析**：**Cache Aside 是工业界最常用的缓存模式**——应用直接管理缓存与 DB，框架不介入。**写策略选"先 DB 再删缓存"而非"先删缓存再 DB"**，原因：①两步之间若有读请求，"先 DB 再删"只可能让缓存暂时旧（短时；下次读时会回填新值）；"先删再 DB"则可能让旧值回填缓存（长时不一致）；②"删而非更新"避免缓存值与 DB 计算结果（如包含派生字段）的不一致。

---

### 5. 关于**缓存一致性**，"**先更新 DB，再删除缓存**"策略仍可能出现的不一致场景是：

✅ **A. 读请求 A 在缓存未命中读 DB 后、未回填前，写请求 B 完成"更 DB+删缓存"，然后 A 把旧值回填到缓存**

B. 缓存永远比 DB 新

C. DB 更新失败导致缓存未删

D. 缓存删除导致 DB 数据丢失

**答案**：A
**解析**：A 读到了旧 DB 值，B 的写完成后缓存被删（但 A 还没回填）；A 把读到的**旧值**回填缓存——形成不一致。**概率极低**（要求读路径慢于写路径），但理论存在。**根治方案**：**延迟双删**——更新 DB 后立即删缓存；睡眠 N 毫秒后再删一次。或用**订阅 binlog**（Canal/Debezium）异步删缓存，彻底解耦。**强一致场景应放弃缓存或用分布式事务**。

### 6. **Redis 内存淘汰策略**中，**优先淘汰最近最少使用**的策略是：

A. allkeys-random — 所有 key 中随机淘汰

✅ **B. allkeys-lru — 所有 key 中淘汰最久未访问的**

C. volatile-ttl — 在设置了过期时间的 key 中淘汰 TTL 最短的

D. noeviction — 不淘汰，直接报错

**答案**：B
**解析**：Redis 8 种淘汰策略 = **数据范围（allkeys / volatile）× 算法（lru / lfu / random / ttl）+ noeviction**。**LRU（Least Recently Used）** 看"最久未访问"；**LFU（Least Frequently Used）**（4.0+）看"访问频次最少"——更适合冷启动数据少访问的场景。**默认 noeviction**：内存满直接拒写。**最常用配置：allkeys-lru** 当纯缓存用。

### 7. 关于 **Redis 持久化**，下列描述**错误**的是：

A. RDB 是某时刻的全量内存快照、压缩存储、恢复快、可能丢失最后一次快照后的数据

B. AOF 记录每个写命令、可配 always/everysec/no 三档刷盘、丢数据少但文件大

C. AOF 重写（rewrite）会压缩历史命令为最简形式

✅ **D. 同时开启 RDB + AOF 时，Redis 启动恢复优先用 RDB**

**答案**：D
**解析**：**同时开启时，Redis 启动恢复优先使用 AOF**——因为 AOF 数据更完整、丢失更少。RDB 主要用于备份/灾难恢复。生产推荐**RDB + AOF 混合持久化**（4.0+）：AOF 文件前半段是 RDB 快照、后半段是增量命令，兼具"恢复快"和"丢失少"。

### 8. 处理 **Redis 热 key**（如秒杀爆款）的下列方案，**错误**的是：

A. **本地缓存**（如 Caffeine）在应用层先扛一层，减少 Redis 压力

B. 把单个热 key 拆分为多个"key:0"~"key:N"，分散到多个分片

C. 用读写分离 + 多个 Redis 副本扛读

✅ **D. 把这个 key 的 TTL 设为 0（永不过期）并用 KEYS * 定期扫描**

**答案**：D
**解析**：**KEYS * 是 Redis 生产禁忌**——会阻塞整个 Redis 实例（单线程模型）。要扫描应该用 SCAN 游标。永不过期本身可以，但搭配 KEYS * 是双重错误。热 key 工业解法：**本地缓存（一级缓存兜底）+ key 分片（打散热点）+ 多副本读扩容**。

### 9. 关于 **Redis 大 key** 问题，下列描述**错误**的是：

A. 单个 String value 超过 10KB、List/Hash/Set/Zset 元素数超过 5000 即视为大 key

B. 大 key 会导致网络阻塞、内存倾斜、删除时阻塞主线程

✅ **C. 删除大 key 应使用 DEL 同步删除以保证一致性**

D. 应优先用 UNLINK 异步删除，或拆分为多个小 key

**答案**：C
**解析**：**DEL 大 key 会阻塞 Redis 主线程**（单线程模型）——百万级元素的 Hash DEL 可能阻塞数秒，导致集群超时雪崩。**正确做法**：**UNLINK**（4.0+，异步删除，主线程只解除引用、后台线程释放内存）或**拆分**（把大 Hash 拆为多个小 Hash）。大 key 排查工具：`redis-cli --bigkeys`。

### 10. 在**多级缓存**架构（本地 Caffeine + 远程 Redis + DB）中，**一致性最难保证**的环节是：

A. Redis 与 DB 之间

✅ **B. 多个应用实例的本地 Caffeine 之间**

C. Caffeine 与 DB 之间

D. 同一实例内 Caffeine 与 Redis

**答案**：B
**解析**：**应用集群中每个实例都有自己的本地缓存**——单实例缓存失效不影响其他实例，传统"删缓存"操作只能删自己机器的。**解决方案**：①**广播通知**（通过 MQ、Redis Pub/Sub、ZK watch 通知所有实例失效本地缓存）；②**本地缓存设短 TTL**（如 10s，容忍短暂不一致）；③**只缓存"几乎不变"的数据**（如字典、配置）。

### 11. 关于 **Redis Cluster**，下列描述**错误**的是：

A. 数据分片基于 **16384 个 hash slot**，每个 key 经 CRC16 mod 16384 分配到 slot

B. 客户端可直连任意节点，发现 key 不在该节点会返回 MOVED 重定向

C. 支持主从复制，每个分片一主多从、主挂时自动故障转移

✅ **D. 支持事务（MULTI/EXEC）跨多个 slot 的原子操作**

**答案**：D
**解析**：**Redis Cluster 不支持跨 slot 事务/Lua 脚本/Pipeline**——所有操作必须在同一个 slot 内（同一节点）。解决方案：用 **hash tag**：把希望放一起的 key 用 `{...}` 标记同一部分（如 `user:{1000}:profile` 和 `user:{1000}:orders`），CRC16 只算 `{}` 内部分，确保进同一 slot。

### 12. **缓存预热（Cache Warm-up）** 的最佳时机和方式是：

A. 用户访问时按需加载

B. 永远不预热，靠用户流量自然热起来

✅ **C. 在系统启动 / 大促前 / 缓存重启后，主动批量加载热点数据到缓存**

D. 把所有 DB 数据全部加载到缓存

**答案**：C
**解析**：**缓存预热是雪崩、击穿、冷启动的关键预防手段**。典型场景：①**应用启动**——批量加载常用字典/配置；②**大促前**（双 11、618）——按历史数据预测热点 SKU 提前加载；③**缓存集群重启/扩容后**——按 Redis 历史访问日志或 DB 慢查询日志反推热数据回填。**全量加载**违背缓存"二八原则"——80% 的访问集中在 20% 的热数据上，全量浪费内存。

## 速查决策树

```
缓存出问题 → 三问：
  ① key 存在吗？     不存在 → 穿透 → 布隆过滤器 / 缓存空值
  ② 是单点热点吗？   是 → 击穿 → 互斥锁 / 永不过期 + 异步刷
  ③ 是大面积失效吗？ 是 → 雪崩 → TTL 打散 / 高可用 / 限流降级 / 多级缓存
```

## 三大缓存问题速查

| 问题 | 现象 | 根因 | 解法 |
|---|---|---|---|
| **穿透** | 查不存在的 key | 缓存层挡不住 | 布隆过滤器 / 缓存空值 |
| **击穿** | 单热 key 失效瞬间打 DB | 热 key 过期+高并发 | 互斥锁 / 热 key 不过期 / 逻辑过期 |
| **雪崩** | 大量 key 同时失效或集群宕机 | TTL 集中 / 缓存挂 | TTL 打散 / 高可用 / 限流降级 / 预热 |

## Redis 内存淘汰策略 8 种

| 数据范围 | LRU | LFU | Random | TTL |
|---|---|---|---|---|
| **allkeys**（全部） | allkeys-lru | allkeys-lfu | allkeys-random | — |
| **volatile**（设了 TTL 的） | volatile-lru | volatile-lfu | volatile-random | volatile-ttl |
| **noeviction**（不淘汰，写直接报错） — 默认 |
