# 分布式事务（2PC / 3PC / TCC / Saga / 本地消息表 / CAP / BASE） · 15 题

> **高频考点**（每年 1-2 题，案例题高频）· ACID vs BASE · **CAP**（C/A/P 三选二，分区永远存在所以是 CP 还是 AP 二选一）· **PACELC**（分区时 P+CA / 不分区时 L+CA）· **2PC**（准备+提交两阶段，阻塞）· **3PC**（CanCommit/PreCommit/DoCommit，缓解阻塞）· **TCC**（Try/Confirm/Cancel，业务侵入）· **Saga**（长事务+补偿，编排 Orchestration vs 编制 Choreography）· **本地消息表/事务消息**（最终一致）· **XA / JTA**（强一致）· **幂等性**（去重/版本号/状态机）· **分布式锁**（Redis Redlock / ZooKeeper / etcd）

---

### 1. 根据 **CAP 定理**，下列描述**正确**的是：

A. 一个分布式系统可以同时满足 C（一致性）、A（可用性）、P（分区容错性）

✅ **B. 网络分区一定会发生，所以实际是在分区发生时 C 和 A 中二选一**

C. CAP 中的 C 等同于 ACID 中的 C

D. AP 系统不可能做到最终一致性

**答案**：B
**解析**：CAP 由 Eric Brewer 提出——分布式系统**网络分区（P）不可避免**，所以实际权衡是分区发生时选 C（拒绝服务保一致）还是选 A（继续服务允许不一致）。**CP 例**：ZooKeeper、etcd、HBase、传统 RDBMS 集群；**AP 例**：Cassandra、Dynamo、Eureka、CouchDB。**CAP 中的 C 是线性一致性（强一致）**，与 ACID 的 C（约束一致）含义不同。AP 系统通常采用 BASE 思想达成**最终一致性**。

---

### 2. 关于 **BASE 理论**，下列描述**错误**的是：

A. BA = Basically Available（基本可用）

B. S = Soft state（软状态/中间状态可存在）

C. E = Eventual consistency（最终一致性）

✅ **D. BASE 是对 ACID 的强化，要求更严格的强一致性保证**

**答案**：D
**解析**：BASE 是**对 ACID 的弱化**，作为 CAP 中 AP 选项的工程实践指导——通过**牺牲强一致换取可用性和性能**。"基本可用"指允许响应时间下降或部分功能降级；"软状态"指允许多副本暂时不一致；"最终一致"指经过一段时间后达到一致。互联网架构的根基。

---

### 3. **两阶段提交（2PC）** 的根本缺陷**不包括**：

A. 同步阻塞——参与者在第二阶段前必须等待协调者指令

B. 单点故障——协调者宕机会导致参与者锁定资源

C. 数据不一致——第二阶段协调者发送 commit 后部分参与者收不到

✅ **D. 不需要日志支持，恢复机制简单**

**答案**：D
**解析**：2PC 反而**强依赖日志**（协调者和参与者都要写 prepare/commit 日志）才能在崩溃后恢复。三大缺陷正是 ABC：**阻塞、单点、不一致**。2PC 两个阶段：**Prepare（询问+锁资源）+ Commit（统一提交/回滚）**。XA 协议是 2PC 的工业标准实现，被 JTA、MySQL XA 等采用。

---

### 4. **三阶段提交（3PC）** 相比 2PC 的**主要改进**是：

A. 提交速度更快

B. 完全解决了数据不一致问题

✅ **C. 引入超时机制和 CanCommit 预询问阶段，缓解了阻塞问题**

D. 不需要协调者

**答案**：C
**解析**：3PC = **CanCommit + PreCommit + DoCommit**。改进点：①参与者也加入超时（超时后自动 abort 或 commit）；②增加 CanCommit 预询问，让协调者在锁资源前知道是否可行，**降低阻塞概率**。**但仍不能彻底解决数据不一致**——网络分区时 PreCommit 后协调者宕机，部分参与者超时提交、部分回滚仍可能不一致。代价是消息往返多一轮。

---

### 5. **TCC（Try-Confirm-Cancel）** 模式的特征，下列描述**错误**的是：

A. Try 阶段做业务检查和资源预留（如冻结余额）

B. Confirm 阶段执行真正业务（如真扣钱），需要幂等

C. Cancel 阶段释放预留资源（如解冻余额），需要幂等

✅ **D. TCC 对业务无侵入，只需在事务管理器配置即可**

**答案**：D
**解析**：**TCC 的最大代价是业务侵入性极强**——每个服务都要拆出 Try/Confirm/Cancel 三个接口、处理预留资源、保证幂等和悬挂/空回滚问题。换来的好处是**强一致性 + 性能优于 2PC**（不锁数据库行、用业务层补偿）。常见框架：Seata TCC 模式、ByteTCC、Hmily。**适合金融账户类强一致场景**。

---

### 6. **Saga 模式**的核心思想是：

A. 用全局锁锁定所有参与者

✅ **B. 把长事务拆为多个本地短事务，每个事务有对应的补偿事务；任一失败则反向补偿前面已成功的事务**

C. 只允许只读操作

D. 完全放弃事务语义

**答案**：B
**解析**：Saga 起源于 1987 年的论文，专为**长事务**设计。两种实现方式：**编排（Orchestration / 集中式）**——一个协调者按顺序调用各服务并管理补偿；**编制（Choreography / 分布式）**——各服务监听事件自主决定下一步，无中央协调。**优点**：性能好、无全局锁；**缺点**：仅最终一致、补偿事务必须可逆且幂等。Seata Saga 模式支持。

---

### 7. **本地消息表 + MQ** 实现最终一致性的关键步骤是：

A. 业务操作和发消息分别使用两个独立事务

✅ **B. 业务操作和"消息插入本地表"在**同一个本地事务**中完成，再由后台任务把消息推送到 MQ**

C. 必须使用分布式锁

D. 消息只发不接

**答案**：B
**解析**：**核心抓手**：把"发消息"这件事用**本地事务**绑定到业务操作上，二者**同时成功或同时失败**——避免了"业务成功了消息没发出去"的经典问题。流程：①业务操作 + 消息表 insert 在同事务；②后台 worker 扫描消息表 → 推送 MQ → 标记已发；③下游消费并 ACK，**消费要幂等**。RocketMQ 的**事务消息**是它的"升级版"——把消息状态机内置到 MQ 中。

---

### 8. 关于**幂等性（Idempotence）**，下列**不属于**常用实现方式的是：

A. 唯一业务键 + 数据库 unique 约束去重

B. 状态机——只在合法状态转移时执行

C. Token / 版本号 / 乐观锁

✅ **D. 使用 UUID 作为参数让每次调用都不同**

**答案**：D
**解析**：**幂等性 = 同一请求执行 N 次效果等同于执行 1 次**。常用四招：**①唯一键去重**（业务 ID + DB 唯一约束 / Redis SETNX）；**②状态机**（如订单只有"待支付→已支付"才允许扣款，"已支付→已支付"直接成功返回）；**③Token 机制**（先申请 token 再使用，用完作废）；**④版本号/CAS**（乐观锁）。**让每次调用不同**恰好破坏幂等性而不是实现它。

---

### 9. **分布式锁**的常见实现，下列描述**错误**的是：

A. Redis 实现需考虑锁过期但业务未完成的问题，可用 Lua 脚本保证"判断+释放"原子性

B. ZooKeeper 通过临时顺序节点 + watch 实现，无锁过期问题但性能较低

C. etcd 基于 Raft + Lease + Compare-And-Swap 实现

✅ **D. Redis 单实例锁在主从切换时永远不会出现两个客户端同时持锁**

**答案**：D
**解析**：Redis 单实例主从异步复制——加锁后**主节点还没同步到从节点就宕机**、从节点被提升为主、另一个客户端可在新主上再次加锁，**双持锁**。这是 Redlock 算法要解决的问题（多个独立 Redis 实例多数派加锁）。但 Redlock 也被 Martin Kleppmann 质疑其安全性。**强一致场景应优先选 ZooKeeper/etcd**，Redis 锁更适合**容忍偶发问题、追求性能**的场景。

---

### 10. 关于 **2PC / TCC / Saga / 本地消息**四种方案的**一致性强度**，从强到弱排序**正确**的是：

✅ **A. 2PC > TCC > Saga ≈ 本地消息（最终一致）**

B. TCC > 2PC > 本地消息 > Saga

C. 本地消息 > 2PC > Saga > TCC

D. 全部都是强一致

**答案**：A
**解析**：**强一致**（2PC / XA：DB 层全局锁）→ **准强一致**（TCC：业务层 Try 阶段预留资源、可见性受控）→ **最终一致**（Saga / 本地消息表 / 事务消息：先成功部分操作再补偿/通知）。**性能与一致性是倒数关系**：2PC 最慢、最终一致最快。**架构师选型口诀**：金融强一致→TCC/XA；长流程业务→Saga；跨系统通知→事务消息/本地消息表。

### 11. **MQ 消息**保证不丢失需要覆盖三段链路，下列**不属于**这三段的是：

A. 生产端确认（Producer Ack）

B. Broker 持久化（刷盘 + 多副本）

✅ **C. 消息内容必须使用对称加密**

D. 消费端 ACK + 重试

**答案**：C
**解析**：MQ 不丢消息**三大关卡**——①**生产端**：发送 confirm/ack（同步确认），失败重试；②**Broker**：消息持久化（写磁盘）+ 主从/集群（多副本）；③**消费端**：处理成功后才 ACK，失败重试或入死信队列。**加密保护机密性，与丢消息无关**。RocketMQ 同步刷盘 + 同步复制是"最严"配置；Kafka 通过 acks=all + min.insync.replicas 保证。

---

### 12. 关于 **MQ 重复消费**问题，下列描述**错误**的是：

A. 消费端必须设计为幂等以处理重复投递

B. 重复消费的根因常是消费端处理完但 ACK 丢失，导致 Broker 重投

C. 可使用业务唯一键 + DB 唯一约束去重

✅ **D. 只要 Broker 端开启了 exactly-once 语义就不会重复消费**

**答案**：D
**解析**：分布式系统理论上**严格的 exactly-once 投递在通用网络下不可达**——Kafka 0.11+ 的 "exactly-once" 仅指 producer→broker→consumer 的**事务性写入**，跨业务系统场景仍需消费端做幂等。**At-least-once + 消费幂等**才是工业界主流稳定方案。

### 13. 某电商下单场景：扣库存（库存系统）+ 创建订单（订单系统）+ 扣余额（支付系统），要求**用户体验流畅、允许短暂数据不一致**。最佳方案是：

A. 三个系统用 XA / 2PC 强一致

B. 用悲观锁锁住库存表直到全部完成

✅ **C. 用 Saga 编排：依次调用三个本地事务，任一失败时按反向顺序补偿**

D. 全部放在订单系统单库内事务

**答案**：C
**解析**：典型 Saga 场景——**长链路、跨服务、允许最终一致、要求高并发**。Saga 编排（Orchestration）让一个 saga 协调器按"扣库存→创订单→扣余额"顺序调用；任一失败按反向补偿（解冻余额→撤单→回滚库存）。**2PC 锁资源时间太长扛不住电商并发**；单库事务破坏了微服务拆分。**Saga 是电商秒杀、出行、票务等长流程业务的事实标准**。

---

### 14. 关于 **XA 协议**，下列描述**错误**的是：

A. XA 是 X/Open 组织定义的 2PC 分布式事务规范

B. 资源管理器（RM）通常是 DB、MQ；事务管理器（TM）调用 XA 接口协调多个 RM

C. Java 中通过 JTA（Java Transaction API）使用 XA

✅ **D. XA 性能高、是互联网高并发场景的首选**

**答案**：D
**解析**：XA 在 prepare 阶段会**全局锁定**参与者资源直到 commit/rollback，**长时间锁、并发能力差**——不适合互联网高并发，更多用于**银行核心、传统企业 ERP** 等强一致内部场景。互联网公司一般用 TCC/Saga/事务消息 替代。MySQL InnoDB 支持 XA 但生产慎用。

### 15. **Seata** 的四种事务模式中，**对业务无侵入、自动生成回滚日志、性能与一致性平衡较好**的是：

A. XA 模式

✅ **B. AT 模式（Automatic Transaction）**

C. TCC 模式

D. Saga 模式

**答案**：B
**解析**：**Seata AT 模式**——通过 JDBC 代理拦截 SQL，**自动解析前后镜像生成回滚日志**（undo_log 表），业务代码无需修改 Try/Confirm/Cancel，**实质是改良版 2PC**：一阶段提交本地事务但持有全局锁、二阶段异步释放或回滚。**适合短事务、追求开发效率**。Seata 四模式对比：**AT（无侵入、性能中、最终一致）**、**TCC（侵入大、性能高、准强一致）**、**Saga（长流程补偿）**、**XA（强一致、性能低）**。

## 速查对比表

| 方案 | 一致性 | 性能 | 业务侵入 | 适用场景 |
|---|---|---|---|---|
| 2PC / XA | 强一致 | 低 | 无 | 传统金融/ERP 内部、跨库 |
| 3PC | 强一致 | 较低 | 无 | 较少实际应用 |
| **TCC** | 准强一致 | 高 | **大**（拆三接口） | 金融账户、库存 |
| **Saga** | 最终一致 | 高 | 中（补偿接口） | 长流程业务（电商/出行） |
| **本地消息表** | 最终一致 | 高 | 中（消息表） | 跨系统通知 |
| **事务消息**（RocketMQ）| 最终一致 | 高 | 小 | 跨系统通知 |
| **Seata AT** | 最终一致 | 中 | 小 | 短事务、快速开发 |

## CAP / BASE 一图速记

```
CAP：网络分区永远存在 → CP（保一致放弃可用）vs AP（保可用最终一致）
     CP 例：ZooKeeper / etcd / HBase
     AP 例：Cassandra / Eureka / Dynamo

BASE：Basically Available + Soft state + Eventual consistency
      = ACID 的工程化弱化版，互联网架构基石
```
