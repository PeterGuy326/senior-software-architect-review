# ABSD + 视图（4+1 视图 / ADL / RUP） · 12 题

> **高频考点**（每年 1-2 题）· **ABSD（Architecture-Based Software Development，基于架构的软件开发）** 六阶段：架构需求 → 架构设计 → 文档化 → 复审 → 实现 → 演化 · **4+1 视图**（Philippe Kruchten 1995）：**逻辑视图 / 开发视图 / 进程视图 / 物理视图 + 场景视图（用例）**· **RUP 视图**：逻辑/实现/进程/部署/用例 · **ADL（Architecture Description Language，架构描述语言）**：构件 + 连接件 + 配置 三要素；典型 **Wright、Acme、UniCon、Rapide、C2、Darwin、AADL**· 视点（Viewpoint）vs 视图（View）· **架构需求驱动**：关键质量场景（QAS）→ 架构关键决策

---

### 1. **ABSD 方法**的核心思想是：

A. 自底向上从代码归纳出架构

✅ **B. 以软件架构为开发的中心，自顶向下、需求驱动、由架构指导后续设计与实现**

C. 完全摒弃设计文档

D. 只关注代码实现细节

**答案**：B
**解析**：ABSD（Architecture-Based Software Development）由 Bass、Clements 等人提出——**架构先行**，把架构作为整个软件生命周期的中心。**与传统瀑布的区别**：传统是"需求→设计→实现"线性，ABSD 是"先架构、再细化"，强调架构对开发的指导和约束。**与敏捷的关系**：敏捷强调演进式架构，ABSD 强调显式架构决策，两者可结合（Lean Architecture）。

---

### 2. **ABSD 的开发活动**通常包含以下六个阶段，按顺序排列**正确**的是：

✅ **A. 架构需求 → 架构设计 → 架构文档化 → 架构复审 → 架构实现 → 架构演化**

B. 架构设计 → 架构需求 → 架构实现 → 架构演化 → 架构复审 → 架构文档化

C. 需求 → 编码 → 测试 → 部署 → 维护 → 退役

D. 架构需求 → 架构实现 → 架构文档化 → 架构演化

**答案**：A
**解析**：ABSD 六阶段——**①架构需求**（获取功能/质量/约束）→ **②架构设计**（候选架构、风格选择、视图设计）→ **③架构文档化**（输出架构规约 SAD）→ **④架构复审**（同行评审 / ATAM）→ **⑤架构实现**（编码、构件实现、组装）→ **⑥架构演化**（运维期持续演化）。**复审在实现之前**——发现问题成本最低。

### 3. **4+1 视图模型**中，**"+1" 的视图**是：

A. 物理视图

B. 进程视图

✅ **C. 场景视图（Use Case View）—— 用关键用例串联其他 4 个视图，验证架构**

D. 数据视图

**答案**：C
**解析**：**4+1** = 逻辑 + 开发 + 进程 + 物理 + **场景**。**场景视图（用例视图）** 的作用是**验证和驱动**——选取关键用例，让这些用例在其他 4 个视图中跑通，验证架构的合理性。如果某用例在物理视图上无法实现（如延迟超标）则说明架构需要调整。**4+1 是 Kruchten 1995 年提出的经典模型**，RUP 在此基础上发展。

---

### 4. **4+1 视图**中，**逻辑视图**主要关注：

✅ **A. 面向**最终用户的功能性需求**——系统提供的功能、对象/类/包的结构关系**

B. 部署节点和网络拓扑

C. 并发、性能、同步

D. 代码包/模块的物理组织

**答案**：A
**解析**：四视图各自关注点（必记）：**逻辑视图（Logical）**——面向**用户**、表达**功能**（类图、对象图、协作）；**开发视图（Development）**——面向**程序员**、表达**模块/包/源代码组织**（包图、组件图）；**进程视图（Process）**——面向**集成员**、表达**并发/同步/性能/可靠性**（进程、线程、通信）；**物理视图（Physical / Deployment）**——面向**系统工程师**、表达**部署节点/网络/硬件**（部署图）。

---

### 5. **进程视图**关注的核心架构问题是：

A. 数据库表结构设计

B. 用户界面布局

✅ **C. 并发、同步、性能、可伸缩性、分布式通信**

D. 代码风格规范

**答案**：C
**解析**：进程视图回答的是**运行时**的问题——多少个进程/线程？如何同步？吞吐量瓶颈在哪？如何水平扩展？典型表达：**进程间通信图、状态机、序列图**。质量属性中**性能、可用性、可伸缩性**主要在进程视图中体现。

---

### 6. 关于 **RUP 4+1 视图**与 **4+1 经典视图**的对应关系，下列描述**错误**的是：

A. RUP 的逻辑视图对应经典逻辑视图

B. RUP 的**实现视图（Implementation）** 对应经典**开发视图**

C. RUP 的**部署视图（Deployment）** 对应经典**物理视图**

✅ **D. RUP 没有用例视图，用需求文档替代**

**答案**：D
**解析**：**RUP 沿用了"用例视图"作为驱动视图**——RUP 是用例驱动（Use-Case Driven）的过程。RUP 五视图：**逻辑 / 实现 / 进程 / 部署 / 用例**，与 4+1 几乎一一对应，只是把"开发"改名"实现"、"物理"改名"部署"。**RUP 三大特征**：用例驱动、架构为中心、迭代增量。

---

### 7. 关于 **ADL（架构描述语言）**，下列描述**错误**的是：

A. ADL 的三要素是**构件（Component）、连接件（Connector）、配置（Configuration）**

B. **连接件（Connector）** 是 ADL 的核心创新——把交互关系"对象化"，可独立指定其协议、约束

C. 典型 ADL 包括 Wright、Acme、UniCon、Rapide、C2、Darwin、AADL

✅ **D. UML 本身是一种 ADL，可以完全替代专门的 ADL**

**答案**：D
**解析**：**UML 不是严格意义上的 ADL**——UML 是通用建模语言，**缺乏对连接件、约束、风格的形式化语义**。学界把 ADL 视为"专为架构设计、有形式化语义、可推理验证"的语言。UML 通过**Profile 扩展机制**（UML 4 SoaML、MARTE 等）可以模拟部分 ADL 能力，但语义和工具支持仍弱于专用 ADL。**AADL（Architecture Analysis and Design Language）** 在航天嵌入式领域有实际应用。

---

### 8. **ADL 中的"连接件（Connector）"** 与编程语言中的**过程调用**有本质区别，下列描述**错误**的是：

A. 连接件是**一等公民**，与构件并列，可独立建模

B. 一个连接件可以连接多个构件，表达 n-元交互

C. 连接件可以指定协议（如管道、消息、调用、共享变量）和质量属性

✅ **D. 连接件本质上就是函数调用，没有独立存在价值**

**答案**：D
**解析**：传统编程语言中"调用"是隐式的——A 调用 B 就是 B 的代码在 A 的上下文执行，**关系不可见**。ADL 把连接件**显式化**，使得：①能描述**远程调用、消息队列、广播、事件总线**等复杂交互；②能在架构层**推理性能/可靠性**；③能**替换交互机制**（如同步调用换为消息）而不影响构件实现。这是从面向对象（OO）到**面向架构（AO）** 的关键提升。

---

### 9. 关于**视点（Viewpoint）** 与**视图（View）** 的关系（ISO/IEC/IEEE 42010 标准），下列描述**正确**的是：

✅ **A. 视点是"模板/规则"，视图是按视点生成的"具体作品"——一个视点可产生多个视图**

B. 视点和视图完全等同，可互换使用

C. 视点是视图的子集

D. 视点是 4+1 中固定的 5 个

**答案**：A
**解析**：**ISO/IEC/IEEE 42010**（系统/软件工程架构描述标准）严格区分两者：**Viewpoint** 是抽象的"角度模板"——规定该角度该看什么、用什么 notation、回答哪些利益相关方的关切；**View** 是按 Viewpoint 应用到特定系统后生成的具体表达。类比：Viewpoint 是"摄影视角"（俯视/仰视），View 是按该视角拍下的具体照片。**架构描述（AD）= 多个 View 的集合**。

### 10. 在 ABSD 中，**架构需求阶段的关键产出**是：

A. 完整的源代码

✅ **B. 关键质量场景（QAS, Quality Attribute Scenarios）和约束清单**

C. 项目甘特图

D. 用户操作手册

**答案**：B
**解析**：**架构需求 = 功能需求 + 质量属性需求 + 约束**。**质量场景**是 ABSD 与传统需求工程的根本区别——把"高性能"这种模糊词转为**可度量场景**（如"刺激：1000 用户并发；制品：订单服务；响应：95% 请求 < 500ms"）。质量场景六要素：**刺激源、刺激、制品、环境、响应、响应度量**。后续 ATAM 评估也是基于质量场景做敏感点/权衡点分析。

### 11. **架构风格**与**架构视图**的关系，下列描述**错误**的是：

A. 架构风格（如分层、管道-过滤器、MVC）定义了一类系统的通用结构和约束

B. 同一个系统的不同视图可能体现不同风格（逻辑视图分层、进程视图管道）

C. 风格选择是架构设计阶段的核心决策

✅ **D. 一个系统只能采用一种架构风格**

**答案**：D
**解析**：**现代复杂系统普遍是"混合风格"**——比如一个电商系统：整体微服务、订单流转事件驱动、商品搜索 CQRS、内部模块仍可分层。架构师的核心抓手是**为不同层次/子系统选合适风格的组合**，而不是固守单一风格。考试中常考"风格识别"——给出系统描述判断主要采用什么风格。

---

### 12. 关于**架构文档化（SAD, Software Architecture Document）**，下列描述**错误**的是：

A. SAD 应面向多种利益相关方（开发、测试、运维、管理层），用多种视图组织

B. SAD 应记录关键架构决策（ADR, Architecture Decision Record）和理由

C. SAD 是架构演化的基线，变更应可追溯

✅ **D. SAD 编写完成后不应修改，要保持一次成型**

**答案**：D
**解析**：**SAD 是活文档（living document）**——架构演化、决策更新、技术债务都应在 SAD 中反映。当代实践推荐：①**轻量 ADR**（每个决策一篇 markdown，记录上下文/决策/后果）；②**arc42 模板**（12 章节标准结构）；③**C4 模型**（Context/Container/Component/Code 四层缩放图）；④**版本化管理**（与代码一起进 Git）。固化不变的 SAD 几个月后就过时无人看。

## 速查表

### ABSD 六阶段

```
架构需求 → 架构设计 → 文档化 → 复审 → 实现 → 演化
   ↑                                          ↓
   └──────────── 反馈循环 ←───────────────────┘
```

### 4+1 视图职责（必背）

| 视图 | 面向 | 关注 | 表达工具 |
|---|---|---|---|
| **逻辑** | 最终用户 | 功能、对象/类结构 | 类图、对象图 |
| **开发** | 程序员 | 模块/包/源代码组织 | 包图、组件图 |
| **进程** | 集成员/SE | 并发、同步、性能 | 进程图、序列图 |
| **物理** | 系统工程师 | 部署节点、网络 | 部署图 |
| **场景** | 利益相关方 | 关键用例、验证架构 | 用例图、活动图 |

### ADL 三要素

| 要素 | 说明 |
|---|---|
| **构件（Component）** | 系统的计算单元和数据存储 |
| **连接件（Connector）** | 构件间交互的显式抽象（管道/调用/事件/共享） |
| **配置（Configuration）** | 构件 + 连接件的拓扑组合 |

### 质量场景六要素

```
刺激源 → 刺激 → [环境] → 制品 → 响应 → 响应度量
who      what    where     where    how      measure
```

### 典型 ADL

Wright（CSP 形式语义）/ Acme（通用交换）/ UniCon / Rapide（事件驱动）/ C2（GUI 风格）/ Darwin（动态结构）/ **AADL**（嵌入式实时，工业应用）
