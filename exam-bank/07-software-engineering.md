### 1. 关于**瀑布模型**的描述，下列**错误**的是：

A. 严格按"需求分析 → 设计 → 编码 → 测试 → 运维"顺序进行

B. 强调文档驱动，每阶段输出作为下一阶段输入

C. 适用于需求明确、技术成熟、稳定的项目

✅ **D. 鼓励在开发过程中频繁地反向修改前期阶段、拥抱变化**

**答案**：D
**解析**：瀑布模型的根本特征是**单向、文档驱动、阶段严格隔离**，**最大缺点就是不响应变化**——一旦需求变更，回到前面阶段成本极高。"拥抱变化"是**敏捷开发**的核心价值观，与瀑布相反。瀑布适合**国防、航天、金融核心、嵌入式控制**等需求稳定、对正确性要求极高的项目。

### 2. 当用户**对需求不清楚**、希望通过尽快看到可运行版本来逐步明确需求时，最合适的开发模型是：

A. 瀑布模型

B. V 模型

✅ **C. 原型模型（Prototyping）**

D. 喷泉模型

**答案**：C
**解析**：原型模型——**快速构建可运行原型**给用户体验，用户反馈后迭代，**适合需求不明确**的场景。原型分两类：**抛弃式原型**（验证后丢弃，重新正式开发）和**演化式原型**（在原型基础上持续完善为最终系统）。V 模型是瀑布的测试增强版（每阶段开发对应一个测试阶段）；喷泉模型是面向对象的迭代模型。

---

### 3. **螺旋模型**与其他生命周期模型相比，最大的特点是：

A. 强调快速交付

✅ **B. 在每次迭代中加入"风险分析"环节，适用于大型复杂、高风险项目**

C. 完全摒弃文档

D. 适合需求完全明确的小项目

**答案**：B
**解析**：螺旋模型（Boehm 1988）将开发分为**多次螺旋**，每圈四象限：**目标设定 → 风险分析 → 开发与验证 → 计划下一阶段**。**风险分析**是其灵魂，每次迭代都判断"是否继续"。适用于**需求复杂、技术新、不确定性高、规模大**的项目（如大型航天、政务系统）。代价是**重型流程**，不适合小项目。

### 4. **RUP（Rational Unified Process）** 将软件生命周期划分为 4 个阶段，按顺序**正确**的是：

A. 启动 → 构建 → 精化 → 移交

✅ **B. 初始（Inception）→ 精化（Elaboration）→ 构建（Construction）→ 移交（Transition）**

C. 需求 → 设计 → 实现 → 测试

D. 计划 → 分析 → 部署 → 维护

**答案**：B
**解析**：RUP 四阶段是**用例驱动、架构为中心、迭代增量**的统一过程。**初始**：确定项目范围与商业可行性；**精化**：建立可执行架构基线、识别主要风险（最关键的一步）；**构建**：完成所有功能开发；**移交**：交付用户、Beta 测试、培训。每阶段含多次迭代。RUP 9 大工作流：6 个核心（业务建模/需求/分析设计/实现/测试/部署）+ 3 个支持（配置变更/项目管理/环境）。

### 5. **敏捷开发**与传统开发模型相比，下列说法**错误**的是：

A. 强调"个体与互动 高于 流程与工具"

B. 强调"可工作的软件 高于 详尽的文档"

C. 强调"响应变化 高于 遵循计划"

✅ **D. 完全摒弃任何形式的文档与计划**

**答案**：D
**解析**：敏捷宣言强调左侧**优于**右侧，**不是否定右侧**——文档、计划、合同、流程仍然有价值，只是不应僵化。敏捷常见框架：**Scrum**（产品/Sprint Backlog、Daily Standup、Sprint Review/Retro、PO/SM/Dev）、**XP**（结对编程、TDD、持续集成、重构）、**Kanban**（看板、限制 WIP）、**SAFe**（规模化敏捷）。

### 6. **CMMI 5 个成熟度等级**按从低到高的正确顺序是：

A. 初始 → 已定义 → 可重复 → 量化管理 → 优化

✅ **B. 初始（Initial）→ 已管理（Managed）→ 已定义（Defined）→ 量化管理（Quantitatively Managed）→ 优化（Optimizing）**

C. 初始 → 已定义 → 已管理 → 量化管理 → 优化

D. 可重复 → 已定义 → 量化管理 → 优化 → 持续改进

**答案**：B
**解析**：CMMI 阶段式表示 5 级——**1 级初始**（混沌、依赖个人英雄主义）→ **2 级已管理**（项目级管控，需求管理、项目策划/监控、配置管理）→ **3 级已定义**（组织级标准过程，过程剪裁）→ **4 级量化管理**（统计过程控制、度量驱动）→ **5 级优化**（持续改进、缺陷预防）。**老 CMM 的 2 级叫"可重复"**，CMMI 改名"已管理"，这是高频陷阱。

### 7. **需求工程**包含五个主要活动，下列对应**错误**的是：

A. 需求获取：与用户/相关方沟通，识别需要

B. 需求分析：建模、分类、解决冲突

C. 需求规约（Specification）：形成 SRS 文档

✅ **D. 需求实现：编码完成所有功能**

**答案**：D
**解析**：需求工程五大活动——**获取 → 分析 → 规约 → 验证 → 管理**（变更管理贯穿生命周期）。**"需求实现"不是需求工程的活动**，编码是设计/实现阶段的工作。需求验证手段：**评审、原型演示、测试用例追溯、形式化分析**。

### 8. 关于**功能性需求与非功能性需求**，下列描述**错误**的是：

A. 功能需求描述系统**做什么**

B. 非功能需求包括性能、可靠性、安全性、可用性等质量属性

✅ **C. 非功能需求不影响架构设计，仅在实现阶段考虑**

D. 非功能需求往往是**架构的关键驱动力**（Architecturally Significant Requirements）

**答案**：C
**解析**：**非功能需求恰恰是架构设计最大的驱动力**——功能可以靠多种实现方式满足，但要同时满足"5000 TPS + RTO<1min + 等保 3 级"才决定架构形态（是否集群、是否多活、是否分库分表）。**ASR（Architecturally Significant Requirement）** 就是软件架构师的核心抓手，是 ATAM/质量场景的命题源头。

### 9. 下列**需求获取方法**中，**适合大量分散用户**、能在短时间内收集广泛意见的是：

A. 一对一访谈

B. 头脑风暴

✅ **C. 问卷调查**

D. 联合应用开发（JAD）

**答案**：C
**解析**：需求获取主要方法对比——**访谈**（深度高、覆盖小、耗时）、**问卷**（覆盖广、深度浅、适合大量分散用户）、**观察**（适合工人/操作员等说不清楚自己流程的场景）、**原型法**（适合说不清楚要什么）、**JAD（联合应用开发）**（关键相关方集中开会，效率高）、**头脑风暴**（用于创新性需求挖掘）。

### 10. 关于**软件测试的分类**，下列描述**错误**的是：

A. 按是否查看内部结构：**黑盒测试（功能/规约驱动）vs 白盒测试（结构/路径驱动）**

B. 按测试阶段：**单元 → 集成 → 系统 → 验收**

✅ **C. 黑盒测试只能由开发人员执行；白盒测试由用户执行**

D. α 测试在开发方场地由用户参与；β 测试在用户实际环境运行

**答案**：C
**解析**：执行者与盒子颜色无关——**黑盒**通常由独立测试人员或用户做（基于需求规约）；**白盒**由开发或测试工程师做（基于代码结构）。两者互补、缺一不可。其他经典分类：**α 测试**（受控环境、开发方场地、用户/测试参与）vs **β 测试**（真实环境、用户场地、收集反馈）；**回归测试**（变更后验证未影响已有功能）；**冒烟测试**（最基本的可运行验证）。

### 11. 关于**集成测试策略**，下列描述**错误**的是：

A. 自顶向下集成需要**桩程序（Stub）** 模拟下层未完成模块

B. 自底向上集成需要**驱动程序（Driver）** 模拟上层调用

C. 大爆炸集成（Big-Bang）一次性集成所有模块，调试困难

✅ **D. 自顶向下集成可以**最早**测试系统的关键计算/数据处理模块（通常在叶子节点）**

**答案**：D
**解析**：**自顶向下**：先集成主控/顶层模块，**最先验证主控流程和决策结构**——但**关键计算模块通常在底层**，要靠桩模拟，验证晚。**自底向上**：先集成叶子模块，**早期验证底层功能，但主控逻辑最后才验证**。两者优劣对称。**三明治集成**：上下同时往中间集成，折中方案。

### 12. 下列**测试用例设计方法**中，适合处理"多个输入条件的不同组合"逻辑、覆盖各种组合规则的是：

A. 边界值分析

B. 等价类划分

✅ **C. 判定表（决策表）/ 因果图法**

D. 状态迁移法

**答案**：C
**解析**：**判定表/因果图**——把所有输入条件组合枚举为规则表，每条规则一个测试用例，**适合复杂业务规则**（如保险定价、税率计算）。其他方法适用场景：**等价类**（每类选代表）适合输入域大；**边界值**（边界值优先选）适合数值/范围；**状态迁移**适合有状态对象（如订单流转）；**正交实验**（L9 等正交表）适合多参数组合但完全枚举成本高；**错误推测**适合补充。

### 13. 某程序的控制流图中有 12 条边（E）、9 个节点（N），按 **McCabe 圈复杂度**公式计算：

A. 3

B. 4

✅ **C. 5**

D. 7

**答案**：C
**解析**：**McCabe 圈复杂度（环路复杂度）V(G) = E − N + 2 = 12 − 9 + 2 = 5**。另一种等价计算：**V(G) = 判定节点数 + 1**。**圈复杂度含义**：独立线性无关路径数，也是**至少需要的测试用例数**。经验值参考：**V(G) ≤ 10** 为可接受；> 15 复杂；> 20 应重构。

### 14. **软件维护**按目的分为四类，**完善性维护**通常占总维护工作量的：

A. 约 5%

B. 约 20%

✅ **C. 约 60% 以上**

D. 约 90%

**答案**：C
**解析**：软件维护四类——**改正性（Corrective）**：修 bug，~20%；**适应性（Adaptive）**：适应环境变化（OS 升级、数据库换型），~25%；**完善性（Perfective）**：增加新功能/优化性能，**~50-60%（占比最大）**；**预防性（Preventive）**：重构、加测试以预防未来问题，~5%。理解这个分布是软考案例题的常考点。**口诀：完适改预（占比从高到低）**。

### 15. 关于**耦合（Coupling）与内聚（Cohesion）**，下列描述**正确**的是：

A. 好的设计应**强耦合 + 强内聚**

B. 好的设计应**强耦合 + 弱内聚**

✅ **C. 好的设计应**弱耦合 + 强内聚****

D. 好的设计应**弱耦合 + 弱内聚**

**答案**：C
**解析**：软件设计黄金原则——**高内聚（一个模块内部紧密相关）、低耦合（模块间依赖少）**。**耦合 7 级**（从坏到好）：内容耦合 > 公共耦合 > 外部耦合 > 控制耦合 > 标记耦合 > 数据耦合 > 非直接耦合。**内聚 7 级**（从坏到好）：偶然 < 逻辑 < 时间 < 过程 < 通信 < 顺序 < **功能内聚（最强）**。

### 16. 在软件可靠性领域，下列指标对应**正确**的是：

A. MTTF — 平均故障修复时间

✅ **B. MTBF（Mean Time Between Failures）— 平均故障间隔时间，= MTTF + MTTR**

C. MTTR — 平均无故障运行时间

D. 可用性 A = MTTR / (MTBF + MTTR)

**答案**：B
**解析**：**MTTF（Mean Time To Failure）= 平均无故障运行时间**；**MTTR（Mean Time To Repair）= 平均故障修复时间**；**MTBF（Mean Time Between Failures）= 平均故障间隔时间 ≈ MTTF + MTTR**（不可修复系统：MTBF = MTTF）。**可用性 A = MTTF / (MTTF + MTTR) = MTBF 中的可用部分占比**。99.99% 可用性（四个 9）≈ 每年宕机 52.6 分钟。

### 17. 关于**净室软件工程（Cleanroom Software Engineering）**，下列描述**错误**的是：

A. 强调通过形式化方法和数学证明确保软件无缺陷

B. 在开发阶段不进行单元测试，依靠**正确性验证**

C. 使用统计测试方法估计软件可靠性

✅ **D. 主要适用于需求频繁变化的互联网项目**

**答案**：D
**解析**：净室工程脱胎于硬件"无尘室"思想——**通过形式化规约和正确性验证防止缺陷被引入**，而不是事后测试发现。**适用于对可靠性极高要求的航天、医疗、核电、国防等领域**，而**不适合**互联网这种快速迭代、需求频繁变化的场景。代价是开发成本极高、需要数学背景人员。

### 18. 下列关于**软件架构演化与重构**的描述，**错误**的是：

A. 重构（Refactoring）是在不改变外部行为前提下改进内部结构

B. 重构应有自动化测试覆盖以保证安全

✅ **C. 重构是大爆炸式重写，一次完成所有改造**

D. 架构演化常见模式包括绞杀者模式（Strangler Fig）、分阶段迁移

**答案**：C
**解析**：**重构是小步快跑、持续微调、每步可测**——**与重写（Rewrite）形成根本对立**。大爆炸式重写在工业界几乎从不成功（Joel Spolsky 经典文 "Things You Should Never Do"）。架构演化推荐**绞杀者模式**：新系统逐步接管老系统功能，老系统逐步死亡。上云 **6R**：Retain、Retire、Rehost、Replatform、Refactor、Repurchase。

## 速查表

### 生命周期模型适用场景

| 模型 | 特征 | 适用场景 |
|---|---|---|
| **瀑布** | 线性、文档驱动 | 需求稳定、技术成熟（航天/军工） |
| **V 模型** | 瀑布+测试增强 | 高可靠性、强测试要求 |
| **原型** | 快速可运行 | 需求不明确 |
| **增量** | 分块交付完整功能 | 部分需求清晰，可分块 |
| **迭代** | 全功能逐步精化 | 风险高、需早期反馈 |
| **螺旋** | 风险驱动迭代 | 大型复杂高风险 |
| **喷泉** | OO 迭代无缝 | 面向对象项目 |
| **RAD** | 快速开发 | 商业信息系统、有大量可复用构件 |
| **RUP** | 用例驱动+架构中心+迭代 | 大中型 OO 项目 |
| **敏捷** | 拥抱变化、小步快跑 | 需求频繁变化、互联网 |

### CMMI 5 级

| 级 | 名称 | 关键过程域代表 |
|---|---|---|
| 1 | 初始（Initial） | 无 |
| 2 | 已管理（Managed） | 需求管理、项目策划/监控、配置管理 |
| 3 | 已定义（Defined） | 组织级过程、需求开发、技术解决方案 |
| 4 | 量化管理 | 组织级过程绩效、量化项目管理 |
| 5 | 优化（Optimizing） | 因果分析、组织级改进 |

### 耦合 / 内聚 7 级（必记）

```
耦合（坏 → 好）：内容 > 公共 > 外部 > 控制 > 标记 > 数据 > 非直接
内聚（坏 → 好）：偶然 < 逻辑 < 时间 < 过程 < 通信 < 顺序 < 功能
```

### 维护四类占比

- 改正性 ~20% · 适应性 ~25% · **完善性 ~50-60%（最大）** · 预防性 ~5%

### 圈复杂度

- V(G) = E − N + 2 = 判定节点数 + 1
- 也是所需测试用例数下限
