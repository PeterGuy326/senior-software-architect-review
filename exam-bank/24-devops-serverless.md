### 1. 关于 DevOps 的描述，下列**错误**的是：

A. 它是打通开发（Dev）与运维（Ops）的工程文化与实践方法

B. 强调构建、测试、部署、基础设施的全流程自动化

C. 常用 DORA 四大指标来度量团队的交付能力

✅ **D. 它的本质就是引入 Jenkins、Kubernetes 等一套自动化工具的组合**

**答案**：D
**解析**：DevOps 是「文化 + 流程 + 工具」三位一体，自动化工具只是承载手段；把它等同于「装了 Jenkins/K8s」是典型误区。其核心理念用 CALMS（Culture/Automation/Lean/Measurement/Sharing）概括。

---

### 2. DevOps 的核心理念常用 CALMS 五字概括，下列**不属于** CALMS 的是：

A. Culture（文化）

B. Automation（自动化）

✅ **C. Containerization（容器化）**

D. Measurement（度量）

**答案**：C
**解析**：CALMS = Culture（文化）、Automation（自动化）、Lean（精益）、Measurement（度量）、Sharing（分享）。容器化是落地的实现手段之一，并不在 CALMS 字面之内。

---

### 3. 关于持续集成（CI）、持续交付、持续部署的区别，下列说法**正确**的是：

A. 三者完全等价，只是叫法不同

B. 持续交付（Continuous Delivery）每次变更都会自动发布到生产环境

✅ **C. 持续部署在持续交付的基础上去掉了发布前的人工审批，自动上生产**

D. 持续集成（CI）本身就包含把制品自动部署到生产

**答案**：C
**解析**：CI 只负责「代码频繁合并 + 每次自动构建/自动化测试」，不涉及部署；持续交付让制品始终处于「随时可一键发布」状态，但**上线由人工点一下**；持续部署则在所有门禁通过后**全自动发布到生产**，要求灰度/监控/回滚足够成熟。

---

### 4. 一条典型的 CI/CD 流水线，下列阶段顺序**正确**的是：

A. 构建 → 代码提交 → 单元测试 → 部署 → 制品打包

✅ **B. 代码提交 → 构建 → 单元测试 → 静态扫描 → 制品打包 → 部署到环境 → 集成/验收测试 → 发布生产 → 监控**

C. 代码提交 → 单元测试 → 构建 → 制品打包 → 部署 → 监控

D. 代码提交 → 部署 → 构建 → 测试 → 监控

**答案**：B
**解析**：先由提交触发构建出可执行物，再跑单元测试，通过后做静态扫描（SAST）/依赖镜像扫描（SCA），打包成制品/镜像入库，然后逐环境部署并做集成、E2E/验收测试，最后灰度发布到生产并持续监控。安全左移要求 SAST/SCA 尽量放在流水线早期。

### 5. 关于蓝绿部署（Blue-Green Deployment）的描述，下列**正确**的是：

✅ **A. 准备两套完全相同的环境，新版本在「绿」环境就绪后整体切换流量，出问题可瞬时切回「蓝」环境**

B. 新版本先接管 1%→10%→100% 的流量，逐步放量

C. 逐批替换实例，新旧版本短时共存、平滑过渡

D. 按用户特征把不同版本投给不同人群，目的是对比业务转化率

**答案**：A
**解析**：选项 B 描述的是金丝雀（灰度）发布，C 是滚动发布，D 是 A/B 测试。蓝绿部署回滚最快（秒级切回），代价是需要双倍环境资源。

---

### 6. 关于金丝雀（灰度）发布，下列说法**错误**的是：

A. 新版本先接管一小比例流量（如 1%）

B. 以监控指标（错误率、P99 延迟等）作为是否继续放量的门禁

C. 出问题时只需把流量缩回去或下掉金丝雀实例即可

✅ **D. 必须准备两套完全相同的环境同时运行，再整体切换流量**

**答案**：D
**解析**：「两套完全相同环境整体切换」是蓝绿部署的特征；金丝雀只需多出少量金丝雀实例，按流量比例（1%→10%→50%→100%）渐进放量，并用观测指标作为放量门禁。金丝雀 ≠ 滚动：滚动是按实例批次逐批替换，本身不带流量比例门禁。

---

### 7. 关于蓝绿、金丝雀、滚动三种发布策略的对比，下列说法**错误**的是：

A. 蓝绿部署回滚最快，但需要双倍环境资源

B. 金丝雀发布资源开销较小，可按指标渐进放量、风险可控

C. 滚动发布是 Kubernetes 默认的更新方式，逐批替换实例、过程无中断

✅ **D. 滚动发布出现问题时可像蓝绿一样瞬时整体切回旧版本**

**答案**：D
**解析**：滚动发布回滚时需要按实例批次逐批回退到上一版本，速度为「中等」，做不到蓝绿那样的瞬时整体切换。能瞬时回滚的是蓝绿（切回旧环境即可）。

### 8. 下列工具中，定位为「GitOps 持续部署控制器」（以 Git 仓库为期望状态、持续把 Kubernetes 集群对齐到 Git 声明）的是：

A. Jenkins

B. Ansible

✅ **C. Argo CD**

D. Prometheus

**答案**：C
**解析**：Jenkins 是 CI/CD 流水线编排引擎，Ansible 是配置管理工具，Prometheus 是监控系统；Argo CD（以及 Flux）是 GitOps 工具，在集群里跑控制器持续比对 Git 中的期望状态与集群实际状态并自动同步。

---

### 9. 关于持续集成（CI）的目的，下列说法**错误**的是：

A. 鼓励开发者频繁把代码合并到主干，减少长期分支带来的合并冲突

B. 每次合并都触发自动构建与自动化测试，尽早暴露集成问题

C. 目标之一是让主干始终处于「可构建、可测试通过」的健康状态

✅ **D. CI 的最终目的是把每次提交都自动发布到生产环境**

**答案**：D
**解析**：「自动发布到生产」是持续部署（Continuous Deployment）的目标，不是 CI。CI 的核心是「早集成、早暴露、保持主干随时可构建」，是持续交付/持续部署的前提，但本身不涉及生产部署。

---

### 10. 关于基础设施即代码（IaC），下列说法**错误**的是：

A. 用代码/配置文件描述基础设施（网络、虚机、集群、数据库等）并纳入版本控制

B. 声明式 IaC 描述「期望的最终状态」，由工具自行计算差异并收敛

C. 幂等性意味着同一份配置应用一次和应用 N 次的结果一致

✅ **D. 引入 IaC 后，基础设施变更必须改为手工在云控制台逐项操作以保证安全**

**答案**：D
**解析**：IaC 的目的恰恰是让基础设施变更走代码评审 + 流水线，做到可重复、可审计、可回滚，**取代手工点控制台**。声明式 + 幂等性是 IaC 的核心属性，配合不可变基础设施可消除配置漂移。

---

### 11. 关于 Terraform 与 Ansible 的对比，下列说法**正确**的是：

✅ **A. Terraform 偏向声明式的资源编排（建出 VPC/集群/数据库等），Ansible 偏向在已有主机上做配置管理（装软件、改配置）**

B. 两者都只能管理 AWS 平台的资源

C. Ansible 必须在每台被管机器上常驻一个 Agent 才能工作

D. Terraform 本质是一套命令式 Shell 脚本，且无法跨云

**答案**：A
**解析**：Terraform 跨云、声明式，用 state 文件记录现状，负责「把机器/集群建出来」；Ansible 无 Agent（基于 SSH push）、playbook 偏命令式，负责「把建好的机器配置好」。两者常配合使用——先 Terraform 建，再 Ansible 配。

---

### 12. 关于 GitOps，下列说法**错误**的是：

A. 以 Git 仓库作为系统期望状态的「单一可信源（Single Source of Truth）」

B. 通过 Argo CD / Flux 等控制器持续把集群对齐到 Git 中的声明（拉取式部署）

C. 回滚可以通过 git revert 把声明退回到上一个版本来实现

✅ **D. 强调由运维人员直接登录服务器手工修改配置，以提高变更效率**

**答案**：D
**解析**：直接登服务器手改正是 GitOps 要消灭的「配置漂移」来源。GitOps = 声明式 + 版本化 + 自动协调，每次变更都是一次 commit/PR，审计可追溯、权限收敛在 Git。

---

### 13. 关于 Docker 镜像分层，下列说法**正确**的是：

✅ **A. Dockerfile 每条指令生成一层只读层，层可被缓存复用，应把不常变的内容（基础镜像、依赖安装）放在前面**

B. 一个镜像只有一层，无法被其他镜像复用

C. 容器运行时不能在镜像层之上写入任何数据

D. 把应用代码放在 Dockerfile 最前面能最大化构建缓存命中

**答案**：A
**解析**：不常变的内容放前面、常变的（应用代码）放后面，能最大化缓存命中、减小镜像拉取量；容器运行时会在只读镜像层之上叠加一个可写层。把应用代码放最前面反而会让后续每层都失效。

---

### 14. 关于不可变基础设施（Immutable Infrastructure），下列说法**正确**的是：

A. 部署后经常登录服务器原地打补丁、改配置

✅ **B. 实例一旦部署就不再原地修改，升级即用新镜像替换旧实例（重建而非修补）**

C. 它只适用于物理机，不适用于云主机和容器

D. 它与容器镜像、AMI、Packer 等没有关系

**答案**：B
**解析**：不可变基础设施奉行「重建而非修补」——升级 = 构建新镜像 → 推仓库 → 用新镜像替换旧实例，回滚 = 换回旧镜像，从而保证各环境实例都来自同一份可追溯的镜像，彻底消除「手改后没人知道改了啥」。它常配合容器镜像、AMI、Packer 实现。

---

### 15. 按 12-Factor App（十二要素）原则，应用的配置（如数据库地址、密钥）应当：

A. 硬编码在源代码里

✅ **B. 存放在环境变量中，与代码严格分离**

C. 直接写死打包进 Docker 镜像

D. 由 DBA 在每台生产机上手工维护

**答案**：B
**解析**：「配置存于环境变量、与代码严格分离」是 12-Factor 第 3 条（Config），保证「一次构建、多环境运行」。容器化场景下通常通过环境变量 / ConfigMap / Secret 注入。

### 16. 关于 Serverless / FaaS（函数即服务）的特征，下列说法**错误**的是：

A. 按实际调用量计费（执行时长 × 内存），不调用基本不花钱

B. 自动弹性伸缩，可从 0 扩到 N、闲时缩回

C. 由事件触发执行（对象存储上传、消息到达、HTTP 请求、定时器等）

✅ **D. 特别适合承载需要长连接、长时间运行的有状态服务（如 IM 长连、游戏服）**

**答案**：D
**解析**：长连接（IM/游戏）、长任务（执行时长一般有 ~15 分钟上限）、强状态计算都不适合 FaaS——FaaS 实例无状态、随时被回收。它擅长低频长尾、突发流量、事件处理（如图片上传后生成缩略图）、定时任务、Webhook 等场景。「无服务器」是指对使用者透明，不是真没有服务器。

### 17. 关于 FaaS 的冷启动（Cold Start）问题，下列说法**错误**的是：

A. 函数实例不存在时需要拉起容器、加载运行时、初始化代码，会引入额外延迟

B. 首次调用、突发扩容、长时间无调用被回收后再调用，都容易触发冷启动

C. 可用预留/预热实例（Provisioned Concurrency）、精简依赖包、轻量运行时（如 GraalVM AOT 原生镜像）、把初始化代码移出处理函数等方式缓解

✅ **D. 冷启动只影响计费金额，不会影响请求的响应延迟**

**答案**：D
**解析**：冷启动会直接拉高首个/扩容请求的响应延迟（几十毫秒到数秒，Java/.NET 较重），对延迟敏感的接口需重点优化。它影响的是延迟而非计费。

### 18. 关于 Knative，下列说法**正确**的是：

✅ **A. 它是构建在 Kubernetes 之上的 Serverless 框架，支持按请求自动扩缩（含缩容到 0）和事件驱动**

B. 它是一种关系型数据库

C. 它是一个 CI 流水线引擎，专门用于编译和构建代码

D. 它只能运行在 AWS 云平台上

**答案**：A
**解析**：Knative（含 Serving + Eventing 两部分）让你在自己的 K8s 集群上获得「按需扩缩、缩容到 0、事件驱动」的 Serverless 体验，规避厂商绑定；同类自建/开源方案还有 OpenFaaS、Kubeless。商用产品则有 AWS Lambda、阿里云函数计算 FC、腾讯云 SCF 等。

### 19. 关于 DORA 四大指标，下列说法**错误**的是：

A. 四大指标为：部署频率、变更前置时间（Lead Time for Changes）、变更失败率、服务恢复时间（MTTR）

B. 部署频率和变更前置时间衡量交付速度（吞吐）

C. 变更失败率和 MTTR 衡量交付质量与稳定性

✅ **D. 团队只需一味提高部署频率，其余三个指标无关紧要**

**答案**：D
**解析**：四个指标要平衡看——只追部署频率而不顾变更失败率和 MTTR，会变成「快而脆」。DORA 据此把团队分为 Low / Medium / High / Elite 四档，Elite 级大致对应「按需部署（日多次）、Lead Time < 1 天、变更失败率 < 15%（通常 < 5%）、MTTR < 1 小时」。
