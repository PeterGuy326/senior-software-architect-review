# 软件工程速查表（生命周期 / CMMI / 需求 / 测试 / 维护）

## 生命周期模型对比

| 模型 | 特征 | 适用场景 |
|---|---|---|
| **瀑布（Waterfall）** | 线性、文档驱动、阶段严格 | 需求稳定、技术成熟（航天/军工/金融核心） |
| **V 模型** | 瀑布+测试增强（每开发阶段对应测试） | 高可靠性、强测试要求 |
| **原型（Prototyping）** | 快速可运行、抛弃式 / 演化式 | 需求不明确，用户说不清想要什么 |
| **增量（Incremental）** | 按模块分块完整交付 | 部分需求清晰、可拆分 |
| **迭代（Iterative）** | 全功能逐步精化 | 风险高、需早期反馈 |
| **螺旋（Spiral）** | 风险驱动迭代（4 象限） | 大型复杂、高风险、不确定性高 |
| **喷泉（Fountain）** | 面向对象、迭代无缝 | OO 项目 |
| **RAD** | 快速开发、大量可复用构件 | 商业信息系统 |
| **RUP** | 用例驱动 + 架构中心 + 迭代增量 | 大中型 OO 项目 |
| **敏捷（Agile）** | 拥抱变化、小步快跑 | 需求频繁变化、互联网 |
| **净室（Cleanroom）** | 形式化验证、缺陷预防 | 航天 / 医疗 / 核电 |
| **DevOps** | 开发-运维一体化 + CI/CD | 持续交付场景 |

## RUP 四阶段

```
Inception 初始 → Elaboration 精化 → Construction 构建 → Transition 移交
（确定范围）    （建立架构基线）   （完成功能开发）  （部署到用户）
```

RUP 三大特征：**用例驱动 + 架构中心 + 迭代增量**

## CMMI 5 级（必背）

| 级 | 名称 | 关键过程域代表 | 通俗描述 |
|---|---|---|---|
| 1 | 初始（Initial） | 无 | 混沌、英雄主义 |
| 2 | 已管理（Managed） | 需求管理、项目策划、项目监控、配置管理、QA | 项目级有章可循 |
| 3 | 已定义（Defined） | 组织级标准过程、需求开发、技术解决方案、集成产品 | 组织级标准化 |
| 4 | 量化管理（Quantitatively Managed） | 组织级过程绩效、量化项目管理 | 数据驱动 |
| 5 | 优化（Optimizing） | 因果分析、组织级改进 | 持续改进 |

> **坑**：CMMI 的 2 级叫"**已管理**"（CMMI 1.3 后），老 CMM 叫"可重复"——考试时按 CMMI 选已管理。

## 需求工程五大活动

```
获取（Elicitation） → 分析（Analysis） → 规约（Specification） → 验证（Verification） → 管理（Management，贯穿全生命周期）
```

### 需求分类（IEEE/Sommerville）

| 层次 | 含义 | 输出 |
|---|---|---|
| **业务需求** | 公司/项目层面想达成什么 | 项目愿景、商业目标 |
| **用户需求** | 用户站在自己角度的需求 | 用户故事 / 用例 |
| **系统需求** | 系统实现层面要做什么 | SRS（功能 + 非功能 + 约束） |

### 功能 vs 非功能

- **功能需求**：系统**做什么**（FR）
- **非功能需求**：系统**做得怎么样**（NFR）= 质量属性（性能 / 可靠性 / 安全 / 可用 / 可维护 / 可移植）+ 约束（技术栈、合规、运行环境）
- **NFR 是架构的关键驱动力**（ASR）

### 需求获取方法

| 方法 | 适用 |
|---|---|
| 访谈 | 深度、覆盖小、耗时 |
| 问卷 | 大量分散用户、深度浅 |
| 观察 | 用户说不清自己流程时 |
| 原型 | 用户说不清要什么时 |
| **JAD**（联合应用开发） | 关键相关方集中讨论、效率高 |
| 头脑风暴 | 创新性需求挖掘 |
| 文档分析 | 已有业务流程梳理 |

## 软件测试矩阵

### 按是否查看内部结构

| 类型 | 视角 | 典型方法 |
|---|---|---|
| **黑盒（功能/规约驱动）** | 输入 → 输出 | 等价类 / 边界值 / 因果图 / 判定表 / 正交实验 / 错误推测 |
| **白盒（结构/路径驱动）** | 内部代码与流程 | 语句覆盖 / 分支覆盖 / 条件覆盖 / 路径覆盖 / MC/DC |
| **灰盒** | 部分了解内部 | 接口测试常用 |

### 按测试阶段

```
单元测试 → 集成测试 → 系统测试 → 验收测试
（Unit）   （Integration） （System） （Acceptance：α / β）
```

- **集成测试策略**：自顶向下（用 Stub）、自底向上（用 Driver）、大爆炸（不推荐）、三明治
- **α 测试**：开发方场地 + 受控环境 + 用户参与
- **β 测试**：用户场地 + 真实环境 + 收集反馈
- **回归测试**：变更后验证未影响已有功能
- **冒烟测试**：最基本可运行验证（"接通电源不冒烟"）

### 覆盖率层级（弱到强）

```
语句覆盖 < 分支覆盖 < 条件覆盖 < 条件/分支覆盖 < 路径覆盖 < MC/DC（航空 DO-178B 强制）
```

## 软件维护四类（占比必记）

| 类型 | 含义 | 占比 |
|---|---|---|
| **改正性（Corrective）** | 修 bug | ~20% |
| **适应性（Adaptive）** | 适应环境变化（OS / DB 升级） | ~25% |
| **完善性（Perfective）** | 加新功能、性能优化 | **~50-60%（最大）** |
| **预防性（Preventive）** | 重构、加测试预防未来问题 | ~5% |

**口诀**：完适改预（占比从高到低）

## McCabe 圈复杂度

```
V(G) = E − N + 2
     = 判定节点数 + 1
     = 独立线性无关路径数
     = 所需测试用例数下限
```

经验阈值：**≤ 10 简单 · 11-20 中等 · 21-50 复杂 · > 50 重构**

## 耦合 / 内聚 7 级

```
耦合（坏→好）：内容 > 公共 > 外部 > 控制 > 标记 > 数据 > 非直接
内聚（坏→好）：偶然 < 逻辑 < 时间 < 过程 < 通信 < 顺序 < 功能
```

设计目标：**低耦合 + 高内聚**

## 配置管理三要素

```
基线（Baseline，已评审批准的版本）
   ↓
变更控制（CCB 审批）
   ↓
配置审计（确认变更已正确实施）
```
